Why ML needs its own "Ops"

In normal software only the code changes. In ML, three things change — and any one can break production.

DevOps (you know this)MLOps adds
Version the code (git)Version the data and the model too (DVC, model registry)
Unit tests: pass / failModel tests: "MAE under 6 min and better than the current model"
CI → build → deploy+ CT (continuous training): retrain when the world changes
Monitor errors, latency+ monitor inputs (drift) and accuracy, which fail silently: no exception, just wrong answers
Hidden technical debt (Sculley et al., Google 2015): in a real ML system the model code is a small box surrounded by data collection, feature pipelines, serving, monitoring and config. That surrounding 90% is what MLOps is about. (Same picture as SE4ML Session 2.)
Interview line: "MLOps is DevOps plus two moving parts, data and models. Models fail silently, so you add data versioning, model tests as CI gates, continuous training and monitoring for drift."

Experiment: baseline first, and one feature function

Two habits that prevent most beginner failures.

Habit 1 · Always have a baseline

"Predict the average" → MAE 9.2 minvsGradient boosting → MAE 2.6 min=72% better ✔ worth deploying

A model that can't clearly beat "always say 38 minutes" isn't worth a server.

Habit 2 · Training and serving share one feature function

In the codebase: features.py → imported by train.py AND serve.py. In industry: a feature store (Feast, Tecton) serves the same features to training and to the live API.

Monitor: the monsoon arrives

Models don't crash when the world changes — they quietly become wrong. Drag the slider to bring the monsoon.

Monsoon strength

Kitchen prep time (prep_min): ■ training data vs ■ live data

PSI = 0okModel error (MAE): 2.6 min
Data driftConcept drift
What changesThe inputs (more rain, longer prep)The rule input → output (rain now costs 15 min, not 9)
Needs labels?No: compare input distributions (PSI, KS test)Yes: wait for real delivery times, compute MAE
DeliverEase signalPSI on is_raining 1.73, prep_min 1.36 → ALERTMAE jumps 2.6 → 10.9 min

PSI (Population Stability Index): split training values into bins; compare the % in each bin now vs then. PSI = Σ (a% − e%) · ln(a% / e%). < 0.1 ok · 0.1–0.25 watch · > 0.25 alert.

Monitor three layers: system (latency, errors: Prometheus/Grafana) · data (drift: Evidently, Arize) · model (accuracy once labels arrive). Feedback loop: labels arrive late (delivery finishes 40 min later), so drift is your early warning.

Retrain and test in production

The pipeline retrains on monsoon data. Now: how do you swap models without betting every customer on it?
