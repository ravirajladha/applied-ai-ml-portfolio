Manual Testing & QA Fundamentals

Q1 – Q41 · Even for a pure automation role, the first 15 minutes are usually manual/process questions. This is where interviewers decide whether you think like a tester or only code like one.

Q1What is software testing, and what is its real objective?▼

Software testing is the process of evaluating a system to find the difference between expected and actual behaviour, and to give stakeholders information about the quality and risk of releasing it.

The objective is not "to find all bugs"

Exhaustive testing is impossible — a single form with 10 text fields has effectively infinite input combinations. The real objectives are:

  • Find defects early, when they are cheapest to fix (a requirement defect costs ~1x to fix in analysis, ~100x in production).
  • Reduce risk to an acceptable level and provide evidence for a go/no-go decision.
  • Prevent defects — reviewing a requirement and asking "what happens if the amount is negative?" prevents a bug from ever being coded.
  • Build confidence that the product meets business and user needs.
Say this in the interview: "Testing shows the presence of defects, not their absence." It is one of the seven ISTQB testing principles and instantly signals you know the fundamentals.

Q3QA vs QC vs Testing — how are they different?▼
  • Quality Assurance (QA) — process oriented, preventive. Defining and improving the process so defects do not get created: definition of done, code review standards, branching strategy, CI gates, test entry/exit criteria, audits. QA is proactive.
  • Quality Control (QC) — product oriented, corrective. Checking the actual built product against requirements to detect defects. Reactive.
  • Testing — a subset of QC: the concrete activity of executing the system with inputs to observe behaviour.

Relationship: QA ⊃ QC ⊃ Testing.

Interview angle: "In my team QA is when I insist that no story is 'done' without automated regression coverage and a passing pipeline; QC is when I execute that regression suite on the release build."

Q6What are entry and exit criteria? Give real examples.▼

Entry criteria = conditions that must be true before a test phase can start. Exit criteria = conditions that must be true before it can be declared complete.

Example — System Test phase
  • Entry: requirements signed off; test cases reviewed and approved; test environment available and stable; build deployed and smoke test passed; unit & integration tests green.
  • Exit: 100% of planned test cases executed; ≥ 95% pass rate; zero open Critical/High defects; all Medium defects triaged with an agreed fix or deferral; regression suite green; test summary report signed off.
Trap follow-up: "What if the deadline arrives and exit criteria are not met?" Correct answer: you do not silently pass it. You escalate with data — which criteria failed, the open defect list with severity, the risk of releasing anyway — and the business owner takes the go/no-go decision. QA's job is to expose risk, not to own the release decision alone.

Q8Test Scenario vs Test Case vs Test Script?▼
  • Test Scenario — a one-line statement of what to test, from the user's point of view. "Verify user can log in." It answers "what areas must we cover?"
  • Test Case — a detailed, repeatable set of steps with preconditions, test data, and an expected result for one condition. "Login with valid username and invalid password."
  • Test Script — the automated/coded implementation of a test case.

One scenario typically explodes into 8–15 test cases (valid, invalid, empty, locked account, case sensitivity, SQL injection, session behaviour, remember-me, etc.).

Why interviewers ask: they want to see that you go from a vague requirement to a structured set of conditions. If they say "give me test scenarios for a login page", answer in categories: functional positive, functional negative, boundary, security, UI/usability, performance, compatibility, accessibility. Categories score far higher than a random list.

Q10Explain Equivalence Partitioning with an example.▼

Divide the input domain into classes where the system is expected to behave identically, then test one representative value from each class. Rationale: if one value in a class fails, all of them will — so testing 1 value instead of 1000 gives the same defect-finding power for 0.1% of the effort.

Example — "Age must be between 18 and 60"
PartitionRangeRepresentativeExpected
Invalid (low)< 1810Reject
Valid18 – 6035Accept
Invalid (high)> 6075Reject
Invalid (type)non-numeric / empty / negative / decimal"abc", "", -5, 22.5Reject with proper message

4 tests instead of hundreds. It applies to outputs and to non-numeric data too (e.g. user roles: admin / manager / guest are three partitions).

Q11Explain Boundary Value Analysis. Why is it more effective than EP alone?▼

Defects cluster at the edges of partitions because that is where developers write > instead of >= or use <= size instead of < size. BVA tests the values at and around each boundary.

For "Age 18 to 60"
  • 2-value BVA (each boundary ± 1): 17, 18  |  60, 61
  • 3-value BVA (min-1, min, min+1, max-1, max, max+1): 17, 18, 19, 59, 60, 61

EP and BVA are used together: EP tells you which classes exist, BVA tells you which specific values inside/around them to pick.

Other boundaries people forget: string length limits (0, 1, max, max+1 characters), file upload size, pagination (page 0, page 1, last page, last+1), dates (leap year 29-Feb, month-end 31st, year rollover 31-Dec 23:59:59), and empty/one/many for lists.

Q12What is Decision Table testing? When do you use it?▼

Used when the output depends on a combination of conditions (business rules), not on a single input range. You enumerate all condition combinations and their expected actions, which guarantees no rule is missed.

Example — discount rule: "Premium members get 20% off; orders above ₹5000 get 10% off; they do not stack — the higher applies."
RuleR1R2R3R4
Premium member?YYNN
Order > ₹5000?YNYN

With n binary conditions you get 2^n rules. For large tables you collapse impossible/irrelevant combinations using "–" (don't care) entries.

This is the technique to name when asked "how would you test a loan eligibility / insurance premium / pricing engine?" — combination logic is exactly what decision tables are for.

Q13What is State Transition testing?▼

Used when the system's response depends on its current state and history, not just the current input. You model states, events, transitions and actions, then design tests that cover valid transitions — and importantly, attempt invalid ones.

Example — ATM card / login states

Active → (1 wrong PIN) → Active(1 fail) → (2nd wrong) → Active(2 fails) → (3rd wrong) → Blocked → (admin unblock) → Active

  • Valid transition tests: each arrow above.
  • Invalid transition tests (high value): can a Blocked card be used with the correct PIN? Can a cancelled order be shipped? Can a submitted-and-approved leave request be edited? These find the most bugs.
  • Coverage levels: 0-switch = every single transition once; 1-switch = every valid pair of consecutive transitions.

Great real-world fits: order lifecycle (Created → Paid → Shipped → Delivered → Returned), ticket workflow, subscription (Trial → Active → Past-due → Cancelled).

Q14What is pairwise (all-pairs) / orthogonal array testing?▼

A combinatorial reduction technique. Research shows most defects are triggered by a single parameter or an interaction between just two parameters. So instead of testing all combinations, you generate the smallest set of tests in which every pair of parameter values appears at least once.

Example

Browser (Chrome, Firefox, Safari) × OS (Windows, macOS, Linux) × Payment (Card, UPI, Wallet) × Language (EN, HI) = 3×3×3×2 = 54 full combinations. Pairwise reduces this to roughly 9–10 tests while still covering every browser-OS, browser-payment, OS-payment and language pair.

Tools: PICT (Microsoft), ACTS (NIST), pairwise npm/pip libraries, or Hexawise.

Caveat to mention: pairwise will not catch a bug that only appears with a specific 3-way combination, and it is blind to business-critical combinations. So you always seed the must-test combinations (e.g. Chrome + Windows + Card) and let the tool fill in the rest.

Q15Error guessing and exploratory testing — are they just "random testing"?▼

No. Both are experience-based techniques with structure.

  • Error guessing — deliberately trying inputs that historically break systems: empty submit, whitespace-only, very long strings, special characters <script> / '--, 0 and negative numbers, duplicate submit (double click), browser back after submit, session timeout mid-flow, network drop mid-payment, copy-paste with trailing spaces, emoji in a name field.
  • Exploratory testing — simultaneous learning, test design and execution, time-boxed and charter-driven. This is Session-Based Test Management: a 60–90 minute session with a written charter ("Explore checkout with expired coupons to discover pricing errors"), notes taken during the session, and a debrief afterwards. That is what makes it auditable rather than random.
  • Monkey/random testing is the truly unstructured one — random inputs, no oracle beyond "did it crash".
Strong line: "Automation checks what we already know; exploratory testing discovers what we didn't think of. I reserve one timeboxed exploratory session per sprint for the newly built feature and it consistently finds defects my scripted cases miss."

Q19Regression vs Retesting (confirmation testing).▼
  • Retesting — re-executing the exact failed test case with the same data on a new build to confirm the defect is fixed. Always uses the defect's reproduction steps. Cannot be planned in advance (you don't know which tests will fail). Priority: done first.
  • Regression — re-executing previously passing tests to confirm the fix or new feature did not break anything else. Can be planned and is the #1 candidate for automation.
Regression selection strategy (asked as a follow-up)

You rarely run everything. Selection approaches:

  1. Full regression — before a major release or after a framework/infra change.
  2. Regional / impact-based — analyse the changed module and its dependencies (talk to the dev, read the PR diff) and run those areas.
  3. Risk-based — always include revenue-critical flows (login, checkout, payment) regardless of what changed.
  4. Test-impact analysis — modern tooling maps code changes to the tests that cover them and runs only those.

Q20Explain the integration testing approaches.▼
  • Big Bang — integrate everything at once, then test. Simple but fault isolation is a nightmare. Only for very small systems.
  • Top-down — test high-level modules first, using stubs (dummy called-modules) for the not-yet-built lower ones. Advantage: the main control flow / UI is validated early.
  • Bottom-up — test low-level modules first using drivers (dummy calling-modules). Advantage: core utilities are proven early; disadvantage: no working product to demo until late.
  • Sandwich / Hybrid — both directions meeting in the middle. Most common in practice.
  • Incremental / continuous — in modern microservices, integration is verified continuously using contract testing (Pact) and service virtualisation (WireMock, MockServer).
Stub vs Driver in one line: a stub replaces the module being called (used in top-down); a driver replaces the module that calls (used in bottom-up). Mnemonic: Stub is Subordinate, Driver Drives from above.

Q21System testing vs UAT. What are alpha and beta testing?▼
  • System testing — QA validates the complete, integrated system against the specified requirements in a QA environment. Includes functional + non-functional.
  • UAT — the business/end user validates against business needs and real-world workflows in a UAT/pre-prod environment with production-like data. Passing system tests does not guarantee passing UAT: the software can match the spec and still not fit how the business actually works.
  • Alpha testing — done by internal staff (often non-QA employees) at the developer's site, in a controlled environment, before release.
  • Beta testing — done by real external users in their own environment, uncontrolled. Feedback is collected, not scripted. Also called field testing.

Related modern practices worth mentioning: canary release (roll out to 1% of production traffic), feature flags / dark launch, and A/B testing — these have largely replaced long beta phases in SaaS.

Q22Explain the test automation pyramid. Do you agree with it?▼

Mike Cohn's pyramid says the bulk of automated tests should be fast unit tests, a smaller layer of service/API tests, and a thin layer of UI end-to-end tests. The reasoning is economics: as you go up, tests get slower, more brittle, more expensive to maintain, and harder to debug — but each one gives more end-user confidence.

The right answer to "do you agree?"

"Directionally yes — the principle is push every check to the lowest layer that can still catch the defect. But I treat the ratios as guidance, not law. On a micro-services back-end I lean heavily on contract and API tests, and the 'trophy' shape (heavy integration layer) fits better. What I do defend strictly is: the UI layer only covers critical user journeys — login, search, add-to-cart, checkout, payment — not field-level validations, which belong in unit/component tests."

Anti-patterns to name: the ice-cream cone (huge manual + UI layer, no unit tests → 4-hour suites, constant flakiness) and the cupcake (dev, QA and business each build their own duplicated layers).

Q23What is shift-left testing? What about shift-right?▼

Shift-left = moving testing activities earlier in the lifecycle instead of treating testing as a phase after coding.

  • QA joins requirement refinement and challenges acceptance criteria (the "three amigos": BA + Dev + QA).
  • Static testing: requirement reviews, design reviews, code reviews, linting, SAST.
  • Developers write unit & component tests; QA writes API tests before UI exists (against contracts/mocks).
  • TDD / BDD / ATDD — tests written before the code.
  • CI gates: no merge without passing tests and coverage thresholds.

Shift-right = continuing to test in production, because no pre-prod environment fully models reality: synthetic monitoring, canary releases, feature flags, A/B tests, real-user monitoring, chaos engineering, and observability-based alerting on error rates.

A modern QA answer covers both: "Shift left to prevent defects, shift right to detect what escaped. I owned the synthetic monitoring checks that re-used our Playwright login and checkout tests against production every 15 minutes."

Q24Walk me through the defect life cycle.▼
  1. New — tester logs the defect.
  2. Assigned — triage/lead assigns it to a developer.
  3. Open / In Progress — developer accepts and starts working. From here it can also go to Rejected, Duplicate or Deferred.
  4. Fixed — code change done and merged to the test branch.
  5. Retest / Ready for QA — deployed to QA; tester re-executes the original steps.
  6. Closed — verified fixed by the tester. If it still fails → Reopened and back to the developer.
Terminal / side states
  • Rejected / Not a bug — behaviour matches the requirement. Your response: re-read the spec; if you still disagree, take it to the BA/PO as a possible requirement defect.
  • Duplicate — already reported; link to the original.
  • Deferred / Postponed — genuine bug, but fixed in a later release (low severity, low priority, or high fix risk near a release).
  • Cannot reproduce — usually missing environment/data/version detail in the report. Add logs, video, network HAR, exact build number and re-open.

Q25Severity vs Priority — with examples of all four combinations.▼

Severity = technical impact of the defect on the system's functionality. Set by the tester. Priority = urgency of fixing it from a business perspective. Set by the PO / product manager / triage (though the tester proposes it).

CombinationExample
High severity, High priorityPayment gateway fails for all users — the app crashes on checkout. Blocks revenue entirely.
High severity, Low priorityThe application crashes when a user sets the system date to the year 2099, or on a legacy browser used by 0.01% of users. Technically fatal, commercially irrelevant.
Low severity, High priorityThe company name is misspelt on the home page banner, or the logo is a competitor's. Nothing breaks, but it must ship today — brand/legal impact.
Low severity, Low priorityTooltip text on a rarely-used admin screen has a typo or wrong alignment.
Typical severity scale

S1 Critical (system down / data loss, no workaround) · S2 Major (major feature broken, workaround is painful) · S3 Minor (feature partially works, easy workaround) · S4 Trivial (cosmetic).

The trap: many candidates say "severity is set by the tester and priority by the developer." Priority is a business decision — PO/manager/triage board, not the developer.

Q26What does a good defect report contain?▼

The goal is that a developer can reproduce it in under 2 minutes without messaging you.

  • ID and a title that states the problem, not the symptom vaguely: ✅ "Checkout: order total excludes GST when a coupon is applied" ❌ "Total wrong".
  • Environment: build/version number, environment (QA2), browser + version, OS, device, user role, tenant.
  • Preconditions and test data (the actual account/order ID used).
  • Steps to reproduce — numbered, minimal, deterministic. Strip out irrelevant steps.
  • Expected result — with the requirement/AC reference that says so.
  • Actual result.
  • Evidence: screenshot with the issue highlighted, screen recording for timing bugs, browser console errors, network HAR, application/server log snippet with timestamp and correlation ID.
  • Severity, proposed priority, reproducibility (always / 3 out of 5 / once), and whether it is a regression (worked in build N-1).
  • Link to the user story / requirement.
Saying "I always state whether it is a regression and which build last worked" is a strong senior signal — it immediately tells the developer where to bisect.

Q27What is defect triage, defect leakage, defect age and DRE?▼
  • Defect triage — a recurring meeting (QA lead, dev lead, PO, sometimes support) to review new defects and agree severity, priority, owner and target release. Its purpose is to make sure limited dev capacity is spent on the highest-risk defects.
  • Defect leakage — defects that escaped a phase and were found later, especially in production. Leakage % = (defects found in prod / total defects) × 100.
  • Defect removal efficiency (DRE) — DRE = defects found before release / (defects found before release + defects found after release) × 100. Above 90% is generally considered healthy. This is the metric to quote when asked "how do you measure your testing effectiveness?"
  • Defect age — time between defect detection and closure (or between injection and detection). High age points to triage/process bottlenecks.
  • Defect density — defects per KLOC or per module; used to find the risky modules that deserve more testing.
  • Defect clustering — the Pareto observation that ~80% of defects come from ~20% of modules. Use it to target regression effort.

Q28A critical bug escaped to production. Walk me through what you do.▼

This is a behavioural + process question. Answer in a structured order and never blame a person.

  1. Contain first. Confirm and reproduce it on prod, assess blast radius (how many users, is data being corrupted, is money at risk), and push for the fastest mitigation — feature flag off, rollback, or hotfix. Communicate to stakeholders immediately with facts.
  2. Fix and verify. Write the failing test first, then verify the hotfix on staging with production-like data, then verify on prod after deployment.
  3. Root cause analysis (blameless). Use the 5 Whys. Why did it happen (code)? Why wasn't it caught (missing test / missing requirement / environment difference / test data gap)? Why wasn't it caught in review?
  4. Close the gap permanently. Add the regression test to the automated suite, tag it, and make sure it runs in CI. If it was an environment/data difference, fix the environment parity. If a requirement was ambiguous, add it to the acceptance criteria checklist.
  5. Share the learning. Post-mortem doc, and update the risk-based regression selection so that area gets more coverage.
The closing sentence that scores: "Every production escape becomes a permanent automated test. That's how a suite earns its value — it encodes every mistake the team has already made once."

Q34What is risk-based testing? How do you prioritise when there is no time to test everything?▼

Risk-based testing allocates test effort proportional to risk, where Risk = Likelihood of failure × Business impact of failure.

How I do it practically
  1. List the features/modules in scope.
  2. Score likelihood (1–5): code churn in this area, complexity, new vs mature, number of past defects, whether a new/junior dev wrote it, number of integrations.
  3. Score impact (1–5): revenue, legal/compliance, data integrity, number of users affected, reputational damage.
  4. Multiply → risk score → sort. Test the top band deeply (all techniques), the middle band normally, the bottom band with a smoke check only.
  5. Explicitly write down what you are not testing and get the PO to acknowledge it. That converts a hidden gamble into an accepted business decision.

Q36How do you calculate and justify the ROI of test automation?▼

Simple, defensible model:

Manual cost per cycle      = Tm  (hours to run the suite manually)
Automation build cost      = Ta  (one-time hours to script it)
Automation maintenance     = Tmt (hours per cycle to keep it green)
Automated execution cost   = Te  (near zero, runs on CI)

Break-even cycles  N  =  Ta / (Tm - Tmt - Te)
ROI after n cycles    =  (n × Tm - (Ta + n × (Tmt + Te))) / (Ta + n × (Tmt + Te))

Worked example: the regression suite takes 40 hours manually. Scripting it costs 200 hours, maintenance is 4 hours per cycle. Break-even = 200 / (40 − 4) ≈ 5.6 cycles. With fortnightly releases, it pays for itself in about 3 months.

Benefits you cannot put in that formula — mention them
  • Feedback in 20 minutes instead of 3 days → cheaper defect fixes.
  • Enables CI/CD and more frequent releases (a business capability, not a cost saving).
  • Frees manual testers for exploratory testing, which finds different (often more severe) defects.
  • Consistency — no human step-skipping at 6pm on a Friday.
Do not claim automation reduces headcount. Experienced interviewers see that as naive. Claim it changes what the team spends its time on.

Q37How do you manage test data?▼

Test data is the #1 cause of flaky and unmaintainable suites, so this question separates real practitioners from theory.

  • Self-sufficient tests — each test creates the data it needs (preferably through an API in setup, which is 10–50× faster and more reliable than doing it through the UI) and cleans it up afterwards. This is my default.
  • Unique data generation — never hardcode test@test.com. Use user_" + System.currentTimeMillis() or a Faker library so parallel runs don't collide.
  • Externalised static data — reference data (product codes, tax rates) in JSON/CSV/Excel, read by the data provider, never in the code.
  • Seeded/reset environments — a known DB snapshot restored before a suite run, or a Docker/Testcontainers database per run.
  • Masked production data — realistic volumes and shapes for performance/UAT, with PII anonymised. Mention GDPR/DPDP compliance here; it is a strong senior signal.
  • Never depend on data another test created — that creates execution-order coupling and kills parallelism.

Q43Abstraction vs Encapsulation — they sound the same. What is the actual difference?▼
  • Abstraction solves a problem at design level: what should be exposed. Achieved with interfaces and abstract classes. It hides complexity/implementation.
  • Encapsulation solves it at implementation level: how to protect the exposed thing. Achieved with access modifiers and getters/setters. It hides data.

One-liner: abstraction hides the implementation; encapsulation hides the data. A TV remote is abstraction (you press "volume up", not knowing the circuitry). The sealed plastic casing with screws is encapsulation.

Q46What does static mean? Why should the WebDriver not be static?▼

Q49== vs equals(), and the equals/hashCode contract.▼
  • == compares references for objects (do both variables point to the same memory?) and values for primitives.
  • equals() compares content, if the class overrides it. The default Object.equals() is just ==.
The contract

If a.equals(b) is true, then a.hashCode() == b.hashCode() must be true. The reverse is not required (unequal objects may share a hash — a collision). If you override equals() you must override hashCode(), otherwise your object will "disappear" inside a HashMap/HashSet: it is stored in bucket A, and the lookup goes to bucket B.

Integer x = 127, y = 127;   System.out.println(x == y); // true  (Integer cache -128..127)
Integer p = 128, q = 128;   System.out.println(p == q); // false (outside the cache!)

Q52How does HashMap work internally?▼
  1. A HashMap holds an array of buckets (default capacity 16, load factor 0.75).
  2. On put(k,v) it calls k.hashCode(), applies a supplemental hash (spreads the high bits), and computes the index as hash & (n-1).
  3. If the bucket is empty → store a new Node. If occupied (a collision) → walk the chain comparing with hashCode() then equals(). If an equal key exists, the value is replaced; otherwise the node is appended.
  4. When a bucket's chain exceeds 8 nodes (and capacity ≥ 64), Java 8+ converts that chain into a balanced red-black tree, improving worst-case lookup from O(n) to O(log n). It reverts to a list below 6 nodes.
  5. When size > capacity × loadFactor (12 for the default 16), the map resizes to double capacity and rehashes all entries — an expensive operation, which is why you pre-size a map when you know the volume.
Follow-up: "What if you use a mutable object as a key and then change it?" Its hashCode changes, so it now maps to a different bucket — the entry becomes unreachable (a memory leak that get() can never find). That is exactly why String is immutable and is the preferred key type.

Q61What is ThreadLocal and why is it essential for parallel Selenium execution?▼

ThreadLocal<T> gives every thread its own independently initialised copy of a variable. Internally each Thread object carries a ThreadLocalMap keyed by the ThreadLocal instance — so get() returns the calling thread's value.

In TestNG parallel mode, each test method runs on its own thread. Each thread must drive its own browser, but the page objects and utilities need to reach "the driver" without passing it through every method signature. ThreadLocal solves exactly that.

public final class DriverFactory {
    private static final ThreadLocal<WebDriver> TL = new ThreadLocal<>();

    public static void init(String browser) {
        WebDriver driver = switch (browser.toLowerCase()) {
            case "firefox" -> new FirefoxDriver();
            case "edge"    -> new EdgeDriver();
            default        -> new ChromeDriver();
        };
        driver.manage().window().maximize();
        TL.set(driver);
    }
    public static WebDriver get() {
        WebDriver d = TL.get();
        if (d == null) throw new IllegalStateException("Driver not initialised for thread "
                + Thread.currentThread().getName());
        return d;
    }
    public static void quit() {
        WebDriver d = TL.get();
        if (d != null) { d.quit(); TL.remove(); }   // remove() prevents a memory leak
    }
}
Always call TL.remove() in teardown. Thread pools reuse threads; if you don't remove, the stale driver reference stays attached to the pooled thread and leaks memory (and the next test may grab a dead driver).

Q62Basic multithreading: thread lifecycle, synchronized, and why Thread.sleep() is bad in tests.▼

Lifecycle: New → Runnable → Running → (Blocked / Waiting / Timed-waiting) → Terminated.

  • Creating a thread: extend Thread, or implement Runnable/Callable (preferred — leaves your inheritance slot free) and submit to an ExecutorService.
  • synchronized — a lock ensuring only one thread executes a block/method on that monitor at a time. Prevents race conditions on shared mutable state (e.g. a shared report or a counter).
  • wait()/notify() vs sleep(): wait() releases the lock, sleep() does not.
Why Thread.sleep() is an anti-pattern in tests: it is a fixed unconditional pause. On a fast run it wastes seconds (a 200-test suite with 3s sleeps wastes 10 minutes per run); on a slow run 3s isn't enough and the test fails anyway. It converts a deterministic wait into a gamble. Use explicit/fluent waits (Selenium) or auto-waiting assertions (Playwright). The only defensible use is a documented workaround for an animation with no observable end state.

Q67Explain the Selenium WebDriver architecture — what happens when you call driver.findElement(...).click()?▼
  1. Your test calls a method on the WebDriver interface (implemented by ChromeDriver → RemoteWebDriver).
  2. The Selenium client library serialises that command into an HTTP request with a JSON body following the W3C WebDriver protocol, e.g. POST /session/{id}/element with {"using":"css selector","value":"#login"}.
  3. The request goes over HTTP to the browser driver (chromedriver / geckodriver / msedgedriver), which is a small HTTP server running locally on a port.
  4. The driver translates it into the browser's own native automation interface (DevTools Protocol for Chrome, Marionette for Firefox) and executes it.
  5. The browser performs the action on the real DOM and returns a result. The driver wraps it in an HTTP response; the client deserialises it into a Java object (a WebElement reference, a String, or an exception).

Key consequence to state: every single Selenium command is a network round trip. That is why a loop calling getText() on 500 rows is slow, and why chaining fewer, smarter commands (or one executeScript) is faster.

Also mention: since Selenium 4.6, Selenium Manager is built in — it auto-downloads the matching driver binary, so WebDriverManager and manual System.setProperty("webdriver.chrome.driver", ...) are no longer required.

Q77Explain StaleElementReferenceException in depth. How do you fix it properly?▼

When you call findElement, Selenium returns a reference (an internal element id) to a node in the browser's DOM at that instant. If the page then re-renders — an AJAX update, a React/Angular re-render, a page refresh, a sort/filter — the old node is discarded. Your reference now points to something that no longer exists in the DOM, so the next use throws StaleElementReferenceException.

Two flavours
  • The element was deleted from the DOM.
  • The element is no longer attached to the current document (navigation happened).
Fixes, best to worst
  1. Don't cache element references. Store By locators and find the element at the moment of use. This is why By-based page objects are more robust than eagerly-cached WebElement fields.
  2. Wait for the update to finish first — wait for the spinner to disappear or for a specific expected condition before interacting.
  3. Re-find inside a loop when iterating a list that changes: 
    int size = driver.findElements(By.cssSelector(".row")).size();
for (int i = 0; i < size; i++) {
    // re-find EVERY iteration — the list is rebuilt after each click
    WebElement row = driver.findElements(By.cssSelector(".row")).get(i);
    row.findElement(By.cssSelector(".open")).click();
    driver.navigate().back();
}
  4. Retry wrapper for genuinely racy UIs:

Q79Explain implicit, explicit and fluent waits with code.▼
1. Implicit wait — global, DOM presence only
driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(10));

Applies to every findElement/findElements for the life of the driver. Polls until the element is present in the DOM, then returns. It cannot express visibility, clickability or text conditions.

2. Explicit wait — per element, per condition (the default choice)
WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(20));
WebElement btn = wait.until(ExpectedConditions.elementToBeClickable(By.id("pay")));
btn.click();
wait.until(ExpectedConditions.textToBe(By.id("status"), "Payment successful"));

Polls every 500ms by default and throws TimeoutException if the condition never becomes true.

3. Fluent wait — full control
Wait<WebDriver> fluent = new FluentWait<>(driver)
        .withTimeout(Duration.ofMinutes(2))          // long-running report
        .pollingEvery(Duration.ofSeconds(3))         // don't hammer the server
        .ignoring(NoSuchElementException.class)
        .ignoring(StaleElementReferenceException.class)
        .withMessage("Report never reached READY state");

WebElement report = fluent.until(d -> {
    WebElement s = d.findElement(By.id("report-status"));
    return "READY".equals(s.getText()) ? s : null;   // null/false = keep polling
});
WebDriverWait is actually a subclass of FluentWait with a fixed 500ms polling interval and NoSuchElementException pre-ignored. Saying that shows you've read the source, not just a blog.

Q80Why should you never mix implicit and explicit waits?▼

Because the two polling mechanisms interfere and produce unpredictable, non-additive timeouts. The explicit wait calls findElement internally; that call is itself subject to the implicit wait, so each polling attempt can block for the full implicit duration. The official Selenium documentation explicitly warns that this can cause waits to last far longer than either value — and in some driver versions, unexpected timing behaviour.

Example of the confusion: implicit = 10s, explicit = 15s. You might expect a failure at 15s. In practice the first internal lookup blocks for 10s, so you get roughly one or two polls in 15s and a confusing result — or a total closer to 20–30s.

My recommendation (say this): "Set the implicit wait to zero and use explicit waits exclusively, wrapped in reusable helper methods in BasePage. That gives one predictable wait strategy, self-documenting conditions, and much better failure messages."
// BasePage — one place, used everywhere
protected WebElement visible(By locator) {
    return wait.until(ExpectedConditions.visibilityOfElementLocated(locator));
}
protected WebElement clickable(By locator) {
    return wait.until(ExpectedConditions.elementToBeClickable(locator));
}
protected void click(By locator) { clickable(locator).click(); }
protected void type(By locator, String text) {
    WebElement e = visible(locator);
    e.clear();
    e.sendKeys(text);
}

Q86How do you handle frames and iframes?▼

An iframe is a separate HTML document embedded in the page. WebDriver can only see elements in the frame it is currently focused on — this is the #1 cause of "the locator is correct in DevTools but Selenium says NoSuchElement".

// switch by index (fragile), name/id (better), or WebElement (best)
driver.switchTo().frame(0);
driver.switchTo().frame("payment-frame");
driver.switchTo().frame(driver.findElement(By.cssSelector("iframe[title='Card details']")));

// safest — waits for the frame to exist AND switches in one step
new WebDriverWait(driver, Duration.ofSeconds(15)).until(
    ExpectedConditions.frameToBeAvailableAndSwitchToIt(By.id("payment-frame")));

// do the work inside the frame
driver.findElement(By.id("cardNumber")).sendKeys("4111111111111111");

// come back out — MANDATORY
driver.switchTo().defaultContent();     // back to the top-level document
driver.switchTo().parentFrame();        // up exactly one level (nested frames)

// how many frames on the page?
int count = driver.findElements(By.tagName("iframe")).size();

    wait.until(ExpectedConditions.frameToBeAvailableAndSwitchToIt(frame));
    try   { return action.get(); }
    finally { driver.switchTo().defaultContent(); }
}

Q88Explain the Actions class — mouse interactions.▼

Actions builds a chain of low-level input events (the W3C Actions API) and dispatches them with .perform(). Used for anything a simple .click() cannot do.

Actions actions = new Actions(driver);

actions.moveToElement(menu).perform();                       // hover
actions.contextClick(row).perform();                         // right click
actions.doubleClick(cell).perform();
actions.clickAndHold(source).moveToElement(target).release().perform();
actions.dragAndDrop(source, target).perform();               // convenience method
actions.dragAndDropBy(slider, 120, 0).perform();             // offset drag (sliders)
actions.moveToElement(el, 10, 10).click().perform();         // click at an offset

// Multi-step chain: hover a menu, then click a submenu item
actions.moveToElement(driver.findElement(By.id("products")))
       .pause(Duration.ofMillis(300))            // let the CSS animation settle
       .moveToElement(driver.findElement(By.linkText("Laptops")))
       .click()
       .build().perform();
Very common real-world issue: HTML5 drag-and-drop (using the native dragstart/drop events) frequently does not work with Actions.dragAndDrop, because the browser's native DnD is not driven by synthetic mouse events. The standard workaround is a JavaScript-based DnD simulation, or the newer clickAndHold → moveByOffset (small steps) → release sequence with pauses. Mentioning this shows real project experience.

build() composes the chain into a single action; perform() executes it. Calling perform() directly implies build().

Q108How would you find all broken links on a page?▼

A classic practical exercise. Selenium finds the links; a plain HTTP client checks the status codes (do not navigate to each link with the browser — it would take forever).

List<WebElement> links = driver.findElements(By.tagName("a"));
List<String> broken = new ArrayList<>();

Set<String> urls = links.stream()
        .map(l -> l.getAttribute("href"))
        .filter(Objects::nonNull)
        .filter(h -> h.startsWith("http"))          // skip mailto:, tel:, javascript:, #
        .collect(Collectors.toCollection(LinkedHashSet::new));   // dedupe

    conn.setRequestMethod("HEAD");                  // HEAD is enough — no body downloaded
    conn.setConnectTimeout(5000);
    conn.setReadTimeout(5000);
    conn.connect();

    if (code >= 400) broken.add(url + " -> " + code + " " + conn.getResponseMessage());
    conn.disconnect();

Q109How do you handle CAPTCHA and OTP in automation?▼

The correct answer is you don't automate them — you remove the blocker with the team's help. Trying to "solve" a CAPTCHA defeats its purpose and is unreliable.

CAPTCHA
  • Ask dev/DevOps to disable CAPTCHA in non-production environments, or whitelist the test environment/IP. This is the standard industry practice.
  • Use a test key — reCAPTCHA provides official test site/secret keys that always pass in test environments.
  • Bypass via an API-based login for all other tests, keeping one manual test for the CAPTCHA itself.
  • Third-party solving services exist but are slow, cost money, and are a poor engineering answer in an interview.
OTP / 2FA
  • Use a fixed test OTP (e.g. 000000) enabled for test accounts in lower environments — the most common real solution.
  • Fetch the OTP from a backend API / test endpoint, or query the database directly with JDBC.
  • Read it from a test mail service (Mailinator, MailHog, Mailosaur API) or an SMS sandbox (Twilio test credentials).
  • For TOTP-based 2FA, generate the code in the test from the shared secret using a library (e.g. totp-java) — this is fully legitimate and impressive to mention.
Frame it as a conversation, not a hack: "I raise testability as a requirement during refinement. A feature that cannot be tested in a lower environment isn't 'done' — and the team agreed to a test-mode flag for exactly that reason."

Q113Your Selenium suite takes 4 hours. How do you make it fast?▼

Answer as an ordered plan — measure first, then optimise.

  1. Measure. Get per-test durations from the TestNG/Allure report and find the top 20 slowest tests. Optimise those, not everything.
  2. Parallelise. TestNG parallel="methods" with a thread count matched to CPU/grid capacity. This alone often gives 4–8×. Prerequisite: ThreadLocal driver and fully independent tests.
  3. Kill all Thread.sleep() and replace with explicit waits. In most legacy suites this is 30–50% of the runtime.
  4. Skip the UI for setup. Log in via API + cookie injection; create the test data via API instead of clicking through wizards. Typically saves 5–15s per test.
  5. Push tests down the pyramid. Field validations and error messages become API/component tests; only journeys stay in the UI layer.
  6. Run headless and use PageLoadStrategy.EAGER; block analytics/ads/third-party scripts via CDP.
  7. Split the suite — a <10 minute smoke set on every commit, the full regression nightly. Tag with TestNG groups.
  8. Scale horizontally with a Docker Grid or a cloud provider; shard tests across CI agents.
  9. Remove duplication — audit for tests that assert the same thing through different paths.
  10. Fix the flaky ones instead of retrying them; retries hide problems and double the runtime of failing tests.
Quantify it if you can: "We took our regression from 3h 40m to 34 minutes: parallelism 8×, API-based login, and moving 120 validation checks to the API layer." Numbers are what interviewers remember.

Plus @BeforeGroups / @AfterGroups (run around methods belonging to a named group), @DataProvider, @Parameters, @Factory, @Listeners.

public class BaseTest {
    @BeforeSuite(alwaysRun = true)
    public void startReport() { ExtentManager.init(); }

    @BeforeMethod(alwaysRun = true)
    @Parameters({"browser"})
    public void setUp(@Optional("chrome") String browser, Method m) {
        DriverFactory.init(browser);
        DriverFactory.get().get(Config.get("base.url"));
        logger.info("Starting test: {}", m.getName());
    }

    @AfterMethod(alwaysRun = true)
    public void tearDown(ITestResult result) {
        if (result.getStatus() == ITestResult.FAILURE) Screenshot.capture(result);
        DriverFactory.quit();
    }

    @AfterSuite(alwaysRun = true)
    public void flushReport() { ExtentManager.get().flush(); }
}
alwaysRun = true matters: without it, a @Before/@After method is skipped if a method it depends on fails — which means your driver is never quit and the process leaks. Always set it on teardown methods.

Q119Explain the @Test attributes: priority, dependsOnMethods, invocationCount, timeOut, enabled, expectedExceptions.▼
@Test(priority = 1)                       // lower number runs first; default 0
@Test(priority = 2, description = "Verify checkout with a saved card")
@Test(enabled = false)                    // skip this test entirely
@Test(groups = {"smoke", "checkout"})
@Test(dependsOnMethods = {"login"})       // runs only if login PASSED; else SKIPPED
@Test(dependsOnGroups = {"setup"})
@Test(alwaysRun = true, dependsOnMethods = {"login"})   // runs even if login failed
@Test(invocationCount = 5)                // run 5 times
@Test(invocationCount = 10, threadPoolSize = 3)         // 10 times across 3 threads
@Test(timeOut = 5000)                     // fail if it exceeds 5000 ms
@Test(expectedExceptions = NoSuchElementException.class)
@Test(retryAnalyzer = RetryAnalyzer.class)
@Test(dataProvider = "loginData", dataProviderClass = TestData.class)
Ordering rules — a favourite trap
  • Without priority, TestNG runs methods in alphabetical order, not the order written in the file.
  • priority is honoured only within the same class/test tag; dependencies take precedence over priority.
  • Two methods with the same priority run alphabetically.
  • If a method with dependsOnMethods has its dependency fail, the dependent is marked SKIPPED (not failed).
Opinion worth stating: "I avoid dependsOnMethods for chaining business steps. It creates order-dependent tests that cannot run in parallel and produce cascading skips that hide the real failure count. I use it only for genuine environment prerequisites."

Q123How does parallel execution work in TestNG? What are the prerequisites?▼
<suite name="S" parallel="methods"   thread-count="5">  <!-- every @Test in its own thread -->
<suite name="S" parallel="classes"   thread-count="5">  <!-- each class in one thread -->
<suite name="S" parallel="tests"     thread-count="3">  <!-- each <test> tag -->
<suite name="S" parallel="instances" thread-count="4">  <!-- each @Factory instance -->
Prerequisites — this is what they're really asking
  1. ThreadLocal WebDriver — no static/shared driver (Q61).
  2. Independent tests — no dependsOnMethods, no shared mutable state, no assumption about execution order.
  3. Isolated test data — unique users/records per test, or per-thread data pools. Two threads updating the same record is the classic parallel bug.
  4. Thread-safe reporting — ExtentTest also needs a ThreadLocal, otherwise logs from different tests interleave.
  5. Capacity — thread count matched to CPU/RAM and grid nodes. Too many threads makes everything slow and flaky; I usually start at (cores) and tune from measurements.
// Thread-safe Extent reporting
public class ExtentManager {
    private static final ThreadLocal<ExtentTest> TEST = new ThreadLocal<>();
    public static void set(ExtentTest t) { TEST.set(t); }
    public static ExtentTest getTest()   { return TEST.get(); }
    public static void unload()          { TEST.remove(); }
}

Q124What are TestNG listeners? Which ones have you implemented?▼
InterfacePurpose
ITestListenerHooks on test start/success/failure/skip — screenshots, report logging
ISuiteListeneronStart/onFinish of the whole suite — init & flush reports
IInvokedMethodListenerBefore/after every method including configuration methods

public class TestListener implements ITestListener {
    @Override public void onTestStart(ITestResult r) {
        ExtentManager.set(ExtentManager.get().createTest(
            r.getMethod().getMethodName(), r.getMethod().getDescription()));
    }
    @Override public void onTestSuccess(ITestResult r) {
        ExtentManager.getTest().pass("Passed in " +
            (r.getEndMillis() - r.getStartMillis()) + " ms");
    }
    @Override public void onTestFailure(ITestResult r) {
        String b64 = ((TakesScreenshot) DriverFactory.get()).getScreenshotAs(OutputType.BASE64);
        ExtentManager.getTest().fail(r.getThrowable(),
            MediaEntityBuilder.createScreenCaptureFromBase64String(b64).build());
        ExtentManager.getTest().info("URL at failure: " + DriverFactory.get().getCurrentUrl());
    }
    @Override public void onTestSkipped(ITestResult r) {
        ExtentManager.getTest().skip(r.getThrowable());
    }
}

Register via @Listeners(TestListener.class) on the base class, in testng.xml, or globally through the ServiceLoader (META-INF/services) — the last option means nobody can forget it.

Q125Implement a retry mechanism for failed tests.▼
public class RetryAnalyzer implements IRetryAnalyzer {
    private int count = 0;
    private static final int MAX = 2;                 // 1 original + 2 retries

    @Override public boolean retry(ITestResult result) {
        if (count < MAX) {
            count++;
            result.setAttribute("retried", count);    // so the report can show it
            LoggerFactory.getLogger(getClass()).warn(
                "Retrying {} — attempt {}/{}", result.getName(), count, MAX);
            return true;
        }
        return false;
    }
}

// Apply it to EVERY test automatically — no annotation needed on each method
public class RetryTransformer implements IAnnotationTransformer {
    @Override public void transform(ITestAnnotation ann, Class<?> c, Constructor<?> m,
                                    Method testMethod) {
        ann.setRetryAnalyzer(RetryAnalyzer.class);
    }
}
The judgement question that follows: "Isn't retrying just hiding flakiness?" Yes — if used blindly. My policy: retries exist to absorb genuine infrastructure noise (a grid node hiccup, a network blip), not product bugs. So I (a) cap retries at 2, (b) report retried tests as a distinct category rather than a clean pass, and (c) track a flaky-test list that must be fixed, not tolerated. Saying this converts a naive answer into a senior one.

Q126Hard assertion vs soft assertion. When do you use each?▼
// HARD — stops the test at the first failure (default)
Assert.assertEquals(actual, expected, "Order total mismatch");
Assert.assertTrue(page.isLoaded(), "Dashboard did not load");
Assert.assertNotNull(orderId);
Assert.assertThrows(NoSuchElementException.class, () -> driver.findElement(gone));

// SOFT — collects failures and reports them all at the end
SoftAssert soft = new SoftAssert();
soft.assertEquals(invoice.getCustomerName(), "Ravi Kumar",   "Name");
soft.assertEquals(invoice.getGst(),          "18%",          "GST");
soft.assertEquals(invoice.getTotal(),        "₹1,499.00",    "Total");
soft.assertEquals(invoice.getInvoiceDate(),  today,          "Date");
soft.assertAll();      // MUST be called or failures are silently swallowed

Rule I use: hard assert for anything that makes the rest of the test meaningless (the page didn't load, the order wasn't created). Soft assert for independent field-level verifications on the same screen, where I want one run to report all mismatches instead of five debug cycles.

The classic bug: forgetting soft.assertAll() — the test passes green while every assertion failed. Some teams put assertAll() in an @AfterMethod with a per-thread SoftAssert to make it impossible to forget.
Always pass the message parameter. "expected [true] but found [false]" costs 20 minutes of debugging; "Dashboard did not load after login for user qa_01" costs zero.

Q128What is the Page Object Model and why use it?▼

POM is a design pattern where every page (or significant component) of the application gets a class that holds its locators and exposes its business actions as methods. Tests call those methods and never see a locator.

Benefits
  • Single point of maintenance — the login button's id changes, you edit one line in one file, not 40 tests.
  • Readable tests — loginPage.login(user, pass) reads like the requirement.
  • Reusability — the same page methods serve dozens of scenarios.
  • Separation of concerns — test logic (what) vs page interaction (how).
public class LoginPage extends BasePage {
    // locators — private, By-based (not cached WebElements)
    private final By email  = By.id("email");
    private final By pwd    = By.id("password");
    private final By signIn = By.cssSelector("[data-testid='signin']");
    private final By error  = By.cssSelector(".alert-danger");

    public LoginPage(WebDriver driver) { super(driver); }

    public DashboardPage loginAs(String user, String pass) {
        type(email, user);
        type(pwd, pass);
        click(signIn);
        return new DashboardPage(driver);       // return the NEXT page = fluent navigation
    }
    public LoginPage loginExpectingFailure(String user, String pass) {
        type(email, user); type(pwd, pass); click(signIn);
        return this;                            // stay on the same page
    }
    public String getError() { return visible(error).getText(); }
}

// The test — clean, business-readable, zero Selenium API
@Test
public void invalidPasswordShowsError() {
    String msg = new LoginPage(driver)
            .loginExpectingFailure("valid@test.com", "Wrong@123")
            .getError();
    Assert.assertEquals(msg, "Invalid credentials");
}

Q129What is PageFactory? Explain @FindBy, @FindAll, @FindBys and @CacheLookup.▼
public class HomePage {
    @FindBy(id = "search")                       private WebElement searchBox;
    @FindBy(css = "[data-testid='cart']")        private WebElement cart;
    @FindBy(xpath = "//div[@class='product']")   private List<WebElement> products;

    // OR — matches EITHER locator (union)
    @FindAll({ @FindBy(id = "submit"), @FindBy(name = "submit") })
    private WebElement submit;

    // AND — chained/nested (intersection): find .cart, then inside it find button
    @FindBys({ @FindBy(className = "cart"), @FindBy(tagName = "button") })
    private WebElement cartButton;

    @FindBy(id = "logo") @CacheLookup private WebElement logo;   // cached — see warning

    public HomePage(WebDriver driver) {
        PageFactory.initElements(driver, this);
        // or: PageFactory.initElements(new AjaxElementLocatorFactory(driver, 15), this);
    }
}

How it works: initElements replaces each annotated field with a dynamic proxy. The element is not located at construction time — it is located lazily each time you call a method on it, which is why PageFactory naturally resists stale elements.

@CacheLookup stores the located element after the first use. It is faster, but if the element is re-rendered you get StaleElementReferenceException. Only use it on genuinely static elements (a logo, a static header) — and honestly, in modern SPAs, almost never.
Should you use PageFactory at all? A defensible senior answer: "PageFactory is fine, but I often prefer plain By locators. They're explicit, easier to parameterise (String.format for dynamic rows), can be passed to explicit-wait conditions directly, and produce clearer failure messages. PageFactory is also no longer actively developed. Both are acceptable — I stay consistent within a project."

Q130What are Page Object best practices — and what should NOT go in a page object?▼
Do
  • Model business actions, not UI mechanics: searchAndOpenFirstResult("laptop"), not clickSearchButton().
  • Return the next page object so navigation is expressed in the type system.
  • Keep locators private; expose only methods.
  • Extract reusable widgets into component objects (HeaderComponent, DataTableComponent, DatePickerComponent) and compose them — a page object per URL is not enough for a modern SPA.
  • Put common helpers (click, type, visible, selectDropdown) in BasePage.
  • Expose state getters (getErrorMessage(), isLoaded()) so the test can assert.
Do NOT
  • No assertions inside page objects. A page object describes the page; the test decides what is correct. (One tolerated exception: an isLoaded() self-check.) Assertions inside pages make them unreusable for negative tests.
  • No test data hardcoded in pages.
  • No Thread.sleep(), no raw driver management, no report/log formatting.
  • No giant "god page" with 80 methods — split by component.
  • Don't expose WebElement from public methods; that leaks Selenium into the test layer.
If they ask "how do you keep page objects from becoming unmaintainable?", answer: component objects + a strict rule that tests never import org.openqa.selenium.*. That import rule can even be enforced with ArchUnit or a Checkstyle rule — a great detail to mention.

  • Tests may not import Selenium classes — enforced in code review.

public final class Config {
    private static final Properties PROPS = load();

    private static Properties load() {
        String env = System.getProperty("env",
                     System.getenv().getOrDefault("TEST_ENV", "qa"));
        Properties p = new Properties();
        try (InputStream in = Config.class.getResourceAsStream("/config/" + env + ".properties")) {
            if (in == null) throw new FrameworkException("No config for env: " + env);
            p.load(in);
        } catch (IOException e) { throw new FrameworkException("Config load failed", e); }
        return p;
    }

    /** Precedence: -D system property  →  environment variable  →  properties file */
    public static String get(String key) {
        String v = System.getProperty(key);
        if (v == null) v = System.getenv(key.toUpperCase().replace('.', '_'));
        if (v == null) v = PROPS.getProperty(key);
        if (v == null) throw new FrameworkException("Missing config key: " + key);
        return v;
    }
    public static int getInt(String key)      { return Integer.parseInt(get(key)); }
    public static boolean getBool(String key) { return Boolean.parseBoolean(get(key)); }
}

Q145What are BDD best practices — and when should you NOT use BDD?▼
Best practices
  • Write scenarios in business language, describing behaviour and outcome — not UI mechanics. ✅ "When I pay with an expired card" ❌ "When I click the button with id 'pay'".
  • One scenario = one behaviour. If it has 15 steps and three Thens, split it.
  • Declarative over imperative: "When I log in as an admin" rather than five steps of typing and clicking.
  • Reuse step definitions; keep them thin — a step should call one page-object or API method, with all logic in the layers below.
  • Keep the feature files in the same repo, reviewed by the PO.
When NOT to use BDD — an honest, senior answer

"BDD's value is the conversation with the business, not the Gherkin syntax. If the product owner never reads the feature files, you're paying a real cost — an extra glue layer, regex-matched steps, harder refactoring and debugging — for zero collaboration benefit. In that case plain TestNG with well-named methods is better. I've used Cucumber where business analysts genuinely reviewed the scenarios, and plain TestNG where they didn't."

This is a differentiator answer. Most candidates recite Cucumber syntax; very few can say when the tool is the wrong choice. That is what a lead wants to hear.

Q149A test passes locally but fails in Jenkins. How do you debug it?▼

Work through the differences systematically — say them in this order:

  1. Get evidence first. Screenshot at failure, page source, browser console log, the video (Selenium/video container), and the exact stack trace. Never guess.
  2. Timing — CI agents are slower and more loaded. Fixed waits that were "just enough" locally now fail. Fix: condition-based waits, and CI-specific timeout values.
  3. Headless vs headed — different viewport (headless has no default window size!), no hover states, different font rendering. Fix: set an explicit window size; reproduce locally with -Dheadless=true.
  4. Screen resolution / responsive layout — elements may be behind a hamburger menu at the CI viewport.
  5. Environment & data — different DB state, feature flags off, the record the test expects doesn't exist, another parallel job mutated shared data.
  6. Parallelism — it passes alone but fails with 5 threads → shared state, static driver, or data collision.
  7. Version drift — different browser/driver/JDK version on the agent.
  8. Network — CI may be behind a proxy or firewall; third-party scripts time out.
  9. Reproduce in the same conditions — run the Docker image locally, or use the Grid's VNC/debug image to watch it live.
Strong closing line: "I treat 'passes locally, fails in CI' as a defect in the test, not an excuse. CI is the source of truth, because it's the environment the release decision is based on."

Q151What is Playwright and how does its architecture differ from Selenium's?▼

Playwright is an open-source end-to-end testing framework from Microsoft that automates Chromium, Firefox and WebKit with a single API. Unlike Selenium it is a complete test framework — runner, assertions, fixtures, parallelism, reporting and tracing all come in the box.

Architectural differences
  • Transport — Selenium sends one HTTP request per command via the W3C protocol. Playwright keeps a single WebSocket connection to a Node driver process, which speaks each browser's native debugging protocol. Fewer round trips, and the browser can push events back.
  • Bi-directional — because events flow both ways, Playwright natively knows when the DOM changed, when a request fired, when navigation completed. That is the foundation of auto-waiting.
  • BrowserContext — a lightweight isolated browser session (own cookies, storage, cache) that starts in milliseconds. Selenium's equivalent isolation requires launching a whole new browser.
  • Bundled browsers — Playwright downloads and pins patched browser builds, so version mismatch problems largely disappear.

Q155What is auto-waiting? What actionability checks does Playwright perform?▼

Before performing an action, Playwright automatically waits for the element to pass a series of actionability checks, retrying until they pass or the timeout expires. You almost never write a wait.

CheckMeaning
AttachedElement is in the DOM
VisibleNon-empty bounding box and not visibility:hidden
StableBounding box hasn't changed for two consecutive animation frames (i.e. animation finished)
Receives eventsIt is the actual hit target at the click point — not covered by an overlay
EnabledNot disabled
EditableFor fill(): enabled and not readonly

Which checks apply depends on the action: click() does all of visible/stable/receives-events/enabled; fill() adds editable; textContent() requires none.

Contrast to draw in the interview: "In Selenium, elementToBeClickable only checks visible + enabled — it will happily return an element that is covered by a modal overlay, and then click() throws ElementClickInterceptedException. Playwright's 'receives events' and 'stable' checks eliminate that entire class of flakiness."
Auto-waiting is not magic: it does not wait for your application's business state (e.g. "the order has been persisted"). For that you still assert on an observable condition — a visible confirmation, a network response, or an API check.

Q161What are fixtures in Playwright? Write a custom fixture.▼

Fixtures are Playwright's dependency-injection mechanism. Instead of beforeEach setting up shared variables, you declare what a test needs in its arguments and Playwright constructs it, on demand, and tears it down afterwards.

Built-in fixtures: page, context, browser, browserName, request (API), baseURL.

// fixtures.ts — page objects + an authenticated API client as fixtures
import { test as base } from '@playwright/test';
import { LoginPage } from './pages/login.page';
import { CheckoutPage } from './pages/checkout.page';

type Fixtures = {
  loginPage: LoginPage;
  checkoutPage: CheckoutPage;
  testOrder: { id: string };
};

export const test = base.extend<Fixtures>({
  loginPage:    async ({ page }, use) => { await use(new LoginPage(page)); },
  checkoutPage: async ({ page }, use) => { await use(new CheckoutPage(page)); },

  // A fixture with setup AND teardown — creates data, then cleans it up
  testOrder: async ({ request }, use) => {
    const res = await request.post('/api/orders', { data: { sku: 'TSH-001', qty: 1 } });
    const order = await res.json();
    await use(order);                                  // <-- the test runs here
    await request.delete(`/api/orders/${order.id}`);   // always runs, even on failure
  },
});
export { expect } from '@playwright/test';
// the test — declarative and clean
import { test, expect } from './fixtures';

test('can cancel an existing order', async ({ page, testOrder, checkoutPage }) => {
  await page.goto(`/orders/${testOrder.id}`);
  await checkoutPage.cancelOrder();
  await expect(page.getByText('Order cancelled')).toBeVisible();
});

Fixture scopes: { scope: 'test' } (default) or { scope: 'worker' } for expensive setup shared across tests in a worker. Use auto: true to run a fixture even if no test requests it (e.g. per-test logging).

The interview point: fixtures are lazy. A fixture is only created if a test actually asks for it, so unlike beforeEach you never pay for setup a test doesn't need.

Q172Do you need explicit waits in Playwright? What waiting APIs exist?▼

Q179Explain async/await and Promises. What mistakes do people make in Playwright tests?▼

A Promise represents a value that will be available later (pending → fulfilled/rejected). async marks a function that returns a Promise; await pauses inside it until the Promise settles. Almost every Playwright API returns a Promise.

// ✗ MISTAKE 1 — missing await on an assertion: the test always passes
expect(page.getByText('Order confirmed')).toBeVisible();
// ✓
await expect(page.getByText('Order confirmed')).toBeVisible();

// ✗ MISTAKE 2 — missing await on an action: race condition / unhandled rejection
page.getByRole('button', { name: 'Save' }).click();
// ✓
await page.getByRole('button', { name: 'Save' }).click();

// ✗ MISTAKE 3 — await inside forEach: forEach ignores the returned promise
items.forEach(async item => { await item.click(); });   // does NOT wait
// ✓
for (const item of items) { await item.click(); }
// ✓ or, for independent operations, run them concurrently:
await Promise.all(items.map(i => i.click()));

// ✗ MISTAKE 4 — awaiting the trigger before setting up the waiter
await page.getByRole('button', { name: 'Export' }).click();
const download = await page.waitForEvent('download');   // may hang — event already fired
// ✓
const [download] = await Promise.all([
  page.waitForEvent('download'),
  page.getByRole('button', { name: 'Export' }).click(),
]);

// Error handling
try { await page.goto('/slow'); }
catch (e) { console.error('navigation failed', e); throw e; }

// Promise.all (fail fast) vs Promise.allSettled (collect all results)
const [a, b] = await Promise.all([apiCall1(), apiCall2()]);
const results = await Promise.allSettled([apiCall1(), apiCall2()]);
Enable @typescript-eslint/no-floating-promises and eslint-plugin-playwright in the repo. They catch missing awaits automatically — mentioning this shows you think about preventing whole classes of bugs, not just fixing them.

  2. Pilot. Port 10–15 representative tests (including the trickiest: iframes, file upload, multi-tab, dynamic tables) in a spike. Measure runtime and stability against the Selenium equivalents. Present the comparison.
  3. Run both in parallel. Keep Selenium as the gate while Playwright coverage grows; nothing loses coverage during the transition.
  4. Migrate by value, not by file order. Start with the flakiest and slowest suites — the biggest wins first — plus any new tests, which are written only in Playwright from day one.
  5. Rebuild rather than transliterate. A line-by-line port carries over every explicit wait and every brittle XPath. Re-express tests with getByRole and web-first assertions, or you inherit the old flakiness in new syntax.
  6. Address the team. Java/Selenium people need TypeScript and async/await training; budget for it. (Playwright does have a Java binding, but the TS ecosystem is where the tooling and examples are.)
  7. Retire deliberately. Delete each Selenium test only when its Playwright counterpart has been green for a couple of weeks.
The mature closing line: "Migration is a cost with no new features for the business, so it has to be justified by measurable pain and delivered incrementally without ever leaving the team without a working regression suite."

Q190What are the most common Playwright mistakes and best practices?▼
Mistakes
  • Missing await — the assertion never runs and the test always passes.
  • Using page.waitForTimeout() as a wait strategy.
  • Using CSS/XPath everywhere instead of role/label/testid locators.
  • Using force: true to "make it work" instead of understanding the failure.
  • Using page.$() / ElementHandles instead of Locators.
  • Logging in through the UI in every test instead of storageState.
  • Sharing state between tests (module-level variables, a fixed test record) — breaks parallelism.
  • Committing test.only (set forbidOnly: true in CI).
  • Turning up timeouts to hide a real problem.
  • Not enabling traces, then having no idea why CI failed.
Best practices
  • Test user-visible behaviour, not implementation details.
  • Prefer getByRole → getByLabel → getByTestId; CSS/XPath last.
  • Web-first assertions everywhere; let them do the waiting.
  • Each test independent, self-seeding its data via API, running from a clean context.
  • trace: 'on-first-retry', screenshots and video on failure.
  • Page objects + fixtures + test.step for readable reports.
  • Lint with eslint-plugin-playwright; type everything.
  • Keep the smoke suite under 10 minutes and make it a merge gate.

Q192Explain API authentication types and how you handle tokens in tests.▼
  • Basic auth — Authorization: Basic base64(user:pass). Simple, must be over HTTPS.
  • API key — a static key in a header or query param. Identifies the app, not the user.
  • Bearer token / JWT — Authorization: Bearer eyJhbGci…. A JWT has three dot-separated parts: header.payload.signature. The payload is only Base64-encoded, not encrypted — so you can decode it in a test to assert claims (sub, exp, role), and you should verify the app never puts sensitive data in it.
  • OAuth 2.0 — token issued by an authorisation server. Grant types: authorization code (+PKCE) for user-facing apps, client credentials for machine-to-machine (the one you usually automate).
  • Session cookie — traditional server-side session.
Handling tokens in a test framework

Q195"Tell me about the biggest challenge you faced." How do you structure behavioural answers?▼

Use STAR: Situation (context, 2 sentences) → Task (your specific responsibility) → Action (what you did — most of the answer) → Result (measurable outcome + what you learned).

Worked example

Task: "I took ownership of suite reliability for that quarter, alongside my sprint work."

Action: "I started by measuring instead of guessing — I ran the suite 20 times and classified every failure: 40% were fixed sleeps and presence-only waits, 30% were test-data collisions between parallel threads, 20% were a shared static WebDriver, and 10% were genuine product bugs. Q196"A developer rejects your bug saying it works on their machine." What do you do?▼

Q201What is Appium and how does its architecture work?▼

Appium is an open-source tool for automating native, hybrid and mobile-web apps on Android and iOS, using the same W3C WebDriver protocol as Selenium.

  1. Your test creates an AndroidDriver/IOSDriver with a set of capabilities.
  2. The client sends HTTP/JSON commands to the Appium server (Node.js, default port 4723).
  3. The server routes them to the right platform driver: UiAutomator2 for Android, XCUITest for iOS.
  4. That driver talks to the vendor's own automation framework on the device — via ADB and a bootstrap agent on Android, via WebDriverAgent on iOS.
  5. The action executes on the real device or emulator and the result travels back up the same chain.
Why teams choose it
  • Cross-platform — one API and often one test codebase for Android and iOS.
  • No app modification — you test the same binary you ship; no SDK to embed.
  • Any language that has a WebDriver client (Java, Python, JS, C#, Ruby).
  • Reuses your Selenium knowledge — waits, page objects, TestNG, reporting all carry over.
The sentence that lands: "Appium is WebDriver for mobile. My framework layers — driver factory, page objects, waits, listeners, reporting — were reused as-is; I only added a mobile driver factory and mobile locators."

Q207What test scenarios are unique to mobile apps that don't exist on web?▼

Q218How would you design a load test for a checkout flow?▼
  1. Get the requirement in numbers. "Fast" is not a requirement. Ask for: expected concurrent users, peak hour transactions, growth headroom, and the SLA — e.g. "p95 < 2s at 500 concurrent users, error rate < 0.1%". If nobody knows, derive it from production analytics.
  2. Build a workload model from real traffic, not from imagination: 70% browse, 20% search, 8% add-to-cart, 2% checkout. Model the mix, not just the one flow you care about.
  3. Add realistic think time — humans pause 3–10 seconds between clicks. Zero think time turns a 500-user test into an unintentional stress test.
  4. Prepare data — unique users, unique carts, enough product inventory that you don't all collide on one SKU, and a DB seeded to production-like volume (query plans change dramatically between 1k and 10M rows).
  5. Environment — production-like scale, or a known ratio you can extrapolate from. Document the difference; a test on a half-size environment does not prove full-size behaviour.
  6. Ramp up gradually and include a steady state; don't slam all users in at second zero unless you are deliberately spike testing.
  7. Monitor the server side, not just the client: CPU, memory, GC, DB connections, slow query log, downstream API latency. The client only tells you that it was slow, never why.
  8. Baseline first, then compare every later run to it. A single run without a baseline tells you almost nothing.
  9. Exclude third parties you don't own, or stub them — you can't fix someone else's payment sandbox, and it will dominate your numbers.

Q224How do you test authorisation properly? (The bug class most teams miss.)▼

Authentication asks "who are you?"; authorisation asks "are you allowed to do this?" — and it is where the expensive bugs live, because the UI hides the button but the API often still accepts the call.

The matrix I build

Rows = roles (guest, user, premium user, support agent, admin). Columns = protected operations. Every cell is a test: allowed → 200, not allowed → 403 (not 200, not 500, and not a silent success).

        role + " was able to read another user's order — broken access control");

  • Mass assignment — adding "role":"ADMIN" to a profile-update payload and seeing if it sticks.
  • Hidden UI ≠ protected — the button is hidden for this role, but is the endpoint itself protected?
  • Token misuse — an expired token, a token from another tenant, a token after logout, a modified JWT payload.

Q225Explain WCAG and how you'd run an accessibility testing programme.▼

WCAG (Web Content Accessibility Guidelines) has three conformance levels: A (minimum), AA (the usual legal and contractual target), AAA (rarely required in full). Its four principles are POUR:

  • Perceivable — text alternatives for images, captions for video, sufficient colour contrast (4.5:1 normal text, 3:1 large text), information not conveyed by colour alone.
  • Operable — everything reachable and usable by keyboard, no keyboard traps, visible focus, enough time to complete tasks, no flashing content.
  • Understandable — predictable navigation, clear labels, helpful error messages that say how to fix the problem, consistent components.
  • Robust — valid semantic HTML and correct ARIA so assistive technologies can parse it.
A realistic three-layer programme
  1. Automated in CI — axe-core in every Playwright/Selenium run. Catches roughly 30–40%: missing labels, contrast, missing alt, heading order.
  2. Manual keyboard pass — tab through the whole flow with the mouse unplugged. Fast, needs no tooling, and finds what scanners can't: illogical tab order, invisible focus, unreachable modals.
  3. Screen reader spot checks — NVDA (Windows), VoiceOver (Mac/iOS), TalkBack (Android) on the critical journeys, plus zoom to 200% and a large-font test.
Never claim "we're WCAG compliant because axe passes". Automated tools cannot judge whether alt text is meaningful, whether the reading order makes sense, or whether an error is understandable. Stating that limitation is what makes the answer credible.

Q226What is contract testing and when do you need it?▼

In a microservices system, full end-to-end tests across every service are slow, flaky and hard to own. Contract testing verifies the agreement between a consumer and a provider independently, without running both together.

  1. The consumer (e.g. the web app) writes a test declaring "when I call GET /orders/1, I expect a 200 with fields id, status, total". Running it produces a pact file and runs the consumer against a local mock built from it.
  2. The pact is published to a broker.
  3. The provider (the order service) replays every pact against its real implementation in its own pipeline. If a developer renames total to totalAmount, the provider build goes red before the change is deployed.

When you need it: multiple independently deployed services, teams releasing on different schedules, and a full E2E suite that is too slow or too flaky to gate every deploy. When you don't: a monolith, or a single team owning both sides where a shared integration test is simpler.

The framing that lands: "Contract tests let me delete most of my cross-service end-to-end tests. I keep a handful of true E2E journeys for confidence, and catch integration breakages at the contract level, where the feedback is in seconds instead of an hour." Tool to name: Pact.

Q228How do you handle test data privacy and compliance?▼

Copying a production database into QA is the single most common compliance violation in testing teams — and increasingly illegal under GDPR, India's DPDP Act, HIPAA and PCI-DSS.

  • Anonymisation / masking — irreversibly replace names, emails, phone numbers, card and ID numbers while preserving format and distribution, so the data still behaves realistically.
  • Pseudonymisation — replace identifiers with consistent tokens so relationships across tables still work.
  • Synthetic data — generate it (Faker, Mockaroo) rather than copying. Safest option; the challenge is realistic edge cases and volume.
  • Subsetting — take a referentially-consistent 1–5% slice instead of the whole database.
  • Minimisation — don't copy the columns you don't need to test.
  • Never log or screenshot PII — mask it in test reports too; a failure screenshot of a real customer's account is still a data breach.
  • Access control & retention — restrict who can reach lower environments and delete test data on a schedule.
  • Payment data — never real card numbers. Use the gateway's official test cards.
Mentioning GDPR/DPDP unprompted is a genuine differentiator — it signals you think about risk beyond the feature, which is exactly what a QA lead needs.

Q229What is chaos engineering / resilience testing?▼

Deliberately injecting failure into a system to verify it degrades gracefully instead of collapsing — testing the recovery path, which is the path that is almost never exercised before a real incident.

Experiments
  • Kill a service instance / pod — does traffic reroute? Does the user notice?
  • Add latency or drop packets between services — do timeouts, retries and circuit breakers behave, or do they cascade?
  • Take the database read replica down — does it fail over cleanly?
  • Exhaust CPU/memory/disk on a node.
  • Make a third-party dependency (payment gateway, email provider) fail or hang — does the user get a sensible message and is the order left in a recoverable state?
  • Clock skew and expired certificates — an underrated source of real outages.

The discipline: form a hypothesis ("if the payment gateway times out, orders stay in PENDING and the customer sees a retry option"), define the blast radius, run the smallest possible experiment, measure, and always have an abort switch. Tools: Chaos Monkey, Gremlin, LitmusChaos, Toxiproxy.

Even without chaos tooling, you can say something true and valuable: "I test the failure paths deliberately — I stub the payment API to return 500 and to hang, and assert the UI message, the retry, and the final data state. Most teams only test the happy path of their error handling."

Q230What is observability, and how does it change a tester's job?▼

Monitoring tells you that something is wrong against known thresholds. Observability is the ability to ask new questions about system behaviour without shipping new code — built on three pillars:

  • Logs — discrete events with context and a correlation id.
  • Metrics — numeric time series (error rate, latency percentiles, throughput, saturation).
  • Traces — one request followed across every service, showing where the time went.
What changes for QA
  • Testability becomes a requirement you advocate for — correlation ids, structured logs, meaningful error codes. "How will we debug this in production?" is a refinement question.
  • Better bug reports — attaching a trace id turns a two-day investigation into a ten-minute one.
  • Shift-right testing — synthetic monitoring that reuses your E2E tests against production on a schedule, so you detect breakage before customers report it.
  • Data-driven regression scope — production usage data tells you which flows actually matter, so risk-based selection stops being guesswork.
  • Release verification — after a deploy, watch error rate and latency rather than only running a smoke suite.

public final class Mask {
    private static final Pattern CARD  = Pattern.compile("\\b(?:\\d[ -]*?){13,19}\\b");
    private static final Pattern EMAIL = Pattern.compile("([\\w.+-]{1,3})[\\w.+-]*@([\\w.-]+)");
    private static final Pattern PHONE = Pattern.compile("\\b(\\d{2})\\d{6}(\\d{2})\\b");
    private static final List<String> SECRET_KEYS =
            List.of("password", "token", "authorization", "secret", "cvv", "otp", "apiKey");

    public static String text(String input) {
        if (input == null) return null;
        String out = CARD.matcher(input).replaceAll(m -> keepLast4(m.group()));
        out = EMAIL.matcher(out).replaceAll("$1***@$2");
        out = PHONE.matcher(out).replaceAll("$1******$2");
        return out;
    }

    /** Masks values of known-sensitive keys in a JSON body before logging it. */
    public static String json(String body) {
        String out = body;
        for (String key : SECRET_KEYS) {
            out = out.replaceAll("(?i)(\"" + key + "\"\\s*:\\s*\")[^\"]*(\")", "$1***$2");
        }
        return out;
    }

    private static String keepLast4(String digits) {
        String clean = digits.replaceAll("\\D", "");
        return clean.length() < 4 ? "****"
                : "*".repeat(clean.length() - 4) + clean.substring(clean.length() - 4);
    }
    private Mask() { }
}

Q249Write a driver factory that supports local, headless, remote grid and mobile.▼
public final class DriverFactory {
    private static final ThreadLocal<WebDriver> TL = new ThreadLocal<>();

    public static void init() {
        String target  = Config.get("run.target");     // local | grid | mobile
        String browser = Config.get("browser");
        boolean headless = Config.getBool("headless");

        WebDriver driver = switch (target.toLowerCase()) {
            case "grid"   -> remote(browser, headless);
            case "mobile" -> mobile();
            default       -> local(browser, headless);
        };
        driver.manage().timeouts().pageLoadTimeout(Duration.ofSeconds(45));
        if (!"mobile".equalsIgnoreCase(target)) driver.manage().window().maximize();
        TL.set(driver);
    }

    private static WebDriver local(String browser, boolean headless) {
        return switch (browser.toLowerCase()) {
            case "firefox" -> new FirefoxDriver(firefoxOptions(headless));
            case "edge"    -> new EdgeDriver(new EdgeOptions());
            case "chrome"  -> new ChromeDriver(chromeOptions(headless));
            default -> throw new IllegalArgumentException("Unsupported browser: " + browser);
        };
    }

    private static WebDriver remote(String browser, boolean headless) {
        try {
            AbstractDriverOptions<?> options = "firefox".equalsIgnoreCase(browser)
                    ? firefoxOptions(headless) : chromeOptions(headless);
            RemoteWebDriver driver = new RemoteWebDriver(
                    new URL(Config.get("grid.url")), options);
            driver.setFileDetector(new LocalFileDetector());   // enables file upload on nodes
            return driver;
        } catch (MalformedURLException e) {
            throw new FrameworkException("Bad grid URL: " + Config.get("grid.url"), e);
        }
    }

    private static ChromeOptions chromeOptions(boolean headless) {
        ChromeOptions o = new ChromeOptions();
        if (headless) o.addArguments("--headless=new", "--window-size=1920,1080");
        o.addArguments("--no-sandbox", "--disable-dev-shm-usage", "--disable-notifications");
        o.setExperimentalOption("prefs",
                Map.of("profile.default_content_setting_values.notifications", 2));
        return o;
    }

    public static WebDriver get() {
        WebDriver d = TL.get();
        if (d == null) throw new IllegalStateException(
                "Driver not initialised on thread " + Thread.currentThread().getName());
        return d;
    }

    public static void quit() {
        WebDriver d = TL.get();
        if (d != null) {
            try { d.quit(); } finally { TL.remove(); }   // remove() even if quit() throws
        }
    }
    private DriverFactory() { }
}
The try { quit(); } finally { TL.remove(); } detail matters: if quit() throws because the browser already crashed, a naive implementation leaks the ThreadLocal and the next test on that pooled thread inherits a dead driver.

Q250Live exercise: "Automate this flow on a site you've never seen." How do you approach it?▼

Many companies now do this instead of theory questions — they open a demo site (saucedemo, the-internet, automationexercise) and ask you to automate a flow while sharing your screen. They are watching your process, not your typing speed.

  1. Clarify first. "Should I write this as a full framework or a single script? Do you want me to prioritise structure or coverage in the time we have?" This alone puts you ahead of most candidates.
  2. Explore the app for two minutes before writing anything. Walk the flow manually, open DevTools, and look at what locators exist. Say what you see: "there are no test ids, but the ids look stable, so I'll use those."
  3. Write the test first, top-down, as if the page objects already existed: 
    @Test
public void userCanBuyAProduct() {
    loginPage.loginAs(user, pass);
    productsPage.addToCart("Sauce Labs Backpack");
    cartPage.checkout();
    checkoutPage.fillDetails("Ravi", "Kumar", "560001");
    Assert.assertEquals(confirmationPage.getMessage(), "Thank you for your order!");
}
    Then implement downwards. It shows design thinking and gives you a working skeleton even if you run out of time.
  4. Narrate the trade-offs. "I'm using an explicit wait here rather than an implicit one because…" — the commentary is most of your score.
  5. Add one negative test if time allows. Almost every candidate automates only the happy path; adding "login with a locked-out user" shows a tester's instinct rather than a coder's.
  6. Finish with what you'd do next: "with more time I'd externalise the test data, add the driver factory for cross-browser, and wire this into CI with a screenshot listener." That turns an unfinished exercise into a demonstration of judgement.
Practise on saucedemo.com and the-internet.herokuapp.com until you can produce a clean POM-structured login-to-checkout test in 20 minutes from a blank file, talking the whole time. That single rehearsal is worth more than another 50 questions of theory.

BOne-line answers to the 25 most-asked definitions▼
  • Verification / Validation — building it right / building the right thing.
  • Smoke / Sanity — is the build testable? / is this one fix working?
  • Retest / Regression — confirm this bug is fixed / confirm nothing else broke.
  • Severity / Priority — technical impact (tester) / business urgency (PO).
  • Stub / Driver — replaces the called module / replaces the calling module.
  • Alpha / Beta — internal staff at our site / real users at their site.
  • EP / BVA — one value per class / values at and around the edges.
  • findElement / findElements — throws if absent / returns an empty list.
  • close() / quit() — current window / whole session and driver process.
  • Implicit / Explicit wait — global DOM presence / per-element condition.
  • Absolute / Relative XPath — from /html, brittle / from //, resilient.
  • StaleElement — the DOM node your reference pointed to was replaced.
  • ThreadLocal — one value per thread; makes parallel Selenium safe.
  • Singleton / Factory — one instance globally / create objects without naming the class.
  • @Parameters / @DataProvider — config from XML / data rows from Java.
  • Hard / Soft assert — stops at the first failure / collects all, needs assertAll().
  • Surefire / Failsafe — unit tests at test / integration tests at verify.
  • Merge / Rebase — preserves history with a merge commit / rewrites into a linear history.
  • CI / CD — integrate and test every commit / always deployable (or auto-deployed).
  • Locator / ElementHandle (PW) — lazy description, never stale / bound node, can go stale.
  • BrowserContext (PW) — an isolated incognito session created in milliseconds.
  • Web-first assertion (PW) — an assertion that auto-retries until it passes or times out.
  • storageState (PW) — saved cookies + localStorage, so you log in once for the whole suite.
  • Idempotent — calling it N times has the same effect as calling it once.
  • 401 / 403 — not authenticated / authenticated but not allowed.

FINAL

Questions YOU should ask the interviewer

"Do you have any questions for us?" is a scored question. Saying "no" is the most common self-inflicted wound in interviewing.

DAsk 3–4 of these. They make you look senior and they tell you whether to accept the offer.▼
About the work
  • "What does the current automation suite look like — how many tests, how long does it take, and what's the pass rate on a typical night?" (A vague or embarrassed answer tells you a lot.)
  • "Is the automation a gate in the pipeline, or is it informational?"
  • "How is the QA team structured — embedded in feature teams, or a separate QA function?"
  • "Who writes the automated tests today — QA only, or do developers contribute?"
  • "What would you want the person in this role to have achieved in the first six months?"
About quality culture
  • "When a bug reaches production, what does the team do afterwards?" (Looking for: blameless post-mortem and a regression test — not blame.)
  • "How involved is QA at the requirements stage?"
  • "What's the release cadence, and what's the biggest bottleneck in getting a change to production?"
  • "How do you handle the trade-off when a release date is fixed and testing isn't complete?"
About growth
  • "What does the growth path look like for an automation engineer here — is there a senior IC track, or is it management?"
  • "Is there budget/time for learning — conferences, certifications, internal tech talks?"
  • "What's the biggest technical challenge the team is facing right now?" (Great question — the answer often reveals the real reason they're hiring.)
Close the interview with intent: "This sounds like exactly the kind of problem I enjoy — is there anything about my background you'd like me to expand on, or any concern I can address?" It's a confident, professional close that occasionally lets you fix a misunderstanding on the spot.
