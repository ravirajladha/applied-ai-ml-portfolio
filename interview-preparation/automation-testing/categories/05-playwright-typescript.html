Q151 – Q190 · The fastest-growing skill in QA job descriptions. Interviewers assume you know Selenium; what they're probing is whether you understand why Playwright is architecturally different — not just its syntax.

Q151What is Playwright and how does its architecture differ from Selenium's?▼

Playwright is an open-source end-to-end testing framework from Microsoft that automates Chromium, Firefox and WebKit with a single API. Unlike Selenium it is a complete test framework — runner, assertions, fixtures, parallelism, reporting and tracing all come in the box.

Architectural differences
  • Transport — Selenium sends one HTTP request per command via the W3C protocol. Playwright keeps a single WebSocket connection to a Node driver process, which speaks each browser's native debugging protocol. Fewer round trips, and the browser can push events back.
  • Bi-directional — because events flow both ways, Playwright natively knows when the DOM changed, when a request fired, when navigation completed. That is the foundation of auto-waiting.
  • BrowserContext — a lightweight isolated browser session (own cookies, storage, cache) that starts in milliseconds. Selenium's equivalent isolation requires launching a whole new browser.
  • Bundled browsers — Playwright downloads and pins patched browser builds, so version mismatch problems largely disappear.

Never say "Playwright is better" flatly. Say: "For a new greenfield web project I'd pick Playwright — the auto-waiting and Trace Viewer alone cut flakiness and debugging time dramatically, and it's faster out of the box. I'd stay with Selenium where the team's skills and existing suite are Java/Selenium and the migration cost isn't justified, where real mobile devices or legacy browsers matter, or where the organisation's grid and cloud tooling is built around WebDriver. The right tool depends on the team, not the hype."

Q154Explain Browser, BrowserContext and Page. Why does BrowserContext matter?▼
const browser = await chromium.launch({ headless: true });   // 1 OS process — expensive
const context = await browser.newContext({                    // isolated session — cheap
  viewport: { width: 1440, height: 900 },
  storageState: 'auth/admin.json',
  locale: 'en-IN',
});
const page = await context.newPage();                         // a tab
await page.goto('/dashboard');
await context.close();
await browser.close();
  • Browser — the launched browser process. Heavy; Playwright reuses one per worker.
  • BrowserContext — an isolated incognito-like session with its own cookies, localStorage, cache, permissions and geolocation. Creating one takes milliseconds.
  • Page — a single tab within a context. A context can hold several pages that share storage.
Why it matters (the interview point)

Playwright's test runner gives every test its own context. That means perfect test isolation — no cookie or storage leakage between tests — without the cost of restarting a browser. This is the main reason a Playwright suite runs several times faster than the equivalent Selenium suite while being more isolated.

// Multi-user scenario in ONE test — trivial in Playwright, painful in Selenium
test('admin approves what the user submitted', async ({ browser }) => {
  const userCtx  = await browser.newContext({ storageState: 'auth/user.json'  });
  const adminCtx = await browser.newContext({ storageState: 'auth/admin.json' });
  const userPage  = await userCtx.newPage();
  const adminPage = await adminCtx.newPage();
  await userPage.goto('/requests/new');
  // ... submit as user, then approve as admin, in the same test
});

Q155What is auto-waiting? What actionability checks does Playwright perform?▼

Before performing an action, Playwright automatically waits for the element to pass a series of actionability checks, retrying until they pass or the timeout expires. You almost never write a wait.

CheckMeaning
AttachedElement is in the DOM
VisibleNon-empty bounding box and not visibility:hidden
StableBounding box hasn't changed for two consecutive animation frames (i.e. animation finished)
Receives eventsIt is the actual hit target at the click point — not covered by an overlay
EnabledNot disabled
EditableFor fill(): enabled and not readonly

Which checks apply depends on the action: click() does all of visible/stable/receives-events/enabled; fill() adds editable; textContent() requires none.

Contrast to draw in the interview: "In Selenium, elementToBeClickable only checks visible + enabled — it will happily return an element that is covered by a modal overlay, and then click() throws ElementClickInterceptedException. Playwright's 'receives events' and 'stable' checks eliminate that entire class of flakiness."
Auto-waiting is not magic: it does not wait for your application's business state (e.g. "the order has been persisted"). For that you still assert on an observable condition — a visible confirmation, a network response, or an API check.

Q156What are Playwright locators, and how do they differ from ElementHandles?▼
const loginBtn = page.getByRole('button', { name: 'Sign in' });   // a Locator
await loginBtn.click();

A Locator is a lazy description of how to find an element — not the element itself. It is resolved fresh at the moment of every action. That is why Playwright has no equivalent of StaleElementReferenceException: the reference cannot go stale because there is no reference.

Locator (use this)ElementHandle (legacy)
ResolutionLazy, re-queried each actionBound to one DOM node at creation
Stale riskNoneYes, if the DOM re-renders
Auto-waitingYesNo
APIpage.getByRole(), page.locator()page.$(), page.$$() — discouraged
Recommended locators, in priority order (user-facing first)
page.getByRole('button', { name: 'Add to cart' })   // ARIA role + accessible name  ← best
page.getByLabel('Email address')                    // form field by its <label>
page.getByPlaceholder('Search products')
page.getByText('Order confirmed')                   // visible text
page.getByAltText('Company logo')
page.getByTitle('Close')
page.getByTestId('checkout-submit')                 // data-testid — stable, explicit
page.locator('css=.product-card')                   // CSS / XPath — last resort
page.locator('//table//tr[3]/td[2]')
Why getByRole is recommended: it queries the accessibility tree, so your test uses the app the way a screen reader (and therefore a user) does. If getByRole('button', {name:'Sign in'}) fails, it often means a genuine accessibility defect. That reasoning is exactly what interviewers want to hear.

Q157What is locator strictness, and how do you filter/chain locators?▼

Strict mode is on by default: if a locator resolves to more than one element, the action throws a strict mode violation error instead of silently using the first match. This catches ambiguous locators at the moment you write them, rather than in production when a second match appears.

// ✗ throws if there are 12 "Add to cart" buttons
await page.getByRole('button', { name: 'Add to cart' }).click();

// ✓ narrow it properly
await page.getByRole('listitem').filter({ hasText: 'Wireless Mouse' })
          .getByRole('button', { name: 'Add to cart' }).click();

// chaining — scope a search inside another locator
const row = page.getByRole('row', { name: /ORD-991/ });
await row.getByRole('button', { name: 'Cancel' }).click();

// filtering
page.getByRole('listitem').filter({ hasText: 'In stock' });
page.getByRole('listitem').filter({ hasNotText: 'Sold out' });
page.getByRole('listitem').filter({ has: page.getByRole('img') });
page.locator('.card').filter({ hasNot: page.locator('.badge-new') });

// positional (use sparingly — brittle)
page.getByRole('listitem').first();
page.getByRole('listitem').last();
page.getByRole('listitem').nth(2);

// combining with or / and (newer versions)
page.getByRole('button', { name: 'Save' }).or(page.getByRole('button', { name: 'Update' }));

// count and iterate
const items = page.getByTestId('product');
await expect(items).toHaveCount(12);
for (const item of await items.all()) {
  console.log(await item.textContent());
}

Q158What are web-first assertions and why do they matter?▼

Assertions on a Locator or Page automatically retry until they pass or the expect timeout expires. This removes the classic "assert too early" race that plagues Selenium suites.

// Auto-retrying (web-first) — these WAIT
await expect(page.getByText('Order confirmed')).toBeVisible();
await expect(page.getByTestId('total')).toHaveText('₹1,499.00');
await expect(page.getByTestId('total')).toContainText('1,499');
await expect(page.getByRole('button', { name: 'Pay' })).toBeEnabled();
await expect(page.getByLabel('Terms')).toBeChecked();
await expect(page.getByTestId('product')).toHaveCount(12);
await expect(page.getByRole('textbox')).toHaveValue('ravi@test.com');
await expect(page.locator('.error')).toHaveAttribute('role', 'alert');
await expect(page.locator('.badge')).toHaveClass(/active/);
await expect(page).toHaveURL(/\/orders\/\d+/);
await expect(page).toHaveTitle('Checkout — Shop');
await expect(page.getByRole('list')).toHaveScreenshot('cart.png');
await expect(locator).not.toBeVisible();            // negation retries too

// Non-retrying (generic) — these compare a value ONCE
expect(orderId).toBe('ORD-991');
expect(items).toHaveLength(3);
expect(response.status()).toBe(201);
expect(user).toEqual({ id: 1, name: 'Ravi' });
The #1 mistake beginners make: forgetting await on an assertion. expect(locator).toBeVisible() without await returns a floating promise — the test passes regardless. Enable the ESLint rule @typescript-eslint/no-floating-promises to catch it. Mentioning this shows real hands-on experience.
// Custom timeout for one slow assertion
await expect(page.getByText('Report ready')).toBeVisible({ timeout: 60_000 });

// Poll a non-locator value with retry (e.g. an API state)
await expect.poll(async () => (await api.getOrder(id)).status,
                  { timeout: 30_000, intervals: [1000, 2000, 5000] })
      .toBe('CONFIRMED');

// Retry an arbitrary block of assertions
await expect(async () => {
  const res = await request.get(`/api/orders/${id}`);
  expect(res.status()).toBe(200);
}).toPass({ timeout: 20_000 });

Q159How do soft assertions and custom matchers work in Playwright?▼
// Soft assertions — the test continues and reports ALL failures at the end
await expect.soft(page.getByTestId('name')).toHaveText('Ravi Kumar');
await expect.soft(page.getByTestId('gst')).toHaveText('18%');
await expect.soft(page.getByTestId('total')).toHaveText('₹1,499.00');
// The test is marked failed at the end automatically — no assertAll() needed.

// Stop early if any soft assertion has already failed
expect(test.info().errors).toHaveLength(0);

// Custom matcher — makes domain assertions readable and reusable
import { expect as baseExpect } from '@playwright/test';

export const expect = baseExpect.extend({
  async toBeValidOrderId(received: string) {
    const pass = /^ORD-\d{4}-\d{4}$/.test(received);
    return {
      pass,
      message: () => `expected "${received}" ${pass ? 'not ' : ''}to be a valid order id`,
    };
  },
});

// usage
expect(orderId).toBeValidOrderId();
Unlike TestNG's SoftAssert, Playwright's soft assertions cannot be silently forgotten — there is no assertAll() to miss. That is a nice comparison point to raise.

Q160How do you structure tests — test, describe, hooks and test.step?▼
import { test, expect } from '@playwright/test';

test.describe('Checkout', () => {
  test.describe.configure({ mode: 'serial' });   // or 'parallel' (default)

  test.beforeAll(async () => { /* once per worker for this describe */ });
  test.beforeEach(async ({ page }) => { await page.goto('/cart'); });
  test.afterEach(async ({ page }, testInfo) => {
    if (testInfo.status !== testInfo.expectedStatus) console.log('failed:', testInfo.title);
  });
  test.afterAll(async () => { /* cleanup */ });

  test('pays with a valid card @smoke', async ({ page }) => {
    await test.step('open checkout', async () => {
      await page.getByRole('button', { name: 'Checkout' }).click();
    });
    await test.step('enter card details', async () => {
      await page.getByLabel('Card number').fill('4111111111111111');
      await page.getByLabel('CVV').fill('123');
    });
    await test.step('verify confirmation', async () => {
      await expect(page.getByText('Order confirmed')).toBeVisible();
    });
  });

  test.skip(({ browserName }) => browserName === 'webkit', 'Not supported on Safari yet');
  test.fixme('known broken', async ({ page }) => { });
  test.fail('expected to fail until BUG-412 is fixed', async ({ page }) => { });
  test.slow();                                   // triples the timeout
  test.setTimeout(120_000);
  test.only('debug just this one', async ({ page }) => { });   // forbidden in CI
});

test.use({ locale: 'fr-FR', viewport: { width: 375, height: 812 } });  // override config
test.step is undervalued: steps appear as a collapsible tree in the HTML report and the Trace Viewer, so a failure immediately shows which business step broke. Use it in page-object methods too, and your report becomes self-documenting.

Q161What are fixtures in Playwright? Write a custom fixture.▼

Fixtures are Playwright's dependency-injection mechanism. Instead of beforeEach setting up shared variables, you declare what a test needs in its arguments and Playwright constructs it, on demand, and tears it down afterwards.

Built-in fixtures: page, context, browser, browserName, request (API), baseURL.

// fixtures.ts — page objects + an authenticated API client as fixtures
import { test as base } from '@playwright/test';
import { LoginPage } from './pages/login.page';
import { CheckoutPage } from './pages/checkout.page';

type Fixtures = {
  loginPage: LoginPage;
  checkoutPage: CheckoutPage;
  testOrder: { id: string };
};

export const test = base.extend<Fixtures>({
  loginPage:    async ({ page }, use) => { await use(new LoginPage(page)); },
  checkoutPage: async ({ page }, use) => { await use(new CheckoutPage(page)); },

  // A fixture with setup AND teardown — creates data, then cleans it up
  testOrder: async ({ request }, use) => {
    const res = await request.post('/api/orders', { data: { sku: 'TSH-001', qty: 1 } });
    const order = await res.json();
    await use(order);                                  // <-- the test runs here
    await request.delete(`/api/orders/${order.id}`);   // always runs, even on failure
  },
});
export { expect } from '@playwright/test';
// the test — declarative and clean
import { test, expect } from './fixtures';

test('can cancel an existing order', async ({ page, testOrder, checkoutPage }) => {
  await page.goto(`/orders/${testOrder.id}`);
  await checkoutPage.cancelOrder();
  await expect(page.getByText('Order cancelled')).toBeVisible();
});

Fixture scopes: { scope: 'test' } (default) or { scope: 'worker' } for expensive setup shared across tests in a worker. Use auto: true to run a fixture even if no test requests it (e.g. per-test logging).

The interview point: fixtures are lazy. A fixture is only created if a test actually asks for it, so unlike beforeEach you never pay for setup a test doesn't need.

Q162How does parallel execution work? Explain workers, sharding and fullyParallel.▼
  • Workers — independent Node processes, each with its own browser instance. Default is half the CPU cores; set with workers: 4 or --workers=4.
  • By default, files run in parallel and tests within a file run sequentially. fullyParallel: true makes individual tests parallel too.
  • test.describe.configure({ mode: 'serial' }) — run in order, and skip the rest if one fails (for genuinely dependent flows). mode: 'parallel' forces parallel within a file.
  • Sharding — split the suite across CI machines: 
    npx playwright test --shard=1/4      # machine 1 of 4
npx playwright test --shard=2/4
npx playwright merge-reports ./all-blob-reports   # combine into one HTML report
  • Projects run in parallel with each other too, so cross-browser costs little extra wall-clock time.
// Worker-scoped index for isolated test data per worker
test('uses a dedicated account', async ({ page }, testInfo) => {
  const account = ACCOUNTS[testInfo.workerIndex % ACCOUNTS.length];
  // ...
});
Same prerequisite as TestNG: parallel only works if tests are independent. Playwright helps by isolating browser state automatically, but it cannot isolate your backend data — two workers cancelling the same order will still collide. Per-test data creation via API is the fix.

Q163How do you debug a Playwright test? Explain the Trace Viewer.▼
npx playwright test --ui            # UI mode: watch, time-travel, pick locators live
npx playwright test --debug         # step through with the Playwright Inspector
PWDEBUG=1 npx playwright test       # same, via env var
npx playwright test --headed --slowmo=500
npx playwright codegen example.com  # record actions into code; also a locator picker
npx playwright show-trace trace.zip
npx playwright show-report
await page.pause();                 // opens the Inspector at this line
console.log(await page.content());
await page.screenshot({ path: 'debug.png', fullPage: true });
Trace Viewer — the killer feature

With trace: 'on-first-retry', a failed test produces a trace.zip containing:

  • A timeline filmstrip of screenshots for every action.
  • A full DOM snapshot before and after each action — you can open DevTools on the past state and inspect elements as they were at the moment of failure.
  • All network requests and responses, console logs, and the source line for each action.
  • Action duration, so you can see what was slow.
When asked "how do you debug a failure that only happens in CI?", this is the answer: "The trace from the CI run is downloaded as an artifact and opened locally — I get the exact DOM, network and console state at failure, without reproducing anything. In Selenium the same investigation means adding logging and re-running." That single point often wins the Playwright portion of an interview.

Q164How do you handle authentication so you don't log in through the UI in every test?▼

storageState saves cookies + localStorage to a JSON file, which any context can then load. Log in once, reuse everywhere.

// tests/global.setup.ts — a "setup project" that other projects depend on
import { test as setup, expect } from '@playwright/test';

const USER_FILE  = 'playwright/.auth/user.json';
const ADMIN_FILE = 'playwright/.auth/admin.json';

setup('authenticate as user', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill(process.env.USER_EMAIL!);
  await page.getByLabel('Password').fill(process.env.USER_PASSWORD!);
  await page.getByRole('button', { name: 'Sign in' }).click();
  await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible();
  await page.context().storageState({ path: USER_FILE });
});
// playwright.config.ts
projects: [
  { name: 'setup', testMatch: /global\.setup\.ts/ },
  { name: 'chromium', dependencies: ['setup'],
    use: { ...devices['Desktop Chrome'], storageState: 'playwright/.auth/user.json' } },
]
// Faster still — get the token from the API, skip the UI entirely
setup('authenticate via API', async ({ request }) => {
  const res = await request.post('/api/login',
      { data: { email: process.env.USER_EMAIL, password: process.env.USER_PASSWORD } });
  await request.storageState({ path: USER_FILE });
});

// Per-test override for a different role
test.use({ storageState: 'playwright/.auth/admin.json' });

// Or a fresh, unauthenticated context for the login tests themselves
test.use({ storageState: { cookies: [], origins: [] } });
Add playwright/.auth to .gitignore — the file contains live session tokens. And keep one real UI login test so the login page itself is still covered.

Q165How do you intercept and mock network requests?▼
// Stub an API response — test the UI against any backend state you like
await page.route('**/api/orders', async route => {
  await route.fulfill({
    status: 200,

  });

  await new Promise(r => setTimeout(r, 5000));
  await route.continue();
});

// Block noisy third parties — makes tests faster AND less flaky
await page.route(/(analytics|doubleclick|hotjar|\.gif$)/, r => r.abort());

// Modify a real response (spy + patch)
await page.route('**/api/user', async route => {
  const response = await route.fetch();
  const json = await response.json();
  json.role = 'ADMIN';                                   // escalate for a UI-only test
  await route.fulfill({ response, json });
});

// Modify the outgoing request
await page.route('**/api/**', route =>
  route.continue({ headers: { ...route.request().headers(), 'x-test-run': runId } }));

await page.unroute('**/api/orders');                     // remove the handler
Waiting for and asserting on network traffic
const responsePromise = page.waitForResponse(r =>
    r.url().includes('/api/orders') && r.status() === 201);
await page.getByRole('button', { name: 'Place order' }).click();
const response = await responsePromise;                  // set up BEFORE the action
const body = await response.json();
expect(body.status).toBe('CONFIRMED');
Ordering trap: you must create the waitForResponse promise before the click that triggers it. If you await the click first, the response may already have arrived and you'll hang until timeout. Interviewers ask this specifically.
Balance to mention: mocking makes tests fast and deterministic but stops testing the real contract. My rule: mock for edge cases and error states that are hard to produce for real; keep a smaller set of true end-to-end tests against the real backend.

Q166How do you do API testing in Playwright?▼
// Pure API test — no browser launched at all
import { test, expect } from '@playwright/test';

test('creates an order via API', async ({ request }) => {
  const res = await request.post('/api/v1/orders', {
    headers: { Authorization: `Bearer ${token}` },
    data: { sku: 'TSH-001', qty: 2 },
  });
  expect(res.status()).toBe(201);
  expect(res.ok()).toBeTruthy();
  const body = await res.json();
  expect(body).toMatchObject({ status: 'CONFIRMED', qty: 2 });
  expect(res.headers()['content-type']).toContain('application/json');
});

// A reusable, pre-authenticated API context
import { request as pwRequest } from '@playwright/test';
const api = await pwRequest.newContext({
  baseURL: process.env.API_URL,
  extraHTTPHeaders: { Authorization: `Bearer ${token}` },
});

// The high-value pattern: API for setup, UI for the thing under test
test('order appears in the UI order history', async ({ page, request }) => {
  const created = await (await request.post('/api/orders',
        { data: { sku: 'TSH-001', qty: 1 } })).json();       // fast setup
  await page.goto('/orders');
  await expect(page.getByRole('row', { name: created.id })).toBeVisible();
});
Emphasise the architectural advantage: "In Playwright, API and UI testing share the same runner, fixtures, reporter and trace. In the Java world I'd wire RestAssured into TestNG separately. That single-toolchain point is a real productivity argument."

Q172Do you need explicit waits in Playwright? What waiting APIs exist?▼

Rarely — auto-waiting plus retrying assertions cover most cases. But these exist for real situations:

await page.waitForURL('**/orders/*');
await page.waitForURL(/\/dashboard/, { timeout: 15_000 });

await page.waitForLoadState('domcontentloaded');    // 'load' | 'domcontentloaded' | 'networkidle'
await page.waitForSelector('.spinner', { state: 'hidden' });   // 'attached'|'detached'|'visible'|'hidden'

await page.waitForRequest('**/api/track');
await page.waitForEvent('popup');
await page.waitForEvent('download');

// Wait for arbitrary JS state in the page
await page.waitForFunction(() => window.dataLayer?.length > 0);
await page.waitForFunction(sel => document.querySelectorAll(sel).length > 10, '.row');

// Retry a whole block of assertions
await expect(async () => { expect(await getStatus()).toBe('READY'); }).toPass();

await page.waitForTimeout(1000);   // ← the only "sleep". Debugging only, never commit it.
waitForLoadState('networkidle') is discouraged by the Playwright team. Q177Why TypeScript over plain JavaScript for test automation?▼
  • Compile-time safety — a typo in a method name or a wrong argument type fails at build time, not 40 minutes into a nightly run.
  • IDE autocomplete and inline docs for the whole Playwright API — a huge productivity difference for a team.
  • Safer refactoring — rename a page-object method and the compiler finds every call site.
  • Self-documenting — typed test data models (interface User) make the intent obvious.
  • Typed fixtures — base.extend<MyFixtures>() only works properly with types.
  • Playwright itself is written in TypeScript, so the typings are first-class; it transpiles TS out of the box with no extra build step.

Cost, to be fair: a slightly steeper learning curve and occasional type gymnastics. For anything beyond a throwaway script the trade is clearly worth it.

Q179Explain async/await and Promises. What mistakes do people make in Playwright tests?▼

A Promise represents a value that will be available later (pending → fulfilled/rejected). async marks a function that returns a Promise; await pauses inside it until the Promise settles. Almost every Playwright API returns a Promise.

// ✗ MISTAKE 1 — missing await on an assertion: the test always passes
expect(page.getByText('Order confirmed')).toBeVisible();
// ✓
await expect(page.getByText('Order confirmed')).toBeVisible();

// ✗ MISTAKE 2 — missing await on an action: race condition / unhandled rejection
page.getByRole('button', { name: 'Save' }).click();
// ✓
await page.getByRole('button', { name: 'Save' }).click();

// ✗ MISTAKE 3 — await inside forEach: forEach ignores the returned promise
items.forEach(async item => { await item.click(); });   // does NOT wait
// ✓
for (const item of items) { await item.click(); }
// ✓ or, for independent operations, run them concurrently:
await Promise.all(items.map(i => i.click()));

// ✗ MISTAKE 4 — awaiting the trigger before setting up the waiter
await page.getByRole('button', { name: 'Export' }).click();
const download = await page.waitForEvent('download');   // may hang — event already fired
// ✓
const [download] = await Promise.all([
  page.waitForEvent('download'),
  page.getByRole('button', { name: 'Export' }).click(),
]);

// Error handling
try { await page.goto('/slow'); }
catch (e) { console.error('navigation failed', e); throw e; }

// Promise.all (fail fast) vs Promise.allSettled (collect all results)
const [a, b] = await Promise.all([apiCall1(), apiCall2()]);
const results = await Promise.allSettled([apiCall1(), apiCall2()]);
Enable @typescript-eslint/no-floating-promises and eslint-plugin-playwright in the repo. They catch missing awaits automatically — mentioning this shows you think about preventing whole classes of bugs, not just fixing them.

  const critical = results.violations.filter(v => v.impact === 'critical');
  expect(critical, critical.map(v => `${v.id}: ${v.help}`).join('\n')).toEqual([]);
});

Common findings: missing form labels, insufficient colour contrast, missing alt text, wrong heading order, non-focusable interactive elements, missing ARIA landmarks.

Be accurate about the limits: automated scanning catches roughly a third of WCAG issues. It cannot judge whether alt text is meaningful, whether the tab order is logical, or whether a screen-reader flow makes sense. Automated scan in CI + periodic manual keyboard/screen-reader testing is the honest answer.

Q187How do you work with tables and dynamic lists in Playwright?▼
// Find a row by content and act on it — readable, no XPath axes needed
const row = page.getByRole('row', { name: /ORD-991/ });
await expect(row.getByRole('cell', { name: 'Delivered' })).toBeVisible();
await row.getByRole('button', { name: 'Cancel' }).click();

// Or with filter()
const row2 = page.locator('tbody tr').filter({ hasText: 'ORD-991' });

// Read a whole column
const statuses = await page.locator('tbody tr td:nth-child(4)').allTextContents();
expect(statuses).toContain('Delivered');

// Assert sorting
const prices = (await page.getByTestId('price').allTextContents())
    .map(t => Number(t.replace(/[^0-9.]/g, '')));
expect(prices).toEqual([...prices].sort((a, b) => a - b));

// Row count with auto-retry (waits for the table to load)
await expect(page.locator('tbody tr')).toHaveCount(25);

// Iterate safely
for (const row of await page.locator('tbody tr').all()) {
  const id = await row.getByTestId('order-id').textContent();
  console.log(id);
}

// Pagination
while (await page.getByRole('button', { name: 'Next' }).isEnabled()) {
  await collectCurrentPage();
  await page.getByRole('button', { name: 'Next' }).click();
  await expect(page.getByTestId('page-indicator')).not.toHaveText(previousPage);
}
Compare with the Selenium equivalent (Q95): no stale-element loops, no ancestor:: XPath, and toHaveCount waits for the table to populate. This is the concrete example to give when asked "what does Playwright actually make easier?"

Q188What is component testing in Playwright, and when would you use it?▼

Playwright can mount a single React/Vue/Svelte component in a real browser and test it in isolation — no full app, no backend, no navigation.

import { test, expect } from '@playwright/experimental-ct-react';
import { PriceTag } from './PriceTag';

test('formats Indian currency and shows a discount badge', async ({ mount }) => {
  const component = await mount(<PriceTag amount={1499} discount={20} currency="INR" />);
  await expect(component).toContainText('₹1,499.00');
  await expect(component.getByTestId('discount-badge')).toHaveText('20% off');
});

When to use it: for a design system or a component with many states (loading, empty, error, long text, RTL, disabled). Testing 12 states of a component takes seconds here versus minutes of navigating the full app in E2E. It sits between unit tests (jsdom, not a real browser) and E2E (real browser, full app).

Note that it is still marked experimental — say so rather than presenting it as a mainstream production choice.

Q189How would you migrate an existing Selenium suite to Playwright?▼

Never answer "rewrite everything". Answer with a risk-managed plan.

  1. Justify it with data, not preference. Current runtime, flakiness rate, maintenance hours per sprint, debugging time per CI failure. If those numbers aren't painful, don't migrate.
  2. Pilot. Port 10–15 representative tests (including the trickiest: iframes, file upload, multi-tab, dynamic tables) in a spike. Measure runtime and stability against the Selenium equivalents. Present the comparison.
  3. Run both in parallel. Keep Selenium as the gate while Playwright coverage grows; nothing loses coverage during the transition.
  4. Migrate by value, not by file order. Start with the flakiest and slowest suites — the biggest wins first — plus any new tests, which are written only in Playwright from day one.
  5. Rebuild rather than transliterate. A line-by-line port carries over every explicit wait and every brittle XPath. Re-express tests with getByRole and web-first assertions, or you inherit the old flakiness in new syntax.
  6. Address the team. Java/Selenium people need TypeScript and async/await training; budget for it. (Playwright does have a Java binding, but the TS ecosystem is where the tooling and examples are.)
  7. Retire deliberately. Delete each Selenium test only when its Playwright counterpart has been green for a couple of weeks.
The mature closing line: "Migration is a cost with no new features for the business, so it has to be justified by measurable pain and delivered incrementally without ever leaving the team without a working regression suite."

Q190What are the most common Playwright mistakes and best practices?▼
Mistakes
  • Missing await — the assertion never runs and the test always passes.
  • Using page.waitForTimeout() as a wait strategy.
  • Using CSS/XPath everywhere instead of role/label/testid locators.
  • Using force: true to "make it work" instead of understanding the failure.
  • Using page.$() / ElementHandles instead of Locators.
  • Logging in through the UI in every test instead of storageState.
  • Sharing state between tests (module-level variables, a fixed test record) — breaks parallelism.
  • Committing test.only (set forbidOnly: true in CI).
  • Turning up timeouts to hide a real problem.
  • Not enabling traces, then having no idea why CI failed.
Best practices
  • Test user-visible behaviour, not implementation details.
  • Prefer getByRole → getByLabel → getByTestId; CSS/XPath last.
  • Web-first assertions everywhere; let them do the waiting.
  • Each test independent, self-seeding its data via API, running from a clean context.
  • trace: 'on-first-retry', screenshots and video on failure.
  • Page objects + fixtures + test.step for readable reports.
  • Lint with eslint-plugin-playwright; type everything.
  • Keep the smoke suite under 10 minutes and make it a merge gate.
