Q66What is Selenium and what are its components?▼

Selenium is a free, open-source suite for automating web browsers. It is not a testing tool by itself — it is a browser-driving library; you add a test framework (TestNG/JUnit), assertions and reporting around it.

  • Selenium IDE — a browser extension for record-and-playback. Good for quick prototypes and for non-programmers; not used for production suites.
  • Selenium WebDriver — the programmable API (Java, Python, C#, JS, Ruby, Kotlin) that drives a real browser via the browser's native driver. This is what "Selenium" means in practice.
  • Selenium Grid — distributes tests across multiple machines/browsers in parallel.
  • Selenium RC — the deprecated predecessor (proxy/JS-injection based), removed in Selenium 3+. Mention it only historically.
Supported languages: Java, Python, C#, Ruby, JavaScript, Kotlin. Supported browsers: Chrome, Firefox, Edge, Safari, Opera, and headless variants.

Q67Explain the Selenium WebDriver architecture — what happens when you call driver.findElement(...).click()?▼
  1. Your test calls a method on the WebDriver interface (implemented by ChromeDriver → RemoteWebDriver).
  2. The Selenium client library serialises that command into an HTTP request with a JSON body following the W3C WebDriver protocol, e.g. POST /session/{id}/element with {"using":"css selector","value":"#login"}.
  3. The request goes over HTTP to the browser driver (chromedriver / geckodriver / msedgedriver), which is a small HTTP server running locally on a port.
  4. The driver translates it into the browser's own native automation interface (DevTools Protocol for Chrome, Marionette for Firefox) and executes it.
  5. The browser performs the action on the real DOM and returns a result. The driver wraps it in an HTTP response; the client deserialises it into a Java object (a WebElement reference, a String, or an exception).

Key consequence to state: every single Selenium command is a network round trip. That is why a loop calling getText() on 500 rows is slow, and why chaining fewer, smarter commands (or one executeScript) is faster.

Also mention: since Selenium 4.6, Selenium Manager is built in — it auto-downloads the matching driver binary, so WebDriverManager and manual System.setProperty("webdriver.chrome.driver", ...) are no longer required.

Q69What are Selenium's limitations?▼
  • Web only — no desktop apps (use WinAppDriver/Appium for desktop, Appium for mobile native).
  • No built-in reporting, assertions, or test runner — you supply TestNG/JUnit + Extent/Allure.
  • Cannot read non-web content: captcha, OTP, barcodes, PDF content (needs PDFBox), images (needs OCR/visual tools).
  • No native API/DB testing — combine with RestAssured / JDBC.
  • Windows-level dialogs (Windows file picker, print dialog, basic-auth popups, browser notification prompts) are outside the DOM — need Robot class, AutoIT, or browser options.
  • Flakiness from timing and dynamic DOMs — needs a disciplined wait strategy.
  • Performance / load testing is not its purpose (spinning up 1000 browsers is not a load test — use JMeter/k6).
  • No official support — it is a community-driven open-source project.

Q70List all Selenium locators. Which do you prefer and why?▼

Eight standard locators: id, name, className, tagName, linkText, partialLinkText, cssSelector, xpath. Selenium 4 adds relative locators.

My preference order
  1. Custom test attribute — [data-testid='login-btn']. Ask the developers to add these; they never change with styling. This answer alone impresses interviewers.
  2. id — fastest and unique... if it is static. Watch out for generated ids like input_28471.
  3. name, then cssSelector — concise, fast, readable.
  4. linkText / partialLinkText — only for anchors; breaks with localisation.
  5. xpath — last resort, but unavoidable when you need to traverse up the DOM or match by visible text.
  6. Avoid tagName and bare className alone — almost never unique.
Never use absolute XPath (/html/body/div[2]/div[3]/form/input[1]). One extra wrapper div from a designer and every test breaks.
driver.findElement(By.id("username"));
driver.findElement(By.cssSelector("[data-testid='submit']"));
driver.findElement(By.xpath("//button[normalize-space()='Sign in']"));
// Selenium 4 relative locator:
driver.findElement(with(By.tagName("input")).below(By.id("password-label")));

Q71XPath: absolute vs relative, and the syntax you must know by heart.▼

Absolute starts at the root with a single slash /html/body/div/... — extremely brittle. Relative starts with // and searches anywhere in the DOM.

//tagname[@attribute='value']            // basic
//input[@id='user' and @type='text']     // multiple conditions
//input[@id='user' or @name='user']
//*[@id='user']                          // any tag
//button[text()='Submit']                // exact visible text
//button[normalize-space()='Submit']     // trims & collapses whitespace  ← use this one
//div[contains(@class,'alert')]          // partial attribute match
//a[starts-with(@href,'/orders/')]
//input[ends-with(@id,'_email')]         // XPath 2.0 — NOT supported by browsers!
//td[contains(text(),'Delivered')]
(//table//tr)[3]                         // indexing — brackets around the whole expression
//table//tr[last()]
//table//tr[position()<=5]
//input[@type='checkbox'][not(@disabled)]
//div[@class='card'][.//span[text()='In stock']]   // predicate with nested condition
Two very common traps: (1) ends-with() is XPath 2.0 and does not work in browsers — use contains() or substring(). (2) //tr[1] means "the first tr within each parent", while (//tr)[1] means "the first tr in the whole document". Interviewers love this one.

Q74How do you handle dynamic elements whose id/class changes on every page load?▼

Strategies, in order of preference:

  1. Anchor to something stable — a label, heading or visible text near it, then traverse with XPath axes.
  2. Partial matching on the stable part of the attribute: 
    //input[starts-with(@id,'txt_email_')]
//div[contains(@class,'ng-tns-') and @role='dialog']
//*[contains(@id,'_submit')]
  3. Match on a non-changing attribute — name, type, placeholder, aria-label, data-*.
  4. Relative position — Selenium 4 relative locators, or following::input[1] after a label.
  5. Ask the dev team for data-testid — the real long-term fix. Frame it as a team practice, not a personal preference.
  6. Parameterised locators in the page object so one locator serves many values: 
    private static final String ROW_ACTION =
    "//td[normalize-space()='%s']/ancestor::tr//button[@data-action='%s']";

public void rowAction(String orderId, String action) {
    driver.findElement(By.xpath(String.format(ROW_ACTION, orderId, action))).click();
}

Q77Explain StaleElementReferenceException in depth. How do you fix it properly?▼

When you call findElement, Selenium returns a reference (an internal element id) to a node in the browser's DOM at that instant. If the page then re-renders — an AJAX update, a React/Angular re-render, a page refresh, a sort/filter — the old node is discarded. Your reference now points to something that no longer exists in the DOM, so the next use throws StaleElementReferenceException.

Two flavours
  • The element was deleted from the DOM.
  • The element is no longer attached to the current document (navigation happened).
Fixes, best to worst
  1. Don't cache element references. Store By locators and find the element at the moment of use. This is why By-based page objects are more robust than eagerly-cached WebElement fields.
  2. Wait for the update to finish first — wait for the spinner to disappear or for a specific expected condition before interacting.
  3. Re-find inside a loop when iterating a list that changes: 
    int size = driver.findElements(By.cssSelector(".row")).size();
for (int i = 0; i < size; i++) {
    // re-find EVERY iteration — the list is rebuilt after each click
    WebElement row = driver.findElements(By.cssSelector(".row")).get(i);
    row.findElement(By.cssSelector(".open")).click();
    driver.navigate().back();
}
  4. Retry wrapper for genuinely racy UIs: 
    public void safeClick(By locator) {
    int attempts = 0;
    while (attempts < 3) {
        try {
            wait.until(ExpectedConditions.elementToBeClickable(locator)).click();
            return;
        } catch (StaleElementReferenceException e) {
            attempts++;                       // element re-rendered, look it up again
        }
    }
    throw new FrameworkException("Element still stale after 3 attempts: " + locator);
}
  5. ExpectedConditions.refreshed(ExpectedConditions.elementToBeClickable(locator)) — built-in staleness-tolerant wait.
Why @FindBy is less prone to this: PageFactory creates a lazy proxy that re-locates the element on each method call. It still goes stale if you hold the element across a re-render inside one method, and @CacheLookup disables that protection entirely.

Q78ElementClickInterceptedException — the click "works manually but fails in automation". How do you debug it?▼

It means the point Selenium would click is occupied by a different element. Debug in this order:

  1. Take a screenshot at the moment of failure (your listener should do this automatically). 90% of the time you'll see the culprit: a cookie consent banner, a sticky header, a toast notification, a loading overlay, or a modal backdrop that hasn't faded out.
  2. Fix the actual cause — dismiss the banner in setup (or set the cookie directly), wait for the overlay to become invisible: 
    wait.until(ExpectedConditions.invisibilityOfElementLocated(By.cssSelector(".loading-overlay")));
wait.until(ExpectedConditions.elementToBeClickable(saveBtn)).click();
  3. Scroll it into the centre of the viewport (a sticky header covers elements scrolled to the top): 
    ((JavascriptExecutor) driver).executeScript(
    "arguments[0].scrollIntoView({block:'center'});", element);
  4. JavaScript click as a last resort: 
    ((JavascriptExecutor) driver).executeScript("arguments[0].click();", element);
Say this and you'll stand out: "A JS click bypasses the browser's real event model — it fires the click even if a human could never click it, so it can hide a genuine UI bug like an overlay that never disappears. I use it only after understanding why the normal click failed, and I add a comment saying why."

Q79Explain implicit, explicit and fluent waits with code.▼
1. Implicit wait — global, DOM presence only
driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(10));

Applies to every findElement/findElements for the life of the driver. Polls until the element is present in the DOM, then returns. It cannot express visibility, clickability or text conditions.

2. Explicit wait — per element, per condition (the default choice)
WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(20));
WebElement btn = wait.until(ExpectedConditions.elementToBeClickable(By.id("pay")));
btn.click();
wait.until(ExpectedConditions.textToBe(By.id("status"), "Payment successful"));

Polls every 500ms by default and throws TimeoutException if the condition never becomes true.

3. Fluent wait — full control
Wait<WebDriver> fluent = new FluentWait<>(driver)
        .withTimeout(Duration.ofMinutes(2))          // long-running report
        .pollingEvery(Duration.ofSeconds(3))         // don't hammer the server
        .ignoring(NoSuchElementException.class)
        .ignoring(StaleElementReferenceException.class)
        .withMessage("Report never reached READY state");

WebElement report = fluent.until(d -> {
    WebElement s = d.findElement(By.id("report-status"));
    return "READY".equals(s.getText()) ? s : null;   // null/false = keep polling
});
WebDriverWait is actually a subclass of FluentWait with a fixed 500ms polling interval and NoSuchElementException pre-ignored. Saying that shows you've read the source, not just a blog.

Q80Why should you never mix implicit and explicit waits?▼

Because the two polling mechanisms interfere and produce unpredictable, non-additive timeouts. The explicit wait calls findElement internally; that call is itself subject to the implicit wait, so each polling attempt can block for the full implicit duration. The official Selenium documentation explicitly warns that this can cause waits to last far longer than either value — and in some driver versions, unexpected timing behaviour.

Example of the confusion: implicit = 10s, explicit = 15s. You might expect a failure at 15s. In practice the first internal lookup blocks for 10s, so you get roughly one or two polls in 15s and a confusing result — or a total closer to 20–30s.

My recommendation (say this): "Set the implicit wait to zero and use explicit waits exclusively, wrapped in reusable helper methods in BasePage. That gives one predictable wait strategy, self-documenting conditions, and much better failure messages."
// BasePage — one place, used everywhere
protected WebElement visible(By locator) {
    return wait.until(ExpectedConditions.visibilityOfElementLocated(locator));
}
protected WebElement clickable(By locator) {
    return wait.until(ExpectedConditions.elementToBeClickable(locator));
}
protected void click(By locator) { clickable(locator).click(); }
protected void type(By locator, String text) {
    WebElement e = visible(locator);
    e.clear();
    e.sendKeys(text);
}

  • invisibilityOfElementLocated(by) / invisibilityOfElementWithText(by, text) — for spinners

Q82Write a custom ExpectedCondition.▼
// Wait until a jQuery/AJAX-heavy page has finished all in-flight requests
public static ExpectedCondition<Boolean> pageIsQuiet() {
    return driver -> {
        JavascriptExecutor js = (JavascriptExecutor) driver;
        boolean docReady = "complete".equals(js.executeScript("return document.readyState"));
        boolean jqueryDone = (Boolean) js.executeScript(
            "return (typeof jQuery === 'undefined') || jQuery.active === 0");
        return docReady && jqueryDone;
    };
}

// Wait until a table has more than N rows AND the loader is gone
public static ExpectedCondition<Boolean> tableLoaded(By table, int minRows) {
    return new ExpectedCondition<Boolean>() {
        @Override public Boolean apply(WebDriver d) {
            return d.findElements(table).size() >= minRows
                && d.findElements(By.cssSelector(".spinner")).isEmpty();
        }
        @Override public String toString() {          // gives a readable timeout message
            return "table " + table + " to have at least " + minRows + " rows";
        }
    };
}

// usage
wait.until(pageIsQuiet());
wait.until(tableLoaded(By.cssSelector("#orders tbody tr"), 1));
Overriding toString() is the detail that separates a senior answer: it turns "Timed out after 20 seconds" into "Timed out waiting for table #orders tbody tr to have at least 1 row" — which saves hours of CI debugging.

Q85How do you handle JavaScript alerts, confirms and prompts?▼
// Always wait — the alert is asynchronous
Alert alert = new WebDriverWait(driver, Duration.ofSeconds(10))
        .until(ExpectedConditions.alertIsPresent());

String message = alert.getText();       // read the text (assert it!)
alert.accept();                         // OK
alert.dismiss();                        // Cancel (confirm boxes)
alert.sendKeys("QA Tester");            // type into a prompt, then accept()

Three types: alert (OK only), confirm (OK/Cancel), prompt (text input + OK/Cancel).

While a JS alert is open, every other WebDriver command throws UnhandledAlertException — the browser is blocked. So handle it immediately. You can also configure default behaviour: 
ChromeOptions o = new ChromeOptions();
o.setCapability("unhandledPromptBehavior", "accept");  // or "dismiss", "ignore"

Important distinction: a modal built with HTML/CSS (Bootstrap modal, custom dialog) is not a JS alert — it lives in the DOM and is handled with normal locators. Browser-level auth popups and file dialogs are neither, and need different techniques (Q93, Q105).

// Safe helper
public boolean acceptAlertIfPresent() {
    try {
        driver.switchTo().alert().accept();
        return true;
    } catch (NoAlertPresentException e) { return false; }
}

Q86How do you handle frames and iframes?▼

An iframe is a separate HTML document embedded in the page. WebDriver can only see elements in the frame it is currently focused on — this is the #1 cause of "the locator is correct in DevTools but Selenium says NoSuchElement".

// switch by index (fragile), name/id (better), or WebElement (best)
driver.switchTo().frame(0);
driver.switchTo().frame("payment-frame");
driver.switchTo().frame(driver.findElement(By.cssSelector("iframe[title='Card details']")));

// safest — waits for the frame to exist AND switches in one step
new WebDriverWait(driver, Duration.ofSeconds(15)).until(
    ExpectedConditions.frameToBeAvailableAndSwitchToIt(By.id("payment-frame")));

// do the work inside the frame
driver.findElement(By.id("cardNumber")).sendKeys("4111111111111111");

// come back out — MANDATORY
driver.switchTo().defaultContent();     // back to the top-level document
driver.switchTo().parentFrame();        // up exactly one level (nested frames)

// how many frames on the page?
int count = driver.findElements(By.tagName("iframe")).size();
Nested frames: you must switch level by level — frame("outer") then frame("inner"). You cannot jump directly. And you cannot switch from one sibling frame to another without going back to defaultContent() first.
Good framework practice: wrap it so a test never forgets to switch back. 
public <T> T inFrame(By frame, Supplier<T> action) {
    wait.until(ExpectedConditions.frameToBeAvailableAndSwitchToIt(frame));
    try   { return action.get(); }
    finally { driver.switchTo().defaultContent(); }
}
// usage:  inFrame(By.id("pay"), () -> { cardField.sendKeys("4111..."); return null; });

Q87How do you handle multiple windows and tabs?▼
String parent = driver.getWindowHandle();          // current window's unique id (String)

driver.findElement(By.linkText("Terms & Conditions")).click();   // opens a new tab

// Wait for the new window rather than sleeping
new WebDriverWait(driver, Duration.ofSeconds(10))
        .until(ExpectedConditions.numberOfWindowsToBe(2));

Set<String> all = driver.getWindowHandles();       // Set — unique, unordered
for (String handle : all) {
    if (!handle.equals(parent)) {
        driver.switchTo().window(handle);
        break;
    }
}
Assert.assertTrue(driver.getTitle().contains("Terms"));
driver.close();                                     // close only the child
driver.switchTo().window(parent);                   // ALWAYS switch back explicitly
Selenium 4 — open a tab/window yourself
driver.switchTo().newWindow(WindowType.TAB);     // opens AND switches focus
driver.get("https://example.com/help");
driver.close();
driver.switchTo().window(parent);
Two traps: (1) after driver.close() the driver still points at the dead window — any command throws NoSuchWindowException until you switch. (2) getWindowHandles() returns a Set, so it has no guaranteed order — never assume the last element is the newest. Compare against the stored parent handle.

Q88Explain the Actions class — mouse interactions.▼

Actions builds a chain of low-level input events (the W3C Actions API) and dispatches them with .perform(). Used for anything a simple .click() cannot do.

Actions actions = new Actions(driver);

actions.moveToElement(menu).perform();                       // hover
actions.contextClick(row).perform();                         // right click
actions.doubleClick(cell).perform();
actions.clickAndHold(source).moveToElement(target).release().perform();
actions.dragAndDrop(source, target).perform();               // convenience method
actions.dragAndDropBy(slider, 120, 0).perform();             // offset drag (sliders)
actions.moveToElement(el, 10, 10).click().perform();         // click at an offset

// Multi-step chain: hover a menu, then click a submenu item
actions.moveToElement(driver.findElement(By.id("products")))
       .pause(Duration.ofMillis(300))            // let the CSS animation settle
       .moveToElement(driver.findElement(By.linkText("Laptops")))
       .click()
       .build().perform();
Very common real-world issue: HTML5 drag-and-drop (using the native dragstart/drop events) frequently does not work with Actions.dragAndDrop, because the browser's native DnD is not driven by synthetic mouse events. The standard workaround is a JavaScript-based DnD simulation, or the newer clickAndHold → moveByOffset (small steps) → release sequence with pauses. Mentioning this shows real project experience.

build() composes the chain into a single action; perform() executes it. Calling perform() directly implies build().

Q90What is JavaScriptExecutor and when do you use it?▼

JavascriptExecutor runs JavaScript directly in the browser context. arguments[0] maps to the first extra parameter you pass.

JavascriptExecutor js = (JavascriptExecutor) driver;

js.executeScript("arguments[0].click();", element);                  // click through overlays
js.executeScript("arguments[0].value='QA';", input);                 // set value directly
js.executeScript("arguments[0].scrollIntoView({block:'center'});", el);
js.executeScript("window.scrollBy(0,500);");
js.executeScript("window.scrollTo(0, document.body.scrollHeight);"); // scroll to bottom
js.executeScript("arguments[0].style.border='3px solid red';", el);  // highlight for reports
js.executeScript("arguments[0].setAttribute('value','2026-03-15');", dateInput);
js.executeScript("arguments[0].removeAttribute('readonly');", el);

String title  = (String)  js.executeScript("return document.title;");
String state  = (String)  js.executeScript("return document.readyState;");
Long   height = (Long)    js.executeScript("return document.body.scrollHeight;");
Boolean done  = (Boolean) js.executeScript("return jQuery.active == 0;");

js.executeScript("window.open('https://example.com','_blank');");
js.executeScript("localStorage.setItem('token', arguments[0]);", jwt);  // skip UI login!
The judgement question — "so should you always use JS click?" No. JS bypasses the browser's real event pipeline: it will click a disabled, hidden or covered element, and it does not fire the focus/blur/mouseover events a real user triggers. That means your test can pass while the feature is broken for users. Rule: use JS only for things a user cannot do anyway (scrolling into view, highlighting for reports, seeding localStorage), and treat a JS click as a documented workaround, never a default.

public static Path waitForDownload(Path dir, String extension, Duration timeout) {
    long end = System.currentTimeMillis() + timeout.toMillis();
    while (System.currentTimeMillis() < end) {
        try (Stream<Path> files = Files.list(dir)) {
            Optional<Path> done = files
                .filter(p -> p.toString().endsWith(extension))
                .filter(p -> !p.toString().endsWith(".crdownload"))  // Chrome partial file
                .max(Comparator.comparingLong(p -> p.toFile().lastModified()));
            if (done.isPresent() && done.get().toFile().length() > 0) return done.get();
        } catch (IOException ignored) { }
    }
    throw new FrameworkException("No " + extension + " downloaded within " + timeout);
}

    // navigate month/year until the header matches
    String wanted = target.format(DateTimeFormatter.ofPattern("MMMM yyyy"));
    for (int guard = 0; guard < 36; guard++) {            // guard against infinite loops

        boolean forward = YearMonth.parse(shown, MONTH_YEAR).isBefore(YearMonth.from(target));
        click(By.cssSelector(forward ? ".dp-next" : ".dp-prev"));

  "arguments[0].dispatchEvent(new Event('change',{bubbles:true}));", input, "2026-03-15");

public static WebDriver create(String browser, boolean headless) {

Key insight to state: anything drawn by the browser chrome rather than the page cannot be located with WebDriver — notification prompts, the print dialog, the OS file picker, the download bar. You must prevent them via options/preferences, or drive them with CDP / Robot / AutoIT.

Q106How do you handle Shadow DOM elements?▼

Web components (Polymer, Lit, Salesforce Lightning, and native <video> controls) encapsulate their internals in a shadow root. A normal XPath/CSS from the document cannot pierce it — this is a very common "my locator works in DevTools but not in Selenium" cause.

// Selenium 4.x native API (open shadow roots only)
WebElement host = driver.findElement(By.cssSelector("my-app"));
SearchContext shadow = host.getShadowRoot();
WebElement inner = shadow.findElement(By.cssSelector("#login-btn"));
inner.click();

// Nested shadow roots — chain them
WebElement lvl2 = host.getShadowRoot()
        .findElement(By.cssSelector("app-header")).getShadowRoot()
        .findElement(By.cssSelector("button.menu"));

// Pre-4.0 / fallback: JavaScript
WebElement el = (WebElement) ((JavascriptExecutor) driver).executeScript(
    "return document.querySelector('my-app').shadowRoot.querySelector('#login-btn');");
Closed shadow roots (mode: 'closed') cannot be accessed at all — not by Selenium, not by JavaScript from outside. If a team ships closed shadow roots, the only path is asking developers to expose test hooks. Note that Playwright pierces open shadow DOM automatically with its normal CSS/text selectors — a genuine advantage worth mentioning if they ask "why would you pick Playwright?"

Important detail: getText() returns only the rendered, visible text. For an element with display:none it returns an empty string, which silently makes assertions pass or fail for the wrong reason. Use getAttribute("textContent") or getAttribute("innerText") when you deliberately need hidden text.

Q108How would you find all broken links on a page?▼

A classic practical exercise. Selenium finds the links; a plain HTTP client checks the status codes (do not navigate to each link with the browser — it would take forever).

List<WebElement> links = driver.findElements(By.tagName("a"));
List<String> broken = new ArrayList<>();

Set<String> urls = links.stream()
        .map(l -> l.getAttribute("href"))
        .filter(Objects::nonNull)
        .filter(h -> h.startsWith("http"))          // skip mailto:, tel:, javascript:, #
        .collect(Collectors.toCollection(LinkedHashSet::new));   // dedupe

for (String url : urls) {
    HttpURLConnection conn = (HttpURLConnection) new URL(url).openConnection();
    conn.setRequestMethod("HEAD");                  // HEAD is enough — no body downloaded
    conn.setConnectTimeout(5000);
    conn.setReadTimeout(5000);
    conn.connect();
    int code = conn.getResponseCode();
    if (code >= 400) broken.add(url + " -> " + code + " " + conn.getResponseMessage());
    conn.disconnect();
}
Assert.assertTrue(broken.isEmpty(), "Broken links found:\n" + String.join("\n", broken));
Improvements to mention: run the checks in a thread pool (ExecutorService) because they are I/O bound; treat 401/403 as "protected, not broken"; follow redirects deliberately; and also validate <img src>, <script src> and <link href> the same way.

Q109How do you handle CAPTCHA and OTP in automation?▼

The correct answer is you don't automate them — you remove the blocker with the team's help. Trying to "solve" a CAPTCHA defeats its purpose and is unreliable.

CAPTCHA
  • Ask dev/DevOps to disable CAPTCHA in non-production environments, or whitelist the test environment/IP. This is the standard industry practice.
  • Use a test key — reCAPTCHA provides official test site/secret keys that always pass in test environments.
  • Bypass via an API-based login for all other tests, keeping one manual test for the CAPTCHA itself.
  • Third-party solving services exist but are slow, cost money, and are a poor engineering answer in an interview.
OTP / 2FA
  • Use a fixed test OTP (e.g. 000000) enabled for test accounts in lower environments — the most common real solution.
  • Fetch the OTP from a backend API / test endpoint, or query the database directly with JDBC.
  • Read it from a test mail service (Mailinator, MailHog, Mailosaur API) or an SMS sandbox (Twilio test credentials).
  • For TOTP-based 2FA, generate the code in the test from the shared secret using a library (e.g. totp-java) — this is fully legitimate and impressive to mention.
Frame it as a conversation, not a hack: "I raise testability as a requirement during refinement. A feature that cannot be tested in a lower environment isn't 'done' — and the team agreed to a test-mode flag for exactly that reason."

Q110What are Selenium 4 relative locators?▼

They locate an element by its visual position relative to another element, using the browser's rendered box coordinates rather than the DOM structure.

import static org.openqa.selenium.support.locators.RelativeLocator.with;

WebElement password = driver.findElement(with(By.tagName("input")).below(By.id("email")));
WebElement submit   = driver.findElement(with(By.tagName("button")).below(By.id("password")));
WebElement label    = driver.findElement(with(By.tagName("label")).toLeftOf(By.id("qty")));
WebElement helpIcon = driver.findElement(with(By.tagName("svg")).toRightOf(By.id("qty")));
WebElement nearby   = driver.findElement(with(By.tagName("input")).near(By.id("label"), 60));

// chainable
WebElement cell = driver.findElement(
    with(By.tagName("td")).below(By.id("header-status")).toRightOf(By.id("cell-id")));

Five methods: above(), below(), toLeftOf(), toRightOf(), near() (default 50px, overloadable).

Be honest about the limitations — that's what a senior candidate does. They depend on the rendered layout, so they break on responsive re-flow, different screen sizes, and headless-vs-headed rendering differences. They are also slower (Selenium injects JS to compute rectangles). I treat them as a fallback for legacy pages with no usable attributes, not as a primary strategy.

Q111What can you do with Chrome DevTools Protocol (CDP) in Selenium 4?▼
DevTools devTools = ((ChromeDriver) driver).getDevTools();
devTools.createSession();

// 1. Capture browser console errors during the test
devTools.send(Log.enable());
devTools.addListener(Log.entryAdded(), entry ->
    logger.warn("CONSOLE {}: {}", entry.getLevel(), entry.getText()));

// 2. Simulate a slow 3G network — test loaders and timeouts realistically
devTools.send(Network.enable(Optional.empty(), Optional.empty(), Optional.empty()));
devTools.send(Network.emulateNetworkConditions(
        false, 200, 250_000, 100_000, Optional.of(ConnectionType.CELLULAR3G)));

// 3. Block requests (e.g. analytics/ads) to speed tests up and remove flakiness
devTools.send(Network.setBlockedURLs(List.of("*google-analytics.com*", "*.gif")));

// 4. Mock geolocation
devTools.send(Emulation.setGeolocationOverride(
        Optional.of(12.9716), Optional.of(77.5946), Optional.of(1)));

// 5. Intercept & stub a network response (mock the backend from the UI test)
devTools.send(Fetch.enable(Optional.empty(), Optional.empty()));
devTools.addListener(Fetch.requestPaused(), req -> { /* fulfil with stub JSON */ });

// 6. Capture all requests/responses for API-level assertions from a UI test
devTools.addListener(Network.responseReceived(),
        r -> logger.info("{} {}", r.getResponse().getStatus(), r.getResponse().getUrl()));

// 7. Basic auth & device emulation
devTools.send(Emulation.setDeviceMetricsOverride(390, 844, 3, true, Optional.empty(), ...));
Important caveat to state: CDP is Chromium-only and version-bound — Selenium ships versioned CDP packages, so an upgrade can break your code. That is precisely why Selenium is moving toward the cross-browser WebDriver BiDi standard, and why Playwright (built on CDP-style bi-directional communication from day one) does these things more naturally.

Q112How do you validate something in the backend from a UI test — API and database checks?▼

This is a grey-box question that separates a "clicker" from an SDET. A UI assertion alone can pass while the data is wrong.

// UI action
checkoutPage.placeOrder();
String orderId = confirmationPage.getOrderId();   // e.g. ORD-2026-0042

// 1. API verification — the order really exists with the right total
Response res = RestAssured.given()
        .header("Authorization", "Bearer " + token)
        .get(baseUrl + "/api/orders/" + orderId);
res.then().statusCode(200)
   .body("status", equalTo("CONFIRMED"))
   .body("totalAmount", equalTo(1499.00f));

// 2. Database verification — the row and the audit trail
try (Connection con = DriverManager.getConnection(url, user, pass);
     PreparedStatement ps = con.prepareStatement(
         "SELECT status, total_amount FROM orders WHERE order_ref = ?")) {
    ps.setString(1, orderId);
    try (ResultSet rs = ps.executeQuery()) {
        Assert.assertTrue(rs.next(), "Order row missing in DB for " + orderId);
        Assert.assertEquals(rs.getString("status"), "CONFIRMED");
        Assert.assertEquals(rs.getBigDecimal("total_amount"),
                            new BigDecimal("1499.00"));
    }
}
Also mention: use a read-only DB user for tests, always use PreparedStatement (never string concatenation), close resources with try-with-resources, and keep credentials in environment variables / a secrets manager — never in the repo. Those four points get remembered.

Q113Your Selenium suite takes 4 hours. How do you make it fast?▼

Answer as an ordered plan — measure first, then optimise.

  1. Measure. Get per-test durations from the TestNG/Allure report and find the top 20 slowest tests. Optimise those, not everything.
  2. Parallelise. TestNG parallel="methods" with a thread count matched to CPU/grid capacity. This alone often gives 4–8×. Prerequisite: ThreadLocal driver and fully independent tests.
  3. Kill all Thread.sleep() and replace with explicit waits. In most legacy suites this is 30–50% of the runtime.
  4. Skip the UI for setup. Log in via API + cookie injection; create the test data via API instead of clicking through wizards. Typically saves 5–15s per test.
  5. Push tests down the pyramid. Field validations and error messages become API/component tests; only journeys stay in the UI layer.
  6. Run headless and use PageLoadStrategy.EAGER; block analytics/ads/third-party scripts via CDP.
  7. Split the suite — a <10 minute smoke set on every commit, the full regression nightly. Tag with TestNG groups.
  8. Scale horizontally with a Docker Grid or a cloud provider; shard tests across CI agents.
  9. Remove duplication — audit for tests that assert the same thing through different paths.
  10. Fix the flaky ones instead of retrying them; retries hide problems and double the runtime of failing tests.
Quantify it if you can: "We took our regression from 3h 40m to 34 minutes: parallelism 8×, API-based login, and moving 120 validation checks to the API layer." Numbers are what interviewers remember.

Q114What makes tests flaky, and how do you eliminate flakiness?▼
Root causeFix
Fixed sleeps / no waitsExplicit waits on conditions, never on time
Waiting for presence instead of readinessWait for elementToBeClickable, spinner invisibility, or a specific text
Test order dependency / shared dataEvery test creates and cleans its own data; unique identifiers per run
Shared static driver in parallel runsThreadLocal<WebDriver>
Brittle locators (index-based, absolute XPath, generated ids)data-testid attributes, semantic locators
Animations & transitionsWait for the animation-end state; or disable CSS animations in test builds
Third-party dependencies (ads, analytics, payment sandbox)Block or stub them via CDP/proxy
Environment instability, slow CI agentsRight-size timeouts for CI, containerise, monitor agent health
Date/time and timezone assumptionsRelative dates, fixed timezone in browser options, avoid "today" boundary cases
Stale element on re-renderRe-find elements; don't cache WebElements across actions
Process, not just code
  • Quarantine — move a flaky test out of the blocking pipeline into a separate suite with an owner and a due date. Never let it just get retried forever.
  • Track flakiness as a metric (pass rate over the last 20 runs) and treat <98% as a bug with a ticket.
  • Rerun-failed is a diagnostic, not a cure — I use IRetryAnalyzer but I report retried tests distinctly so they cannot be silently ignored.
This is one of the highest-value questions for a 5-year candidate. Having a clear, opinionated flakiness policy is exactly what a lead is listening for.
