What I actually test on an API

Happy path + status code; response schema and data types; field-level validation (missing, null, wrong type, too long, boundary); authentication and — critically — authorisation (user A must get 403 when reading user B's order); pagination and sorting; idempotency and duplicate submission; rate limiting; error message quality and that stack traces are not leaked; response time; and backward compatibility of the contract.

Q192Explain API authentication types and how you handle tokens in tests.▼
  • Basic auth — Authorization: Basic base64(user:pass). Simple, must be over HTTPS.
  • API key — a static key in a header or query param. Identifies the app, not the user.
  • Bearer token / JWT — Authorization: Bearer eyJhbGci…. A JWT has three dot-separated parts: header.payload.signature. The payload is only Base64-encoded, not encrypted — so you can decode it in a test to assert claims (sub, exp, role), and you should verify the app never puts sensitive data in it.
  • OAuth 2.0 — token issued by an authorisation server. Grant types: authorization code (+PKCE) for user-facing apps, client credentials for machine-to-machine (the one you usually automate).
  • Session cookie — traditional server-side session.
Handling tokens in a test framework
// Fetch once, cache, and refresh when it expires — not per test
public static synchronized String token() {
    if (cached == null || Instant.now().isAfter(expiry.minusSeconds(60))) {
        Response r = given().contentType(JSON)
            .body(Map.of("client_id", id, "client_secret", secret,
                         "grant_type", "client_credentials"))
            .post(authUrl + "/oauth/token");
        cached = r.jsonPath().getString("access_token");
        expiry = Instant.now().plusSeconds(r.jsonPath().getInt("expires_in"));
    }
    return cached;
}

Security tests to mention: expired token → 401; tampered signature → 401; token from user A used on user B's resource → 403; token still valid after logout (it shouldn't be); token visible in URL or browser logs (it shouldn't be).

Q193SQL a tester must know — joins, aggregates, and the classic puzzle questions.▼
-- JOINS
SELECT o.order_ref, c.name, o.total
FROM orders o
INNER JOIN customers c ON c.id = o.customer_id      -- only matching rows
LEFT  JOIN payments  p ON p.order_id = o.id         -- all orders, payment if it exists
WHERE p.id IS NULL;                                  -- orders with NO payment (a real bug hunt)

-- Aggregation:  WHERE filters rows BEFORE grouping, HAVING filters groups AFTER
SELECT status, COUNT(*) AS cnt, SUM(total) AS revenue
FROM orders
WHERE created_at >= CURRENT_DATE - INTERVAL '7 days'
GROUP BY status
HAVING COUNT(*) > 10
ORDER BY revenue DESC;

-- Find duplicates (a data-integrity test)
SELECT email, COUNT(*) FROM customers GROUP BY email HAVING COUNT(*) > 1;

-- 2nd highest salary — the classic interview question, three ways
SELECT MAX(salary) FROM employees WHERE salary < (SELECT MAX(salary) FROM employees);

SELECT DISTINCT salary FROM employees ORDER BY salary DESC LIMIT 1 OFFSET 1;

SELECT salary FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk FROM employees
) t WHERE rnk = 2;

-- Nth highest per department (window function)
SELECT * FROM (
  SELECT e.*, DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) rnk
  FROM employees e
) x WHERE rnk <= 3;

-- Useful for test data
SELECT * FROM orders WHERE status IN ('NEW','PAID') AND total BETWEEN 100 AND 500;
SELECT * FROM customers WHERE email LIKE '%@test.com';
SELECT COALESCE(nickname, name) FROM customers;      -- NULL handling
DELETE FROM orders WHERE order_ref LIKE 'AUTOTEST-%';  -- cleanup
Two things interviewers check: (1) WHERE vs HAVING — filtering before vs after GROUP BY; (2) that you understand NULL never equals anything, so WHERE col = NULL returns nothing — you need IS NULL. Also: use a read-only account, and never run an UPDATE/DELETE without a WHERE on a shared environment.

Q194"Tell me about yourself." How do you structure the answer and your project introduction?▼

This is the highest-leverage 3 minutes of the interview and the one candidates prepare least. Use Present → Past → Why here, and end on your strongest technical asset.

Template (adapt with your own numbers)

"I'm a test automation engineer with about five years' experience, currently working on [domain — e.g. an e-commerce platform] at [company]. I own the UI and API automation for the [checkout and payments] modules.

Day to day I work in a Scrum team of [8]: I join refinement to shape acceptance criteria, write and automate the regression tests, and maintain our framework — Java, Selenium 4, TestNG, Maven, Page Object Model, running in parallel on a Docker Grid through Jenkins. Over the last year I've also built out our Playwright/TypeScript suite for the new front end.

The thing I'm proudest of is [cutting regression from 3h40 to 34 minutes by introducing parallel execution and replacing UI logins with API-based authentication] — that let the team move from weekly to twice-weekly releases.

Before this I was at [X] doing [manual + automation], which is where I learned [test design, domain]. I'm looking to move because [I want to work on a product with a stronger engineering culture / deeper CI-CD maturity / a bigger scale challenge], and this role stood out because [specific thing about their job description]."

Rules
  • Two to three minutes. Practise it out loud until it needs no thinking.
  • Include at least one number — runtime, coverage, defects caught, release frequency.
  • Only mention technologies you can defend for ten minutes. Everything you name is a licence for them to dig.
  • Do not narrate your CV chronologically from college. Start from now.
  • End by connecting to their role — it shows you read the job description.

Q195"Tell me about the biggest challenge you faced." How do you structure behavioural answers?▼

Use STAR: Situation (context, 2 sentences) → Task (your specific responsibility) → Action (what you did — most of the answer) → Result (measurable outcome + what you learned).

Worked example

Situation: "Our regression suite had a 60% pass rate on any given night. The team had stopped looking at the results, so failures were being ignored and two real regressions reached production in one quarter."

Task: "I took ownership of suite reliability for that quarter, alongside my sprint work."

Action: "I started by measuring instead of guessing — I ran the suite 20 times and classified every failure: 40% were fixed sleeps and presence-only waits, 30% were test-data collisions between parallel threads, 20% were a shared static WebDriver, and 10% were genuine product bugs. I fixed them in that order: replaced every sleep with condition-based explicit waits, moved data creation into each test through the API with unique identifiers, and moved the driver to a ThreadLocal factory. I also introduced a quarantine policy — a test that fails twice for non-product reasons leaves the blocking pipeline with a named owner and a deadline."

Result: "Pass rate went from 60% to 98%, and because the team trusted it again we were able to make the smoke suite a merge gate. Escaped regressions dropped to zero over the following two quarters. What I took away is that trust is the real product of a test suite — coverage means nothing if nobody believes the result."

Prepare three STAR stories in advance: a technical challenge, a conflict/collaboration story, and a failure/mistake story. Almost every behavioural question is a variation of one of those three.

Q196"A developer rejects your bug saying it works on their machine." What do you do?▼

They are testing your collaboration and evidence discipline, not your debugging skill. Never answer with "I escalate to my manager" as the first step.

  1. Assume good faith and check yourself first. Re-read the requirement — is my expected result actually right? Re-run on a clean environment with the exact build.
  2. Strengthen the evidence. Exact build number, environment, browser and version, user role, test data, timestamp, screenshot/video, browser console error, network HAR, server log with the correlation ID. Most "works on my machine" disputes die the moment you attach a request/response pair.
  3. Reproduce together. A 10-minute screen share resolves more than a day of ticket comments. Often it turns out to be an environment, data, cache or feature-flag difference — which is itself a finding worth fixing.
  4. Separate the fact from the judgement. "The behaviour is X, the requirement says Y" is a fact. Whether it's a defect or a requirement gap is a decision — take that to the BA/PO, not to a debate.
  5. Escalate only with data, and framed as risk to the release, never as a personal complaint.
Close with: "I try to make the bug report so complete that there's nothing left to argue about. If I'm proven wrong, I say so quickly — that's how I keep the credibility I need for the times I'm right."

Q197"The release is tomorrow, testing isn't complete, and there are open bugs. What do you do?"▼

The wrong answers: "I'd work overnight and finish everything" (unrealistic, and signals poor planning) or "I'd block the release" (QA doesn't own that decision).

  1. Re-prioritise by risk immediately. Cover the critical revenue paths and the areas that actually changed. Explicitly deprioritise low-risk, unchanged areas.
  2. Present the facts, not feelings. A short written summary: what was tested, what wasn't, the open defect list with severity and workaround status, and the specific risk of shipping each one. "If we ship, users on Safari cannot complete UPI payments — that's roughly 12% of transactions."
  3. Offer options rather than a veto: ship with the feature behind a flag / disabled; ship to a canary segment first; ship without the risky module; delay 24 hours; ship with a documented known-issue and a hotfix plan.
  4. Let the business decide, and record the decision. The PO owns go/no-go. My job is to make sure they decide with full information, and that the decision is written down.
  5. Follow up after release — monitor error rates, be ready with the rollback, and raise the underlying planning problem in the retro so it doesn't repeat.
Say the principle out loud: "QA's job is to make risk visible, not to make the release decision alone." That single sentence is what a hiring manager is listening for.

Q198"How do you keep your skills current?" and "What's your weakness?"▼
Keeping current — be specific, not generic

Name actual sources and actual outputs: the official Selenium and Playwright release notes and docs, the Ministry of Testing community, specific newsletters/blogs, conference talks, and — most importantly — something you built. "I maintain a personal GitHub repo where I rebuild our framework patterns from scratch; last month I added CDP network mocking and a Playwright visual-regression pilot." A public repo is worth more than a list of blogs you read.

Weakness — the honest formula

Pick a real weakness that is not core to the job, then show the concrete action you're taking and the progress made. Avoid the fake ones ("I'm a perfectionist", "I work too hard") — experienced interviewers discount them immediately.

Good examples: "My performance-testing depth is shallower than my functional automation. I've been working through JMeter and k6 on a side project and ran our first baseline load test last quarter, but I'd still ask for support on a serious performance programme." Or: "Early on I over-automated — I built UI tests for things that belonged at the API layer, and I paid for it in maintenance. Now I consciously ask 'what is the cheapest layer that can catch this bug?' before writing a test."

Q199"Why are you leaving?", "Where do you see yourself in 5 years?", and salary questions.▼
Why are you leaving?

Never criticise your current employer, manager or colleagues — it is the fastest way to lose an offer. Frame it as moving towards something: "I've automated our regression to a good level and the work has become steady maintenance. I'm looking for a role with more scale and more CI/CD depth, where I can also mentor — which is what attracted me to this position."

Five years

Show ambition in the direction of the role, not away from it. "I'd like to grow into an SDET/lead position — owning quality strategy across teams, mentoring juniors, and being more involved in architecture and shift-left practices. I want to stay technical rather than move into pure people management." Avoid "I want to become a manager in 2 years" if the role has no such path, and avoid "I want to move into development" — it tells them you'll leave.

Salary
  • Research the market range for your years, stack and city before the interview.
  • If asked early, deflect politely once: "I'd like to understand the role and responsibilities a bit better first — but I'm confident we can align if the fit is right. Could you share the band for this position?"
  • If pressed, give a range anchored to research, with the bottom of the range being a number you'd genuinely accept.
  • Speak in total compensation (fixed + variable + benefits), and never inflate your current salary — offer letters get verified.

Q200Rapid-fire scenario questions — practise these out loud.▼
ScenarioKey points in a strong answer
"How would you test a pen / a lift / an ATM?"Ask clarifying questions first, then answer in categories: functional, usability, boundary/limits, safety/security, performance, environment, accessibility, negative. They're testing your structure, not the pen.
"You have 100 test cases and 1 hour."Risk-rank; run critical business paths and the areas that changed; communicate what wasn't covered in writing.
"Requirements are missing/unclear. How do you test?"Talk to the PO/BA and users; use the existing behaviour, comparable products and domain knowledge as an oracle; do exploratory sessions; document assumptions and get them confirmed; log requirement gaps as defects.
"A test that passed for months suddenly fails."Check first whether it's a genuine product regression (most likely), then environment/data change, dependency upgrade, or a hidden timing assumption that finally lost the race. Bisect against the last good build.
"How would you test an application with no UI?"API/contract testing, DB validation, message queue/event verification, log assertions, scheduled-job outputs, CLI-level testing.
"Would you automate 100% of tests?"No — explain ROI, exploratory/usability value, churn cost, and the "what can't be automated" list (Q34).
"How do you test a payment flow safely?"Sandbox gateway with test card numbers, never real cards; test decline/timeout/3DS/partial refund; verify idempotency on double submit; check that no PAN/CVV is logged; reconcile against the DB and the gateway's report.
"Your manager asks you to mark a failing test as skipped to make the build green."Push back with data and offer the alternative: quarantine with an owner and a ticket, or a documented known-issue. Never silently disable. Escalate transparently, not confrontationally.
"How do you onboard a junior tester?"Pair on real tickets; give them a small, safe area to own; code review with explanations rather than corrections; a written framework README and a "first week" checklist.
"What would you improve about your current framework?"Have a real, specific answer ready — it shows self-awareness. E.g. "test data is still partly shared; I'd move fully to per-test API seeding" or "our reporting has no historical trend; I'd add Allure or a dashboard."
For every scenario question: ask a clarifying question first, then answer in a structure, then state a trade-off. That three-part shape works for anything they invent.
