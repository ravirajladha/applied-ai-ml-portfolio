SECTION 7

Appium & Mobile Automation

Q201 – Q215 · Asked in almost every product-company automation interview, even for web-first roles. You are not expected to be an expert — you are expected to know the architecture, the locator strategies, and why mobile is harder than web.

Q201What is Appium and how does its architecture work?▼

Appium is an open-source tool for automating native, hybrid and mobile-web apps on Android and iOS, using the same W3C WebDriver protocol as Selenium.

  1. Your test creates an AndroidDriver/IOSDriver with a set of capabilities.
  2. The client sends HTTP/JSON commands to the Appium server (Node.js, default port 4723).
  3. The server routes them to the right platform driver: UiAutomator2 for Android, XCUITest for iOS.
  4. That driver talks to the vendor's own automation framework on the device — via ADB and a bootstrap agent on Android, via WebDriverAgent on iOS.
  5. The action executes on the real device or emulator and the result travels back up the same chain.
Why teams choose it
  • Cross-platform — one API and often one test codebase for Android and iOS.
  • No app modification — you test the same binary you ship; no SDK to embed.
  • Any language that has a WebDriver client (Java, Python, JS, C#, Ruby).
  • Reuses your Selenium knowledge — waits, page objects, TestNG, reporting all carry over.
The sentence that lands: "Appium is WebDriver for mobile. My framework layers — driver factory, page objects, waits, listeners, reporting — were reused as-is; I only added a mobile driver factory and mobile locators."

The appium: prefix trips people up constantly. Standard W3C capabilities (platformName, browserName) need no prefix; everything vendor-specific (appium:app, appium:deviceName, appium:automationName) does. The typed Options classes add it for you, which is why they are the recommended approach.

Q203What locator strategies does Appium support?▼
StrategyExampleNotes
Accessibility IDAppiumBy.accessibilityId("cart_button")Best choice. Maps to content-desc on Android and accessibilityIdentifier on iOS — so one locator works on both platforms, and it doubles as an accessibility check
IDAppiumBy.id("com.example.shop:id/btn_pay")Android resource-id; fast and stable
Class nameAppiumBy.className("android.widget.Button")Rarely unique on its own
XPath//android.widget.TextView[@text='Checkout']Works everywhere but is the slowest on mobile — the driver serialises the whole view hierarchy for each query
Android UiAutomatorAppiumBy.androidUIAutomator("new UiSelector().text(\"Pay\")")Native and fast; supports UiScrollable for scrolling to an element
iOS PredicateAppiumBy.iOSNsPredicateString("label == 'Pay' AND visible == 1")Fast, expressive
iOS Class ChainAppiumBy.iOSClassChain("**/XCUIElementTypeButton[`label == 'Pay'`]")Between XPath and predicate in power, much faster than XPath
// Scroll to an element that is off-screen — the idiomatic Android way
driver.findElement(AppiumBy.androidUIAutomator(
    "new UiScrollable(new UiSelector().scrollable(true))"
  + ".scrollIntoView(new UiSelector().text(\"Order history\"))")).click();
The senior answer to "which do you prefer": "Accessibility ID first, because a single locator works on both platforms and it forces the app to be accessible. XPath last, because on mobile it is genuinely slow — the driver dumps the entire view hierarchy on every lookup, which on a long list can take seconds."

Q204Native vs Hybrid vs Mobile web apps — and how do you switch context?▼
  • Native — built with the platform SDK (Kotlin/Java, Swift/Objective-C). Best performance and full device access. Automated entirely through the native context.
  • Hybrid — a native shell wrapping a WebView that renders HTML/JS (Cordova, Ionic, Capacitor). Automating it needs context switching.
  • Mobile web — a normal website in the phone's browser. Automated with Appium driving Chrome/Safari, using ordinary web locators.
  • (Worth naming: React Native / Flutter — they render native components, so they're treated as native, though Flutter needs a dedicated driver.)
Set<String> contexts = driver.getContextHandles();
// [ "NATIVE_APP", "WEBVIEW_com.example.shop" ]

for (String context : contexts) {
    if (context.contains("WEBVIEW")) {
        driver.context(context);              // switch into the web view
        break;
    }
}
driver.findElement(By.cssSelector("#promo-code")).sendKeys("SAVE20");   // web locators now

driver.context("NATIVE_APP");                 // switch back — always switch back
Two classic hybrid problems: (1) the WebView context appears only after the web content has loaded, so you must wait for it rather than reading the handles immediately; (2) Android requires the app to be built with setWebContentsDebuggingEnabled(true), otherwise the WebView is invisible to Appium — a request you have to make to the developers.

Q205How do you perform mobile gestures — tap, swipe, scroll, long press, pinch?▼

Appium 2 uses the W3C Actions API (the old TouchAction class is deprecated). You build a pointer sequence.

PointerInput finger = new PointerInput(PointerInput.Kind.TOUCH, "finger");

// --- Tap ---
Sequence tap = new Sequence(finger, 0)
    .addAction(finger.createPointerMove(Duration.ZERO, viewport(), x, y))
    .addAction(finger.createPointerDown(PointerInput.MouseButton.LEFT.asArg()))
    .addAction(finger.createPointerUp(PointerInput.MouseButton.LEFT.asArg()));
driver.perform(List.of(tap));

// --- Swipe up (scroll down the screen) ---
Dimension size = driver.manage().window().getSize();
int startX = size.width / 2, startY = (int) (size.height * 0.8), endY = (int) (size.height * 0.2);
Sequence swipe = new Sequence(finger, 1)
    .addAction(finger.createPointerMove(Duration.ZERO, viewport(), startX, startY))
    .addAction(finger.createPointerDown(0))
    .addAction(finger.createPointerMove(Duration.ofMillis(600), viewport(), startX, endY))
    .addAction(finger.createPointerUp(0));
driver.perform(List.of(swipe));

// --- Long press: same as tap, with a pause between down and up ---
    .addAction(new Pause(finger, Duration.ofSeconds(2)))

// --- The pragmatic shortcut: mobile: commands (fast and readable) ---
driver.executeScript("mobile: swipe", Map.of("direction", "up"));
driver.executeScript("mobile: scroll", Map.of("strategy", "accessibility id", "selector", "Pay"));
driver.executeScript("mobile: longClickGesture", Map.of("elementId",
        ((RemoteWebElement) el).getId(), "duration", 2000));
driver.executeScript("mobile: pinchCloseGesture", Map.of("percent", 0.75));
Mention mobile: execute-script commands — they are the modern, driver-native way and far less code than hand-building pointer sequences. Candidates who only know the deprecated TouchAction immediately date themselves.

My strategy: emulators for the bulk of functional regression in CI (cheap and parallelisable), a small set of real devices for the release candidate covering the top handsets in our analytics, and a cloud farm for the long tail of OS/OEM combinations plus anything needing real network conditions.

Anchor it in data: "We pulled the device/OS distribution from our analytics and covered the models representing 80% of our users, rather than guessing." That is exactly the risk-based thinking they want.

Q207What test scenarios are unique to mobile apps that don't exist on web?▼

This is the question that separates people who have really tested mobile from people who have only read about Appium.

  • Interrupts — incoming call, SMS, alarm, push notification, or another app taking focus mid-transaction. Does state survive?
  • App lifecycle — background the app, kill it from recents, relaunch. Is the session preserved? Is the cart intact? Is the payment double-charged?
  • Install / upgrade / uninstall — upgrading from the previous version must migrate local data, not crash or wipe it. Very commonly missed.
  • Permissions — deny camera/location and confirm graceful degradation, then grant it later from OS settings.
  • Network transitions — WiFi → 4G → airplane mode → back. Offline mode, retry, and queued requests.
  • Device conditions — low battery, low storage, low memory (does the OS kill the app?), device rotation, split screen, foldables.
  • Hardware back button (Android) and swipe-back gesture (iOS) at every screen.
  • Deep links / push notification taps landing on the right screen, including when the app is cold-started.
  • Accessibility & display — large system font, dark mode, TalkBack/VoiceOver, small screens.
  • Localisation — RTL layouts, long translated strings overflowing buttons.

Q208Which ADB commands should a mobile tester know?▼
adb devices                                 # list connected devices/emulators
adb -s emulator-5554 shell                  # target a specific device

adb install -r app-qa.apk                   # -r = reinstall, keep data
adb uninstall com.example.shop
adb shell pm clear com.example.shop         # wipe app data — a clean-state reset

adb logcat                                  # live device log
adb logcat *:E                              # errors only
adb logcat | grep -i "com.example.shop"     # filter to your app — crash stack traces live here
adb bugreport                               # full diagnostic bundle

adb shell input text "hello"                # type
adb shell input keyevent 4                  # 4 = BACK, 3 = HOME, 26 = POWER, 82 = MENU
adb shell input swipe 500 1500 500 300      # swipe

adb push file.pdf /sdcard/Download/         # put a test file on the device
adb pull /sdcard/report.csv ./              # fetch a file the app produced
adb shell screencap /sdcard/s.png           # screenshot
adb shell screenrecord /sdcard/v.mp4        # video

adb shell dumpsys battery set level 5       # simulate low battery
adb shell svc wifi disable                  # network conditions
adb shell am start -a android.intent.action.VIEW -d "shopapp://orders/991"   # deep link
adb shell settings put global window_animation_scale 0     # disable animations = less flaky
That last line is a genuine framework tip: turning off window, transition and animator scales on the device removes a whole class of mobile flakiness. Saying it shows you have actually stabilised a mobile suite.

Q209How do you handle waits and flakiness in Appium?▼
// Explicit waits work exactly as in Selenium
WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(20));
wait.until(ExpectedConditions.visibilityOfElementLocated(AppiumBy.accessibilityId("cart_button")));

// Appium-specific: keep the session alive during long operations
options.setNewCommandTimeout(Duration.ofSeconds(120));
Mobile-specific flakiness causes
  • Animations and transitions — the element exists but is still sliding in. Fix: disable animation scales via ADB, and wait for a stable state.
  • Slow emulator cold start — the app is not ready when the driver session begins. Fix: wait for a known first-screen element, not a fixed sleep.
  • Soft keyboard covering elements — driver.hideKeyboard() after typing, or use setDisableWindowAnimation/keyboard capabilities.
  • XPath timeouts on long lists — the hierarchy dump is expensive; switch to accessibility id or UiSelector.
  • Elements outside the viewport — mobile only exposes what is rendered, so you must scroll before the element even exists in the tree.
  • Stale sessions — the device locks or the app is killed by the OS. Fix: newCommandTimeout, keep the screen awake, and reset cleanly between tests.
  • Shared device contention in CI — two jobs grabbing the same device. Fix: a device pool/lock, or a cloud farm.

Q210How do you run mobile tests in parallel?▼

Same principle as web — ThreadLocal driver — plus one extra dimension: each thread needs its own device and its own Appium server port.

<suite name="MobileSuite" parallel="tests" thread-count="3">
  <test name="Pixel7">
    <parameter name="udid"       value="emulator-5554"/>
    <parameter name="systemPort" value="8200"/>
    <parameter name="serverPort" value="4723"/>
    <classes><class name="tests.CheckoutTest"/></classes>
  </test>
  <test name="Pixel5">
    <parameter name="udid"       value="emulator-5556"/>
    <parameter name="systemPort" value="8201"/>
    <parameter name="serverPort" value="4725"/>
    <classes><class name="tests.CheckoutTest"/></classes>
  </test>
</suite>
@BeforeMethod
@Parameters({"udid", "systemPort", "serverPort"})
public void setUp(String udid, int systemPort, int serverPort) throws MalformedURLException {
    UiAutomator2Options options = new UiAutomator2Options()
            .setUdid(udid)
            .setSystemPort(systemPort)        // MUST be unique per device, or sessions collide
            .setApp(appPath);
    MobileDriverFactory.set(new AndroidDriver(
            new URL("http://127.0.0.1:" + serverPort), options));
}
The mistake almost everyone makes: forgetting systemPort (Android) or wdaLocalPort (iOS). Without a unique port per device, the second session hijacks the first one's bridge and you get bizarre cross-device failures that look like application bugs.

Q211How do you structure a mobile automation framework? Can you share code with the web suite?▼

Yes — and saying how is a strong senior answer.

src/main/java/
  core/
    DriverFactory.java        // returns WebDriver: Chrome, Firefox, AndroidDriver, IOSDriver
    BasePage.java             // click/type/waitFor — written against WebDriver, not ChromeDriver
  pages/
    web/     LoginPage.java   CheckoutPage.java
    mobile/  LoginScreen.java CheckoutScreen.java
  utils/                      // SHARED: ApiClient, DbClient, DataFactory, ExcelReader, Logger

What is shared: the driver factory pattern, the wait helpers, config layering, test data creation via API, reporting/listeners, and the whole build/CI setup. What is platform-specific: locators, gestures, and app lifecycle handling.

Cross-platform page objects (Android + iOS from one class)
public class LoginScreen extends BaseScreen {
    private final By email = isAndroid()
            ? AppiumBy.id("com.example.shop:id/email")
            : AppiumBy.accessibilityId("emailField");

    // …or better: ask developers for the SAME accessibility id on both platforms,
    // and then a single locator serves both:
    private final By password = AppiumBy.accessibilityId("passwordField");
}
Push the shared accessibility id convention as a team practice. It removes platform branching from your locators and improves the app's accessibility. That "one change, two benefits" framing is exactly how a senior engineer argues for testability.

Q212How do you find locators in a mobile app?▼
  • Appium Inspector — the standard tool. Connect to a running session, tap an element in the mirrored screen and it shows the id, accessibility id, class, XPath and a suggested locator.
  • uiautomatorviewer (legacy Android SDK tool) and Android Studio's Layout Inspector.
  • Xcode Accessibility Inspector for iOS.
  • driver.getPageSource() — dumps the XML view hierarchy; useful for scripting and for CI debugging where no GUI exists.
  • Ask the developers to add contentDescription (Android) / accessibilityIdentifier (iOS) — the mobile equivalent of data-testid.
A trap: elements that look identical on screen can have different hierarchies on the two platforms, so a locator verified in the Inspector on Android may not exist on iOS. Always verify both, and prefer the shared accessibility id so you only maintain one.

Q214What are the biggest challenges in mobile automation?▼
  • Device fragmentation — thousands of Android device/OS/OEM-skin combinations. Mitigate with analytics-driven device selection and a cloud farm.
  • Slow, unstable infrastructure — emulator boot times, WebDriverAgent rebuilds on iOS, devices disconnecting, ports colliding. Mobile CI needs far more babysitting than web CI.
  • iOS friction — signing certificates, provisioning profiles, needing a Mac build agent, Xcode upgrades breaking WebDriverAgent.
  • Slow feedback — a mobile suite is inherently slower than a web suite; you have to be ruthless about what belongs at the UI level.
  • Locator instability in cross-platform frameworks (React Native/Flutter) where the rendered tree changes between versions.
  • App state management — deciding between noReset (fast, dirty) and full reset (slow, clean) per suite.
  • Things you simply cannot automate — biometrics, real payments (NFC), camera scanning, OS-level dialogs on some versions, push notification delivery.
End with the mitigation, not the complaint: "Because mobile UI tests are expensive, we kept the mobile UI layer to the top 15 user journeys and pushed everything else to API tests and unit tests on the app side. That kept the mobile pipeline under 25 minutes."

Q215How would you test a mobile app end to end, if asked in an open question?▼

Answer in layers, exactly as with the login page question — categories, not a random list.

  1. Functional — install, onboarding, signup/login, core journeys (search → cart → pay), logout, edge cases and validations.
  2. App lifecycle — background/foreground, kill and relaunch, upgrade from the previous version, uninstall/reinstall, cold vs warm start.
  3. Interrupts — call, SMS, notification, alarm, another app, screen lock during a transaction.
  4. Connectivity — offline behaviour, slow 2G/3G, network switching, request retry, sync on reconnect.
  5. Device & OS matrix — screen sizes, OS versions, OEM skins, tablets, foldables, notches, dark mode, large fonts.
  6. Performance — cold start time, screen render time, memory and battery usage, APK/IPA size, ANRs and crash-free rate.
  7. Security — data at rest not stored in plain text, no sensitive data in logs, certificate pinning, root/jailbreak handling, session expiry, screenshot blocking on sensitive screens.
  8. Accessibility — TalkBack/VoiceOver, touch target sizes, contrast, dynamic type.
  9. Store readiness — permissions declared, privacy policy, store metadata, and compliance rules.
