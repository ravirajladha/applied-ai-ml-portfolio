SECTION 1

The mental model, and the services you must be able to choose between

"Azure preferred" appears in most job descriptions on this stack. For many candidates this is the biggest new-territory category — and the one with the highest ratio of marks to study time, because it is mostly vocabulary and decision rules.

PrimerHow Azure is organised, from zero

The hierarchy

LevelWhat it is
TenantThe organisation's identity boundary, in Microsoft Entra ID. One tenant per organisation.
SubscriptionThe billing and quota boundary. Often one per environment or per business unit.
Resource groupA logical container for resources that share a lifecycle. Deleting the group deletes everything in it — which is exactly why you group by lifecycle, not by type.
ResourceThe thing itself: a web app, a database, a storage account.
RegionWhere it physically runs. Latency, data residency and cost all depend on it.

The three things that are true of everything in Azure

  1. Every resource is described by a template. The portal is a UI over the Azure Resource Manager API. Anything you can click, you can declare in Bicep or Terraform — and in a professional setup you always do, because clicked infrastructure cannot be reviewed, reproduced or rolled back.
  2. Access is RBAC on a scope. You assign a role (Reader, Contributor, Storage Blob Data Reader) to an identity at a scope (subscription, resource group, resource). Permissions inherit downward. Least privilege means assigning at the narrowest scope that works.
  3. Identity is the security perimeter. The modern pattern is that resources authenticate to each other as themselves via managed identity, with no connection strings or keys anywhere. If you remember one Azure concept, remember this one.

The vocabulary that trips people up

TermMeaning
Microsoft Entra IDThe identity provider. Formerly Azure Active Directory — both names are still used, so recognise both.
Managed identityAn identity Azure creates and rotates for a resource. System-assigned (tied to one resource's lifecycle) or user-assigned (shared across several).
Service principalAn identity for an application, used where managed identity is not available — for example a CI pipeline outside Azure.
SAS tokenShared Access Signature — a time-limited, scoped URL granting access to a storage object.
Private endpointGives a PaaS service a private IP inside your virtual network, so traffic never crosses the public internet.
SKU / tierThe size and feature level you pay for. Many features (VNet integration, slots, autoscale) are gated behind a tier — a very common real-world surprise.
How to prepare this honestly in a few evenings. Get a free Azure account, deploy one container to Container Apps, put its secret in Key Vault, connect with a managed identity, and send its logs to Application Insights. That single exercise gives you first-hand answers to about half the questions on this page, and lets you say "when I set this up" rather than "I believe you would". It costs nothing on the free tier.

Q2App Service: slots, scaling and configuration▼
  • Deployment slots — a staging slot is a live copy on the same plan. Deploy there, warm it up, smoke test, then swap. The swap is near-instant and reversible, which makes it blue-green deployment with almost no effort. This is the single most useful App Service feature to name.
  • App settings become environment variables, and can be marked slot-specific so they do not travel with a swap — which is how the staging slot keeps pointing at the staging database.
  • Scaling: scale up changes the plan tier (bigger instance); scale out adds instances, manually or by autoscale rules on CPU, memory, queue depth or a schedule.
  • Always On stops the app being unloaded when idle — otherwise the first request after a quiet period is very slow.
  • Health check path so unhealthy instances are taken out of rotation automatically.
The swap trap: if your app caches configuration at startup and the slot swap changes connection strings, you can briefly serve requests against the wrong database. Warm up the slot and verify against the settings it will actually run with. Also: an in-progress swap plus a scale event is a well-known source of confusion — keep deployments and scaling events apart.

Q3Azure Functions: triggers, bindings, plans and cold starts▼

A function has one trigger (what starts it) and any number of bindings (data in and out, declared rather than coded).

@app.blob_trigger(arg_name="blob", path="uploads/{name}",
                  connection="STORAGE_CONNECTION")
@app.queue_output(arg_name="msg", queue_name="processed",
                  connection="STORAGE_CONNECTION")
def process_upload(blob: func.InputStream, msg: func.Out[str]):
    result = parse_survey(blob.read())
    msg.set(json.dumps(result))
PlanTrade-off
ConsumptionPay per execution, scale to zero. Cold starts — the first call after idle takes seconds. Execution time limited.
PremiumPre-warmed instances (no cold start), VNet integration, longer runs. Costs whether used or not.
Dedicated (App Service plan)Runs on a plan you already pay for.
Mention Durable Functions if orchestration comes up: it lets you write a multi-step workflow with fan-out/fan-in, waiting and human approval as ordinary code, with the state checkpointed for you. It is Azure's answer to the saga orchestration problem and knowing it exists is a differentiator.
Common trap: putting a long-running or latency-sensitive API on a Consumption plan. A user-facing endpoint that takes eight seconds because of a cold start is a bad experience, and it appears only after quiet periods — so it passes every test.

Q4Storage: blobs, tiers, and what a data lake is▼
ServiceFor
Blob StorageUnstructured objects — documents, images, backups, raw data. The workhorse.
ADLS Gen2Blob storage with a real hierarchical namespace and POSIX-style ACLs. The data lake; what analytics engines expect.
Azure FilesAn SMB/NFS file share, for lift-and-shift applications that need a mounted drive.
Queue StorageSimple, cheap queue. Service Bus when you need ordering, sessions, topics or transactions.
Table StorageCheap key-value at scale. Cosmos DB for anything richer.

Access tiers — Hot (frequent access, cheap reads), Cool (infrequent, cheaper storage, higher read cost, 30-day minimum), Cold, and Archive (very cheap, but retrieval takes hours). Lifecycle management rules move blobs between tiers automatically by age.

Directly relevant in engineering and environmental work: survey data, drone imagery, LiDAR scans and long-term monitoring records are large and rarely re-read but must be retained for decades for regulatory reasons. Automatic tiering from Hot to Cool to Archive is a substantial and very real cost decision — mentioning it shows you think about running cost, not just architecture.

Q5Azure SQL vs Cosmos DB vs PostgreSQL▼
Azure SQL DatabaseCosmos DBAzure Database for PostgreSQL
ModelRelational, managed SQL ServerMulti-model NoSQL (document by default)Relational, managed PostgreSQL
StrengthTransactions, joins, mature tooling. The default.Global distribution, single-digit-ms reads, elastic scale, tunable consistencyOpen source, rich extensions — notably PostGIS
ScalingVertical, read replicas, elastic pools, HyperscaleHorizontal by partition keyVertical, read replicas, Citus for sharding
BillingDTU or vCore; serverless auto-pauseRequest Units (RU/s), provisioned or serverlessvCore
The domain-specific point worth making: if the work is geospatial — asset locations, boundaries, route networks — PostgreSQL with PostGIS is the strongest option in the field, and Azure SQL also has native spatial types. Raising geospatial storage unprompted in an environmental/infrastructure interview is a genuinely differentiating move.
The Cosmos DB question they always ask: the partition key. It determines how data is distributed and it cannot be changed without migrating everything. Choose one with high cardinality that spreads writes evenly and that most queries filter on — otherwise you get a "hot partition" throttling one physical partition while the rest idle. Also know that a query without the partition key becomes a cross-partition fan-out and costs many times more RUs.

Q6Service Bus, Event Hubs, Event Grid, Storage Queue — which one?▼
ServiceModelUse for
Service BusEnterprise message broker — queues and topics/subscriptionsBusiness messages that must not be lost. FIFO with sessions, dead-lettering, duplicate detection, transactions, scheduled delivery. "Process this order."
Event HubsHigh-throughput partitioned event stream (Kafka-compatible)Telemetry and sensor data at millions of events per second, with consumers reading at their own offset and replay. "Here is a reading."
Event GridReactive pub/sub event routingDiscrete notifications: a blob was created, a resource changed. Push-based, with filtering and retries. "Something happened."
Storage QueueSimple, cheap queueBasic decoupling with no advanced features and very low cost.
A worked example from environmental monitoring. Environmental sensors across a city stream readings → Event Hubs (volume, ordered per device, replayable). A processor detects a threshold breach and publishes a business message → Service Bus (must not be lost, must be processed once). A report file lands in blob storage → Event Grid fires a Function to index it. Being able to place all three in one story is exactly the answer they want, and it is more convincing than defining them separately.

SECTION 2

Identity, secrets, networking and operations

The parts that separate "I deployed something to Azure once" from "I have run something on Azure".

Q7Managed identity and Key Vault — the answer that signals real exposure▼

Key Vault stores secrets, keys and certificates, with access controlled by RBAC and every access audited. Secrets can be versioned and rotated centrally rather than redeployed.

Managed identity goes further and removes the secret entirely. Azure creates an identity for your App Service or Container App, rotates its credentials itself, and you grant that identity a role on the target resource. Your code asks for a token; nothing is stored.

from azure.identity import DefaultAzureCredential
from azure.storage.blob import BlobServiceClient

# no connection string, no key, nothing in config
credential = DefaultAzureCredential()
client = BlobServiceClient(account_url=ACCOUNT_URL, credential=credential)

DefaultAzureCredential tries a chain of sources — managed identity in Azure, your developer sign-in locally — so the same code works in both places with no branching.

"The pattern I'd push for is managed identity everywhere it's supported, and Key Vault for the residue that genuinely needs a secret — a third-party API key, say. If there's no secret, there's nothing to leak, nothing to rotate and nothing to accidentally commit."

Q8Entra ID: how does a user actually sign in to your app?▼
  1. You register two applications in Entra ID: the client (your SPA or web app) and the API, which exposes scopes such as Assets.Read.
  2. The client redirects the user to Entra ID (Authorization Code + PKCE). The user authenticates — with MFA and conditional access policies enforced by the tenant, not by you.
  3. The client receives an ID token (who the user is) and an access token for your API's audience.
  4. Every request carries Authorization: Bearer <access token>.
  5. Your API validates signature, iss, aud, exp, then authorises on scopes (delegated permissions) or app roles (assigned to users or groups).
The organisational point: using Entra ID means you never store passwords, and MFA, conditional access, device compliance and offboarding are handled by the identity team centrally. For a large enterprise that is not a convenience, it is a requirement — and framing it that way shows you understand why enterprises standardise on it.
Also know B2C / External ID — the variant for external users such as clients or contractors, where you do not want them in the corporate directory.

Q10Application Insights, Log Analytics and KQL▼

Application Insights is the application-level telemetry service — requests, dependencies, exceptions, traces, custom metrics, and end-to-end distributed transaction views. It writes into a Log Analytics workspace, which you query with KQL (Kusto Query Language).

requests
| where timestamp > ago(1h)
| where success == false
| summarize failures = count(), p95 = percentile(duration, 95)
          by name, resultCode
| order by failures desc
| take 20

KQL reads like a pipeline: a table, then filters, then aggregation. Being able to write even a simple query out loud is a strong, concrete signal — most candidates only say "we used App Insights".

  • Auto-instrumentation captures requests and dependency calls (SQL, HTTP, Service Bus) with almost no code — including the timings that answer "is it the app or the database?"
  • The operation ID correlates everything in one request, across services.
  • Alerts on metrics, log queries or availability tests, routed to an action group (email, Teams, PagerDuty).
  • Sampling keeps cost down at volume — and telemetry cost is real, so knowing it exists matters.

  name: '${appName}-plan'

}

resource site 'Microsoft.Web/sites@2023-01-01' = {
  name: appName
  location: location
  identity: { type: 'SystemAssigned' }        // managed identity, declared
  properties: {
    serverFarmId: plan.id
    siteConfig: {
      healthCheckPath: '/health'
      appSettings: [
        { name: 'KEY_VAULT_URI', value: keyVault.properties.vaultUri }
      ]
    }
  }
}
Verdict
ARM templatesThe underlying JSON. Verbose; rarely hand-written now.
BicepA readable language that compiles to ARM. Azure-only, first-party, no state file to manage. The default for an Azure-only estate.
TerraformMulti-cloud, huge provider ecosystem, mature module patterns. Requires managing state. Choose it if the organisation is multi-cloud or already standardised on it.
Why it matters, said well: "Infrastructure defined in code gets code review, gets versioned, and can be recreated identically in a new environment. Clicked infrastructure means nobody knows why a setting is the way it is, and dev and prod drift apart silently — which is the same environment-parity problem I've spent years dealing with from the testing side."

Q12The Well-Architected Framework, and what it is for▼

Five pillars — worth knowing by name because Microsoft-stack architects use them as a checklist in design reviews:

PillarAsks
ReliabilityWhat happens when a component fails? Redundancy, retries, backups, recovery objectives (RTO/RPO).
SecurityIdentity, least privilege, encryption in transit and at rest, network isolation, secrets.
Cost optimisationAre we paying for what we use? Right-sizing, autoscale, reserved capacity, storage tiering.
Operational excellenceAutomated deployment, monitoring, alerting, runbooks, infrastructure as code.
Performance efficiencyDoes it scale with demand? Caching, async processing, the right service tier.
Use it as a structure, not a recitation. If asked to review or design an architecture, walking the five pillars gives you an organised answer under pressure and signals that you have been in a real design review.

Q13How do you keep Azure costs under control?▼

A consultancy bills clients for cloud spend, so this question carries more weight here than at a product company.

  • Right-size, then autoscale. Most over-spend is idle capacity provisioned for a peak that happens twice a year.
  • Scale to zero where the workload allows — Container Apps, Consumption Functions, serverless SQL with auto-pause. Excellent for non-production environments.
  • Shut down non-production out of hours. Dev and test running 24/7 is often a third of the bill for no benefit.
  • Storage lifecycle rules to move cold data to cheaper tiers automatically.
  • Reserved instances or savings plans for genuinely steady workloads — one to three year commitments at a large discount.
  • Tag everything by project, environment and client so cost can be attributed — essential when it is rebilled.
  • Budgets and alerts, plus Azure Advisor recommendations reviewed regularly.
  • Watch egress and cross-region traffic — data leaving a region is a line item people forget until the invoice arrives.
The sentence that lands: "Cost is a design constraint, not a procurement problem. The architecture decision and the monthly bill are the same decision, and in a consulting context that number is visible to the client."

Q15Stating the limits of your cloud experience without undermining yourself▼

Azure is one of the easiest topics to be caught out on, because the follow-up is always "and how did you configure that?" Overstating it fails immediately; understating it wastes what you do know. The answer is a bounded claim: state the boundary, demonstrate what sits inside it, and name the specific things outside it.

"I haven't run a production estate on Azure. What I have done is build and deploy on it — containerised a service into Container Apps, wired Key Vault with a managed identity, and shipped telemetry into Application Insights — so I understand the model and the service choices. Where I'd expect to lean on the team early is the organisational side: landing zones, networking standards, and how subscriptions and cost allocation are structured."

Why it works: naming the things you do not know is itself evidence that you understand the landscape — you cannot name landing zones and cost allocation as your gaps unless you know they exist. It is a far stronger answer than a confident generality, and it is one an interviewer can safely believe.

Closing the gap quickly: deploy one container to Container Apps, put its secret in Key Vault, connect with a managed identity, and send logs to Application Insights. That single exercise, on the free tier, converts most of this page from "I believe you would" into "when I set this up". The AZ-900 fundamentals material is a fast, structured way to close the remaining vocabulary gaps.
