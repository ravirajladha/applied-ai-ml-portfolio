SECTION 1

Designing an API

"Build APIs, microservices, and integrations" is a headline responsibility in almost every one of these roles. Expect to design one live.

PrimerThe method for designing an API on the spot

Most developers know APIs far better from the outside — consuming and testing them — than from the design side. The interview asks you to produce one. The gap is usually not knowledge, it is having a repeatable procedure so you are not inventing an approach while someone watches.

Step 1 — find the nouns

Write down the things the system is about. For an asset-management problem: site, asset, inspection, report, attachment, user. These become your resources. Resist starting from the screens — screens change, the domain does not.

Step 2 — establish the relationships and the ownership

An inspection belongs to an asset; an asset belongs to a site. Ownership determines URL nesting and your authorisation rules, which is why it is worth doing before you write a single path.

Step 3 — write the paths

GET    /v1/sites                          list, filtered and paginated
POST   /v1/sites                          create
GET    /v1/sites/{siteId}                 read one
PATCH  /v1/sites/{siteId}                 partial update
DELETE /v1/sites/{siteId}                 remove

GET    /v1/sites/{siteId}/assets          assets of a site  (nested: shows ownership)
POST   /v1/sites/{siteId}/assets          create within a site
GET    /v1/assets/{assetId}               read one directly (do not force deep nesting)
POST   /v1/assets/{assetId}/inspections   record an inspection

Nest one level, no more. /sites/1/assets/5/inspections/9/photos/3 is unusable. Nest to express ownership on collections, then address individual resources by their own top-level path.

Step 4 — decide the collection parameters

GET /v1/assets?siteId=12&status=active&minScore=50
                &sort=-conditionScore&limit=50&cursor=eyJpZCI6MTIzfQ

Filtering, sorting and pagination on every collection endpoint, decided once and applied consistently. Consistency across endpoints is worth more than the specific convention you pick.

Step 5 — the things that are not CRUD

Some operations are genuinely actions, not resource mutations: approving, publishing, recalculating, exporting. Two acceptable answers, and having an opinion matters:

  • Model the action as a resource: POST /v1/reports/{id}/approvals — the approval is a thing with a timestamp and an approver, which is usually true anyway.
  • Or accept a controller-style sub-resource: POST /v1/reports/{id}:approve.

What is not acceptable is POST /approveReport?id=5. If you find yourself writing verbs into paths everywhere, the domain model is probably missing a noun.

Step 6 — say the cross-cutting decisions out loud

Auth, versioning, error format, pagination style, idempotency, rate limits. Naming these unprompted is what separates a designed API from a collection of endpoints — and it is exactly what the interviewer is listening for.

Coming from test automation → you have an unusual advantage: you know what a badly designed API costs, because you have written clients for them. Inconsistent error shapes, pagination that changes under you, a 200 with an error in the body. Say so — "I've written a lot of API clients, so I design for the person who has to consume this" is a genuine, memorable framing that few candidates can offer honestly.
Q1"Design an API for inspecting infrastructure assets." — a worked answer▼

Run the six steps out loud. Start with questions, not endpoints:

  • Who consumes it — a web app, a mobile field app, other services, or third parties?
  • Does the field app work offline? (In infrastructure and environmental work this is very likely yes, and it changes the design — you need client-generated IDs and an idempotent sync endpoint.)
  • How many assets per site, realistically? Hundreds or millions?
  • Are photos and documents attached? How large?
Then the design
POST /v1/assets/{assetId}/inspections
Idempotency-Key: 8f14e45f-ea1a-4b2c-9c1e-0d5f3a7b6c21
Authorization: Bearer <token>

{
  "inspectedAt": "2026-08-14T09:20:00Z",
  "inspectorId": 4412,
  "conditionScore": 62.5,
  "findings": [
    { "code": "CORROSION", "severity": "medium", "note": "north abutment" }
  ],
  "location": { "lat": 28.5355, "lon": 77.3910 }
}

201 Created
Location: /v1/inspections/90210

Points to make while designing:

  • Client-supplied idempotency key so a field device retrying on a flaky connection cannot create duplicate inspections. For an offline-first app this is essential, not a nicety — and volunteering it is the single strongest thing you can say in this answer.
  • Attachments are separate. Do not base64 photos into JSON. Issue a pre-signed upload URL to blob storage, then reference the blob: POST /v1/inspections/{id}/attachments with the returned key. Keeps large binaries off the API and lets uploads resume.
  • Timestamps in UTC, ISO 8601, always. Field data crosses time zones and the argument about local time is not one you want later.
  • Findings as an array of coded objects, not free text, so they can be aggregated and reported on.

Q3How do you version an API?▼
ApproachExampleVerdict
URL path/v1/assetsMost common. Obvious, cacheable, trivially routable at a gateway. The pragmatic default.
HeaderAccept: application/vnd.example.v2+jsonPurist's choice — the URL identifies the resource, not the representation. Harder to test and to route.
Query parameter?version=2Easy, but easy to omit and easy to cache wrongly.

The more important half of the answer is avoiding a new version. Additive changes — a new optional request field, a new response field — are backwards compatible provided consumers ignore unknown fields, which you state explicitly in the contract. Only break out a new major version for a genuinely breaking change.

"Version in the path, but treat a new version as a cost, not a feature. Every version is one you support and test in parallel. I'd add fields additively, deprecate with a Sunset header and a migration window, and only cut v2 when the model genuinely changed shape."

Q4What does a good error response look like?▼
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/problem+json

{
  "type": "https://api.example.com/errors/validation",
  "title": "Validation failed",
  "status": 422,
  "detail": "One or more fields are invalid",
  "instance": "/v1/assets",
  "traceId": "0af7651916cd43dd8448eb211c80319c",
  "errors": [
    { "field": "conditionScore", "code": "out_of_range",
      "message": "must be between 0 and 100" }
  ]
}

That shape is Problem Details — RFC 9457, which obsoleted RFC 7807 in 2023. Most people still say 7807, so either name is understood, but 9457 is the current one. Properties that make it good:

  • Machine-readable codes (out_of_range) as well as human messages — a client should never have to string-match on English.
  • Field-level errors so a form can highlight the right input.
  • A trace ID the caller can quote to support, correlating to your logs.
  • Every endpoint fails identically, produced by one global handler.
  • Nothing internal — no stack traces, no SQL, no table names.
The anti-pattern to name: returning 200 OK with {"success": false}. It defeats HTTP caching, monitoring, retries and every standard client library — your error rate dashboard shows zero while everything is failing. You have almost certainly hit this from the testing side; say so.

Q5Idempotency in a real design▼

The client generates a UUID and sends it as Idempotency-Key. The server:

  1. Looks the key up. If present and complete, return the stored response — same status, same body — without redoing the work.
  2. If present but still in flight, return 409 so the client retries later.
  3. If absent, record the key, do the work in the same transaction as recording the result, and store the response.

Keys expire — 24 hours is typical. Store them in a table or Redis with a TTL.

Where this matters in the field: an offline field app queues inspections and syncs when signal returns. Without idempotency, one bad connection produces duplicate inspection records that someone has to reconcile by hand. Framing the answer around a real failure is far better than describing the mechanism.

Q6How do you handle a long-running operation?▼

Never hold an HTTP connection open for two minutes generating a report. Use the 202 + polling pattern:

POST /v1/reports              →  202 Accepted
                                 Location: /v1/jobs/8812
                                 { "jobId": "8812", "status": "queued" }

GET /v1/jobs/8812             →  200 { "status": "running", "progress": 45 }
GET /v1/jobs/8812             →  200 { "status": "succeeded",
                                        "resultUrl": "/v1/reports/551" }

Behind it: the POST writes a job row and puts a message on a queue; a worker consumes it. That gives you retries, visibility, and a request that returns in milliseconds.

Alternatives worth naming: a webhook so you call the client back when it is done (better for server-to-server, but the client needs a public endpoint and you need retries and signing), or WebSocket / server-sent events for live progress in a UI.

Add Retry-After to the polling response so clients do not hammer you every 100 ms. Small detail, real operational experience.

Q7Designing a webhook (an API that calls someone else)▼

Everything that is hard about webhooks is on your side, and knowing the list is the answer:

  • Sign the payload — HMAC over the body with a shared secret, in a header. The receiver verifies it, otherwise anyone who learns the URL can post fake events.
  • Include a timestamp in the signature to prevent replay.
  • Retry with exponential backoff for a bounded window, then dead-letter and alert.
  • At-least-once delivery — so include an event ID and tell consumers to be idempotent. Duplicates will happen.
  • Do not guarantee ordering, or if you do, say so explicitly and pay for it.
  • Time out fast and treat the delivery as async — a slow consumer must not back up your system.
  • Let consumers replay missed events from a log or an API.

HowWrite the OpenAPI YAML, generate server stubs and client SDKsWrite annotated code, generate the spec (FastAPI, Swashbuckle, springdoc)

"For an integration with another team or a client I'd go contract-first — the spec is the negotiation, and both sides can build against it in parallel. For an internal service I'd go code-first and publish the generated spec, then add a CI check that fails the build on a breaking change against the previous version."
Mention the generated client SDK. Consumers get a typed client instead of hand-writing HTTP calls, which removes a whole category of integration bug. It is also exactly what makes contract testing enforceable.

Security, protection and protocols

Everything between the caller and your handler.

Q9OAuth2 flows — which one, when▼
FlowUse when
Authorization Code + PKCEA user is logging in — web app, SPA or mobile. The default answer. PKCE protects the code exchange on public clients that cannot keep a secret.
Client credentialsService to service, no user involved. A daemon, a scheduled job, a backend calling another backend.
Device codeA device with no browser or keyboard.
ImplicitDeprecated. Tokens in the URL fragment. Saying you would use it dates you badly.
Resource owner passwordDeprecated. The app handles the user's password, which is the thing OAuth exists to avoid.
The roles

Resource owner (the user), client (the app), authorization server (Microsoft Entra ID), resource server (your API). The client gets a token from the authorization server and presents it to the resource server.

Access token vs refresh token: the access token is short-lived (minutes) and sent on every request; the refresh token is long-lived, stored securely, and used only to obtain a new access token. That split is what limits the damage from a leaked access token.

Q10How does your API validate a JWT?▼

A JWT is header.payload.signature, base64url-encoded. Validation, in order:

  1. Signature — against the issuer's public key, fetched from its JWKS endpoint and cached. Match on the kid in the header so key rotation works.
  2. exp and nbf — not expired, not used before valid.
  3. iss — issued by the identity provider you expect.
  4. aud — intended for your API. Skipping this means a token minted for a different application is accepted by yours.
  5. Scopes / roles — the authorisation decision, after authentication succeeds.
Two classic vulnerabilities: accepting alg: none (the token claims it is unsigned and a naive library believes it), and accepting a token signed with a symmetric algorithm when you expected asymmetric. Pin the expected algorithm explicitly. Also remember JWTs are signed, not encrypted — the payload is readable by anyone, so nothing confidential goes in it.

Q11Rate limiting and throttling▼

Why: protect the service from abuse, from a buggy client in a retry loop, and from one tenant consuming everyone's capacity.

AlgorithmBehaviour
Token bucketTokens refill at a fixed rate; a burst is allowed up to the bucket size. Most common, because bursts are normal.
Fixed windowSimple, but allows a double burst at the window boundary
Sliding windowSmoother, more expensive to compute
Concurrency limitCap simultaneous in-flight requests rather than rate

Respond with 429, a Retry-After header, and X-RateLimit-Limit/Remaining/Reset so a well-behaved client can self-regulate. Limit per API key or per tenant, not per IP — many users share one IP behind corporate NAT.

Where it belongs: at the gateway (Azure API Management), so every service behind it is protected without each one implementing it. And in a multi-instance deployment the counter must be in a shared store like Redis, or your limit is silently multiplied by the number of instances.

Q13HTTP caching: ETag, Cache-Control and conditional requests▼
GET /v1/assets/42
→ 200 OK
  ETag: "a17c9f"
  Cache-Control: private, max-age=60

GET /v1/assets/42
  If-None-Match: "a17c9f"
→ 304 Not Modified          (no body — bandwidth and serialisation saved)

ETag is a version identifier for a representation. Beyond caching it gives you optimistic concurrency: send If-Match: "a17c9f" on a PUT/PATCH and the server returns 412 Precondition Failed if someone else changed it meanwhile. That is a clean answer to "how do you stop two users overwriting each other?" and it uses only HTTP.

Cache-Control: private vs public: public allows shared caches and CDNs to store it. Marking a per-user response public means one user's data gets served to another — a serious and entirely real bug class.

Q15Integrating with a third-party API you do not control▼

"Integrations across digital platforms" appears in most of these job descriptions, and this is the practical question behind it.

  • Wrap it behind your own interface (the Adapter pattern). Nothing in your domain should import their SDK's types — otherwise their breaking change becomes yours everywhere.
  • Timeout on every call. Then retry with backoff for transient failures only, and a circuit breaker so their outage does not become yours.
  • Decide the degraded behaviour in advance: cached data, a partial response, or a clear error. "The whole page 500s" is a decision too — just usually the wrong one.
  • Respect their rate limits proactively rather than discovering them via 429s.
  • Log every request and response (redacted) — when there is a dispute about what was sent, this is the only thing that resolves it.
  • Record their contract in a test. A recorded-response test tells you when their payload changes shape.
  • Treat their data as untrusted input and validate it, even though they are a partner.
Coming from test automation → service virtualisation and mocking external dependencies is exactly this problem from the other side. You know why depending on a live third-party sandbox in CI is a bad idea — that story fits perfectly here.

Q16How do you change an API without breaking consumers?▼
  1. Additive changes only, wherever possible. New optional fields, new endpoints.
  2. Never repurpose an existing field. Changing what a value means is worse than removing it, because nothing fails — it just goes quietly wrong.
  3. Deprecate visibly: document it, add a Deprecation and Sunset header, and measure who is still calling it before you remove anything.
  4. Consumer-driven contract tests (Pact): each consumer publishes what it actually relies on, and your build fails if you break it. This is what lets services deploy independently without a full end-to-end suite.
  5. Run both versions in parallel during a migration window with a defined end date.
This is a place to lead rather than follow. Contract testing sits exactly between your testing background and this role's architecture work. If the team has not adopted it, "here is how services deploy independently without an integration bottleneck" is the kind of contribution that gets a mid-level hire noticed.

Q17File upload and download at scale▼

Do not stream large files through your API. The pattern:

  1. Client asks your API for permission: POST /v1/attachments with filename, size and content type.
  2. Your API validates (size cap, allowed types, quota, authorisation) and returns a short-lived pre-signed URL to blob storage — on Azure, a SAS URL.
  3. Client uploads directly to storage. Your service never touches the bytes.
  4. Client confirms: PUT /v1/attachments/{id}/complete. Your service verifies the blob exists, scans it for malware, and records the metadata.

Downloads work the same way in reverse: a short-lived read SAS rather than proxying.

Validate the content, not the extension. A file named report.pdf can contain anything. Check the magic bytes, cap the size before accepting, and never serve user-uploaded files from your application's own origin — a stored HTML file becomes stored XSS.
