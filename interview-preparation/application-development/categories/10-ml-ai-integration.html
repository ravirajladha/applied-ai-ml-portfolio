SECTION 1

The differentiator

"Work with data engineers and scientists to operationalize analysis pipelines and ML models" now appears as a responsibility in a lot of application developer job descriptions, usually alongside "experience integrating ML/AI components" as a preferred qualification. Very few candidates for a mid-level application role can answer it well, which makes it one of the highest-leverage topics on this list.

PrimerWhat an application developer needs to understand about models

A model is a function with learned parameters

Strip the mystique: a trained model is a file containing numbers, plus code that turns an input into an output using them. From an application's point of view it is a dependency with unusual properties:

  • It is probabilistic — the same input gives the same output, but the output is a likelihood, not a fact. Your application has to decide what to do with a 0.71.
  • It degrades over time without anyone changing it, because the world it was trained on moves.
  • Its behaviour depends on data as much as on code, so "what version is running?" must mean the model, the data it was trained on, and the preprocessing.

Training vs inference — the distinction everything else rests on

TrainingInference (serving)
WhatLearning parameters from historical dataApplying them to a new input
WhenOccasionally — daily, weekly, on driftConstantly, in the request path
ComputeHeavy, batch, possibly GPULight, low-latency, usually CPU
OwnerData scientistYou
Fails asA bad metric, caught in evaluationA latency spike, an outage, or silently wrong answers

The lifecycle, and where the gap actually is

data → features → training → evaluation → registry → deployment → monitoring
                     ▲                                                  │
                     └──────────────  retraining triggered  ────────────┘

Data scientists are typically strong from data to evaluation. The gap — the part this job is hiring for — is everything from registry onward: packaging, deployment, latency, cost, versioning, rollback, monitoring and retraining automation. That is ordinary software engineering applied to an unusual artefact, which is exactly why an application developer who understands models is valuable.

The sentence to have ready: "The interface between me and a data scientist should be a versioned model artefact and an agreed input schema. They own the model and the metric; I own that it runs reliably, cheaply, reproducibly and can be rolled back."
Q1"A data scientist hands you a notebook. How do you get it into production?"▼

The flagship question for this role. Answer it as a sequence with a reason for each step.

  1. Understand the contract first. What are the exact inputs, their types and ranges, what does the output mean, and what latency does the consumer need? Most integration failures are contract failures, not model failures.
  2. Extract the code from the notebook into a module with a clear entry point. Notebooks hide execution order and carry hidden state — a notebook that works top to bottom for its author frequently does not work anywhere else.
  3. Pin everything. Library versions, especially the one that serialised the model — loading a model with a different library version is a classic silent failure. Pinned dependencies plus a container.
  4. Separate preprocessing and make it shared. The same transformation code must run at training and at serving. If it is reimplemented for serving, the two will diverge — this is training-serving skew and it is the single most common production ML bug.
  5. Register the model with a version, the training data reference, the evaluation metrics and who produced it. A prediction must be traceable to an exact artefact.
  6. Choose the serving pattern — batch, real-time or streaming (next question).
  7. Wrap it in an API and containerise it, with validation, timeouts, a health endpoint and a fallback for when the model is unavailable.
  8. Deploy through the normal pipeline, behind a flag or a shadow deployment first.
  9. Monitor service health and model health separately.
  10. Automate retraining as a pipeline with the same gates a code change gets.
Land it with a project you have actually done. "That's the sequence I went through on the last model I put behind an API — the part that surprised me most was how much of the work was preprocessing parity rather than anything to do with the model." Specific, humble, and it demonstrates the experience instead of asserting it.

Q2Batch, real-time or streaming inference?▼
PatternHowUse when
BatchScheduled job scores everything, writes predictions to a table the app readsPredictions can be precomputed: risk scores refreshed nightly, next-inspection-due rankings. Cheapest, simplest, and correct more often than people assume.
Real-timeHTTP endpoint, scored per requestInput is only known at request time and a user or transaction is waiting.
StreamingConsumer scores events off a streamContinuous event flows — sensor readings scored for anomalies as they arrive.
EdgeModel runs on the deviceNo connectivity, or latency/privacy requires local processing. Real for field devices.
"I'd start by asking whether the prediction actually needs to be computed at request time. If the inputs are known in advance, batch scoring into a table is far cheaper and more reliable — you get a database lookup instead of a model server in the request path. I'd only go real-time when the input genuinely isn't known until the request."
The senior addition: real-time inference puts the model on the critical path, so it needs a timeout and a defined fallback. Decide in advance what happens when the model service is slow or down — a default score, the previous batch value, or a clear error. An application that hangs because a model is slow is a bad architecture, not a bad model.

Q3Training-serving skew and feature stores▼

Training-serving skew is when the features computed at serving time differ from those computed at training time. The model is fed something subtly different from what it learned on, so accuracy quietly collapses while every dashboard stays green.

How it happens in practice:

  • Training used pandas; serving reimplemented the transformation in the application.
  • A default or imputation value differs between the two paths.
  • Training aggregated over a 30-day window computed one way; serving computes it another.
  • Data leakage — training used a value that is not actually available at prediction time, so the model looked excellent in evaluation and is useless in production.

A feature store addresses this by computing features once and serving them to both paths — an offline store (historical, for training) and an online store (low-latency, for serving) built from the same definitions. It also gives you point-in-time correctness: training on the feature values as they were at that moment, not as they are now.

Say this if nothing else on the topic: "The bug I'd look for first isn't in the model, it's whether training and serving compute features with the same code. In my experience that's where production accuracy goes, and it's invisible unless you check for it deliberately."

Q4Model registry and versioning: what does "version" mean for a model?▼

Four things must be versioned together, or a prediction is not reproducible:

ArtefactVersioned by
Code (training + preprocessing)Git commit
DataA dataset snapshot or a Delta table version — not "the production table", which has changed since
Model binaryModel registry version
EnvironmentContainer image digest / lock file

A model registry (MLflow, Azure ML) stores the artefact with its metrics, parameters, lineage and stage (staging / production / archived), and provides promotion and rollback.

The question behind the question: "a prediction from three months ago is being disputed — can you reproduce it?" If you can name the model version, the code commit and the input, the answer is yes. For anything with a regulatory or contractual dimension — which describes a lot of engineering and public-sector work — that is not a nice-to-have.

Q5How is CI/CD for ML different from CI/CD for software?▼
SoftwareML
TriggersCode changeCode change, new data, or detected drift
TestsDeterministic pass/failMetric thresholds — plus tests on the data itself
ArtefactA buildA build and a model, versioned together
"Broken"Throws an errorReturns confident, plausible, wrong answers
RollbackPrevious versionPrevious model version — which must still be deployable

Gates in an ML pipeline that do not exist in a normal one:

  • Data validation — schema, ranges, null rates, class balance. Bad data in is worse than no data.
  • Metric threshold — the candidate model must beat the current production model on a held-out set by a defined margin, or the promotion fails automatically.
  • Fairness / slice checks — performance on important subgroups, not just the average. A model with good overall accuracy can be much worse for one region or asset type.
  • Latency and size — a more accurate model that doubles inference time may be a net loss.
The framing that lands: "The uncomfortable difference is that a broken deployment throws errors and a broken model doesn't. It keeps answering, confidently, and nothing goes red — so the monitoring has to be designed to catch quiet failure."

Q6Monitoring a model in production: drift and the feedback loop▼

Two independent layers, and saying so is the point:

Service healthModel health
Latency, error rate, throughput, saturation, costInput distributions, prediction distribution, accuracy once labels arrive
Fails loudlyFails silently
Kinds of drift
  • Data drift — the input distribution moves. New sensor type, a new region onboarded, a changed upstream unit of measurement. Detect by comparing live feature distributions against the training baseline.
  • Concept drift — the relationship between inputs and the target changes. Fraud tactics evolve; maintenance regimes change how assets deteriorate. Only detectable once you have labels.
  • Prediction drift — the output distribution shifts. Cheap to monitor, needs no labels, and is often the earliest warning you can actually get.
The label problem

You cannot measure accuracy until you know the truth, and truth arrives late — a fraud chargeback comes weeks later; whether an asset actually failed is known years later. So monitor the leading indicators (input and prediction drift) continuously, and accuracy on the delay the domain imposes.

Ask about the feedback loop. "How do labels get back into the system?" is a question few candidates think to ask, and without an answer no model can improve. It also opens the harder version: if the model's own decisions affect what data you collect — inspecting only the assets the model flagged — you never learn about the ones it missed. That is feedback loop bias, and naming it is a strong senior signal.

Q7Deploying a new model safely▼
TechniqueWhat it does
Shadow deploymentThe new model scores real traffic but its output is not used — only logged and compared. Zero risk, real data. The best first step.
CanaryA small percentage of traffic uses the new model; watch business and technical metrics before ramping.
Champion–challengerRun both continuously and compare on live outcomes over time.
A/B testRandomised split measured against a business metric, not just accuracy.
The point that separates people: the metric that matters is the business outcome, not the offline score. A model with better AUC can perform worse in production because the threshold is wrong for the operational cost of a false positive. If every flagged asset triggers a site visit, a small increase in false positives is expensive in a way no offline metric captures — and choosing the decision threshold is a business conversation, not a modelling one.

Q8Evaluation metrics — enough to talk to a data scientist as a peer▼
MetricMeaningCare when
AccuracyFraction correctMisleading with imbalanced classes — always predicting "not fraud" is 99.9% accurate and worthless
PrecisionOf those flagged, how many were rightFalse positives are costly — a wasted site visit

F1Harmonic mean of the twoYou need one number and both matter
ROC AUCRanking quality across thresholdsGeneral comparison; optimistic under heavy imbalance
PR AUCPrecision–recall trade-offBetter than ROC for rare positives

Precision and recall trade off against each other via the decision threshold. Moving the threshold is a business decision about which error is more expensive — and being able to frame it that way, rather than as a modelling detail, is the whole point of this question for an application developer.

"For infrastructure inspection I'd expect recall to matter more than precision — missing a defect has a much higher cost than an unnecessary inspection. So I'd want the threshold set by whoever owns that risk, not chosen to maximise F1."

Q10Inference cost and latency: the engineering levers▼
  • Do not use a GPU unless you need one. Classical models (gradient boosting, regression) run fine on CPU and cost a fraction. GPUs are for deep learning at volume.
  • Batch requests where latency allows — scoring 100 rows in one call is far cheaper per row than 100 calls.
  • Cache predictions when the same input recurs, keyed including the model version.
  • Optimise the model itself: quantisation, distillation, or exporting to ONNX for a faster, framework-independent runtime.
  • Load the model once at startup, not per request. Sounds obvious; is a real bug.
  • Scale to zero for spiky workloads, accepting cold start — or keep a warm instance if a user is waiting.
  • Precompute. The cheapest inference is the one you did last night in a batch job.
Have a latency budget answer: "If the endpoint has a 200 ms budget and the model takes 40 ms, I have 160 ms for feature lookup, network and serialisation — so the feature store lookup is as much of a design concern as the model." That is systems thinking applied to ML, which is precisely the hybrid this role wants.

Q11Integrating a large language model: RAG and the engineering concerns▼

Increasingly common wherever a role mentions "ML/AI components". Retrieval-augmented generation is the standard pattern for answering questions over an organisation's own documents:

  1. Ingest and chunk the documents — technical reports, specifications, standards. Chunking strategy matters more than people expect; chunks that split a table or a clause in half produce bad answers.
  2. Embed each chunk into a vector and store it in a vector index (Azure AI Search, pgvector, Cosmos DB vector search).
  3. At query time, embed the question, retrieve the most relevant chunks — usually hybrid: vector similarity plus keyword search, because exact terms and reference numbers matter in technical documents.
  4. Compose a prompt with the retrieved context and instructions.
  5. Return the answer with citations back to the source documents.
The engineering concerns — where an application developer earns their place
ConcernHandling
Grounding and hallucinationRequire citations; instruct the model to answer only from the provided context and to say when it cannot. Show sources in the UI so a user can verify.
Access controlThe one people forget. Retrieval must respect document permissions per user, or the assistant becomes a way to read documents you are not allowed to see. Filter at retrieval time, not afterwards.
Prompt injectionRetrieved content is untrusted input. A document containing instructions can attempt to redirect the model. Never let retrieved text trigger privileged actions.
Cost and latencyPriced per token, and slow. Cache, limit context size, stream responses, and set budgets.
EvaluationNon-deterministic output needs an evaluation set with graded answers, run as a regression suite — otherwise "we changed the prompt" is an untested deployment.
PrivacyWhat leaves your tenant. Azure OpenAI keeps data within your Azure boundary, which is usually the requirement for client documents.
The angle worth taking: "The interesting part of that stack isn't the model, it's that the output is non-deterministic — so the testing strategy has to change. You need an evaluation set and graded regression runs rather than assertions." Coming from anyone with a testing background, that is a distinctive and genuinely useful observation, and few candidates make it.

Q12Responsible use: bias, explainability and governance▼

For a consultancy advising public bodies, this is a client-facing requirement, not a philosophical one.

  • Bias comes from data. If historical inspections concentrated on certain regions, the model learns that those assets fail more — because those are the only ones anyone looked at. Evaluate performance per slice, not just overall.
  • Explainability. Feature importance, SHAP values, or a simpler model where a decision must be justified. "The model said so" is not an acceptable answer to a client asking why an asset was prioritised.
  • Human in the loop for consequential decisions. The model recommends; a qualified engineer decides. That is both the right design and the one that survives professional liability scrutiny.
  • Documentation — what the model is for, its limitations, the data it was trained on, when it should not be used.
  • Auditability — reproduce any past prediction from versioned inputs and artefacts.
"In an engineering consultancy the model is advice to a professional who carries the responsibility for the decision. That shapes the design: it has to be explainable and auditable, and it has to be clear that it recommends rather than decides."

Q13Walking through an ML project — the structure that works▼

Any project involving a model will be asked about. Prepare the walkthrough once and reuse it, with real numbers — the specifics matter far more than the structure.

BeatWhat to say
The problem, in business termsWhat decision does the prediction support, and what does being wrong cost in each direction?
The dataSource, volume, class balance, and the labelling problem. Name the class imbalance explicitly if there is one — it drives the metric choice.
FeaturesWhat was engineered and why. Name one that mattered and one that turned out to be leakage or noise.
Model and metricWhat you chose, what you compared against, and why that metric for this cost structure.
ServingReal-time endpoint, latency achieved, containerised, how it is deployed.
MonitoringWhat is watched, and what would reveal that the model had gone stale.
One hard problemThe genuinely difficult part. Threshold selection, imbalance handling, or preprocessing parity are all good, real answers.
What you'd changeOne honest improvement. Every project has one; claiming none is the wrong answer.
Scale the claim to the project. If it is a side project, say so: "the data volume and operational pressure aren't comparable to production — what it gave me is the full path from data to a deployed, monitored endpoint, and a clear view of which parts are hard." That framing is more persuasive than inflating it, because interviewers can tell, and the follow-up questions expose it immediately.
