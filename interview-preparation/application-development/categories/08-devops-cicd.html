SECTION 1

Version control and delivery

"Strong version control and DevOps practices (Git, Azure DevOps, CI/CD pipelines)" appears in almost every job description on this stack. If you have built pipelines in Jenkins or GitHub Actions, the only real gap is Azure DevOps's vocabulary for concepts you already know.

PrimerJenkins to Azure DevOps, translated

You have designed and maintained pipelines. Azure DevOps is a different product with the same concepts. Learn the mapping and you can speak about it fluently and honestly.

ConceptJenkinsAzure DevOps
Pipeline definitionJenkinsfile (Groovy)azure-pipelines.yml (YAML)
Where it runsAgent / nodeAgent pool — Microsoft-hosted or self-hosted
GroupingStage → stepStage → job → step (jobs can run in parallel)
Reusable logicShared libraryTemplate (extends / template:)
CredentialsCredentials pluginVariable group linked to Key Vault, or a service connection

Manual approvalinput stepEnvironment with approval checks
Cloud accessCredentials + CLIService connection (a service principal or workload identity)
TriggersWebhook / polltrigger: (CI) and pr: (pull request) blocks

The five Azure DevOps services

ServiceWhat it is
BoardsWork items, backlogs, sprints, boards. Where stories live.
ReposGit hosting, with branch policies — required reviewers, required builds, linked work items, comment resolution.
PipelinesCI/CD. YAML pipelines are the current standard; classic release pipelines are legacy.

How to open this topic if your pipeline experience is elsewhere. "My pipeline experience is mostly Jenkins and GitHub Actions rather than Azure DevOps, but the model maps directly — stages and jobs, agent pools instead of nodes, variable groups backed by Key Vault instead of the credentials plugin, and environments with approval checks instead of an input step. What I'd bring is the design side: owning a pipeline end to end, including the unglamorous parts — keeping it under ten minutes, and keeping the test suite trustworthy enough that a red build actually stops people." Confident, specific, and it does not overstate.
Q1Which branching strategy, and why?▼
StrategyHow it worksFits
Trunk-basedShort-lived branches off main, merged within a day or two, behind feature flags if incompleteContinuous delivery. The modern default.
GitHub flowBranch → PR → merge → deploy. Essentially trunk-based with a PR gateMost web teams
GitFlowdevelop, release/*, hotfix/*, feature/*Versioned software with scheduled releases and supported older versions. Heavy for a continuously deployed service.
Release branchesTrunk-based plus a branch cut per releaseWhen you must support several versions in the field simultaneously
"I'd default to trunk-based with short-lived branches and a required PR. Long-lived branches are where merge pain comes from, and they hide integration problems until the worst possible moment. If a feature is too big to finish in two days, that's an argument for a feature flag, not for a three-week branch."
The senior addition: the branching strategy should follow the release cadence. If a client contract means quarterly releases with supported older versions, GitFlow or release branches are the honest answer, not a failure of modernity. Showing you would ask about release cadence first is better than naming a favourite.

Q2Merge, rebase, squash — and the Git commands you should have used▼
OperationResultRule
MergeMerge commit; true history preservedUse for shared branches
RebaseYour commits replayed on top; linear historyOnly on your own unpushed work — it rewrites history
Squash mergeThe whole branch becomes one commit on mainGood default for feature branches: clean history, one revertable unit
git switch -c feature/asset-scoring        # create and switch
git rebase -i main                        # tidy your own commits before the PR
git revert <sha>                          # safe undo — a new commit, history intact
git reset --soft HEAD~1                   # uncommit, keep changes staged
git cherry-pick <sha>                     # move one commit to a release branch
git bisect start / bad / good <sha>       # binary search for the breaking commit
git stash push -m "wip"                   # park changes
git reflog                                # find a commit you thought you destroyed
git log --oneline --graph --all           # see the actual shape of history
The question behind the question: "you've pushed a secret to the repository — what do you do?" The answer is rotate the secret first. Rewriting history is secondary housekeeping: it is already in every clone, in CI caches, and possibly already scraped. Candidates who lead with filter-branch instead of rotation are missing the point, and interviewers know it.
git reflog is the answer to "I've lost my commits". Almost nothing is truly gone for 30 days. Having actually used it is a nice small credibility marker.

Q3What makes a good pull request, and a good review?▼
As the author
  • Small. Under ~400 lines gets a real review; 2,000 lines gets an approval and a thumbs-up emoji. This is the single biggest lever on review quality.
  • One concern per PR. A refactor mixed with a behaviour change is unreviewable — the reviewer cannot tell which diff lines matter.
  • A description that says why, links the work item, and notes anything you are unsure about. Point reviewers at the risky part.
  • Green build, tests included, self-reviewed first. Read your own diff before asking anyone else to.
As the reviewer

Priority order: correctness → security → design fit → tests → readability → style (automated). Beyond the checklist, the behaviour matters:

  • Ask questions rather than issue instructions — "what happens if this list is empty?" rather than "handle the empty case".
  • Mark severity: must fix vs suggestion vs nitpick. Without it, every comment feels blocking and reviews become adversarial.
  • Approve with minor comments rather than blocking on trivia.
  • Take anything contentious to a five-minute call. A twelve-comment thread is a conversation that should have happened out loud.
  • Say what is good, not only what is wrong.
Branch policies make this enforceable in Azure Repos: minimum reviewers, a required successful build, linked work items, comment resolution required, and auto-reset approvals on new pushes. Naming those is the concrete half of the answer.

Q4Write an Azure Pipelines YAML file▼
trigger:
  branches: { include: [ main ] }
pr:
  branches: { include: [ main ] }

variables:
  - group: shared-secrets          # linked to Key Vault
  - name: imageName
    value: assets-api

stages:
- stage: Build
  jobs:
  - job: BuildTest
    pool: { vmImage: ubuntu-latest }
    steps:
    - task: UsePythonVersion@0
      inputs: { versionSpec: '3.12' }
    - script: pip install -r requirements.txt -r requirements-dev.txt
      displayName: Install dependencies
    - script: ruff check . && mypy src
      displayName: Lint and type check
    - script: pytest --junitxml=junit.xml --cov=src --cov-report=xml
      displayName: Unit tests
    - task: PublishTestResults@2
      condition: succeededOrFailed()          # publish results even when tests fail
      inputs: { testResultsFiles: junit.xml }
    - task: PublishCodeCoverageResults@2
      inputs: { summaryFileLocation: coverage.xml }
    - task: Docker@2
      inputs:
        command: buildAndPush
        repository: $(imageName)
        containerRegistry: acr-connection
        tags: |
          $(Build.BuildId)
          latest

- stage: DeployDev
  dependsOn: Build
  jobs:
  - deployment: Dev
    environment: dev                          # no approval
    strategy:
      runOnce:
        deploy:
          steps:
          - template: templates/deploy-container-app.yml
            parameters: { envName: dev, tag: $(Build.BuildId) }

- stage: DeployProd
  dependsOn: DeployDev
  condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
  jobs:
  - deployment: Prod
    environment: production                   # approval check configured here
    strategy:
      runOnce:
        deploy:
          steps:
          - template: templates/deploy-container-app.yml
            parameters: { envName: prod, tag: $(Build.BuildId) }
What to point out while explaining it
  • Build once. The image is built in Build and the same tag is promoted through every environment. Rebuilding per environment means production runs something nobody tested.
  • The approval lives on the environment, not in the YAML — so approvers can be changed without a code change, and the audit trail is in one place.
  • condition: succeededOrFailed() on test publishing, or a failing run shows you nothing about why.
  • Secrets come from a variable group linked to Key Vault, never from literals.
  • Templates keep deployment logic in one place across services.

GateStops
Compile / buildThe obvious
Lint + format checkStyle debate in code review

The opinion that shows experience: a gate that is frequently overridden is worse than no gate, because it trains the team to ignore red. Either make it blocking and keep it trustworthy, or make it advisory and stop pretending. The same is true of flaky tests — a suite people re-run until it passes provides no signal at all.
This is the argument you can make better than anyone else in the room. You have watched teams lose faith in a test suite. Say what you did about it — quarantine policy, flake tracking, deleting tests that never caught anything.

Q6Deployment strategies and zero-downtime database changes▼
StrategyMechanismRollback
RollingReplace instances in batchesRoll forward, or redeploy the previous version
Blue-greenTwo full environments, switch at the router. In App Service this is a slot swapSwap back — seconds
CanarySmall traffic percentage to the new version, watch metrics, ramp. Container Apps does this with revision traffic weightsSet the weight back to zero
Feature flagsDeploy dark, enable separatelyTurn the flag off — no deployment at all
The database question, which is the real one

During any of these, two versions of the code run at once. So the schema must work with both. Use expand / contract:

  1. Expand — add the new column as nullable. Deploy. Nothing reads it yet.
  2. Dual write — new code writes both old and new; still reads the old.
  3. Backfill — migrate historical rows in batches, out of hours if large.
  4. Switch reads to the new column. Deploy. Verify.
  5. Contract — in a later release, stop writing the old column and drop it.

Rename in one step and you get errors for the whole rollout window, and a rollback that cannot work.

Say this: "Migrations run as a separate pipeline step before the app deploys, they're versioned in the repository (Alembic, EF migrations, Flyway), and they're forward-only. Rolling back a schema is far riskier than rolling forward, so I'd design the change so it never needs a rollback."

Q7Feature flags — the benefits and the debt▼

Flags decouple deploy (technical, low risk, frequent) from release (a business decision). That lets you merge incomplete work to main safely, run a canary by user segment, A/B test, and kill a broken feature in seconds without a rollback.

Types worth distinguishing: release toggles (short-lived, removed once shipped), ops toggles (a kill switch for an expensive feature under load), permission toggles (long-lived, effectively entitlements).

The cost, which you should volunteer: every flag doubles the paths through the code, and combinations multiply. Untidied flags become permanent conditional complexity that nobody dares remove. The discipline is a removal ticket created with the flag and an owner — release toggles are temporary by definition. On Azure: App Configuration provides managed feature flags.

SECTION 2

Running it: observability, incidents and performance

"Debugging, testing and addressing performance issues" is a JD line, and this is the section where your background is worth the most.

Q8What do you monitor, and what do you alert on?▼

Two useful frameworks, both worth naming:

RED (per service)USE (per resource)
Rate — requests per secondUtilisation — how busy
Errors — failure rateSaturation — queue depth, how much work is waiting
Duration — latency distribution, p50/p95/p99Errors — hardware or resource errors

Alert on symptoms, not causes. "Error rate above 2% for five minutes" is actionable; "CPU above 80%" usually is not — high CPU with healthy latency is a machine doing its job.

The failure mode to name: alert fatigue. If a channel produces forty notifications a day, nobody reads the one that matters. Every alert should be actionable, have a documented response, and page a human only if it needs a human right now. Everything else is a dashboard or a ticket. Being able to say this shows you have been on a rota, or at least understand what one is for.
SLI / SLO / error budget: an SLI is the measurement ("99.2% of requests under 500 ms"), an SLO is the target, and the error budget is the allowed shortfall. It turns "is it reliable enough?" into a number both engineering and the business can argue about — and it is what justifies pausing features to fix stability.

Q9"Production is slow. Walk me through it."▼

Structure matters more than the specific tools. Say the structure first.

  1. Scope it. Everything or one endpoint? All users or one tenant? Since when — and what changed at that time? A deployment, a data volume change, a traffic spike, a dependency?
  2. Look at the percentiles. p50 rising means a systemic slowdown; only p99 rising means a subset — a particular tenant's data volume, a lock, or a cold cache.
  3. Open one slow trace. The end-to-end transaction view tells you immediately whether the time is in your code, the database, or a downstream call. This step replaces most guessing.
  4. If it is the database: query count (N+1), execution plan, missing index, lock waits, connection pool exhaustion.
  5. If it is your code: serialising too much, synchronous I/O in a loop, no pagination, blocking the event loop, GC pressure.
  6. If it is infrastructure: CPU or memory saturation, throttling (Cosmos RU limits, SQL DTU), cold starts, a noisy neighbour, cross-region calls.
  7. Mitigate, then fix. Scale out or roll back to stop the bleeding, then find the root cause properly. Do not debug in the middle of an incident when you can restore service first.
  8. Add the alert you wished you had and write it up.
Land the framing: "The most valuable thing I learned doing performance work is that the bottleneck is almost never where the team assumes it is — so I won't change anything until I have a profile or a trace pointing at it." Then give a real example with numbers. This should be one of the two or three strongest answers you give all day.

Q10"You broke production. What do you do?"▼
  1. Restore service first. Roll back, swap the slot, turn off the flag. Do not debug while users are affected — diagnosis can happen after.
  2. Communicate immediately. Tell the team and whoever owns the stakeholder relationship, before they find out from a client. In a consultancy this matters as much as the fix.
  3. Fix properly, with a test that would have caught it.
  4. Blameless postmortem. What happened, timeline, why the safeguards did not catch it, what changes. Actions with owners and dates.
The word to use is "blameless". The point is that if people fear blame, they hide problems and you lose the information. And the useful question is never "who pushed it" but "how did a change like this reach production without being caught?" — that is a systems answer and it is what senior engineers give.
Have a real story ready. Something you broke, how you handled it, what changed afterwards. Candidates who claim they have never broken anything have either not shipped much or are not being straight.

Q12The DORA metrics, and what they are for▼
MetricMeaning
Deployment frequencyHow often you release. Higher means smaller, safer changes.
Lead time for changeCommit to production. Measures the whole pipeline, including review and approval queues.
Change failure rateShare of deployments causing a problem.
Mean time to restoreHow fast you recover.

The insight that makes them worth quoting: speed and stability move together, not against each other. Teams that deploy frequently deploy small changes, and small changes are easier to review, test and revert.

Add the caveat. These are team health indicators, not individual performance measures. The moment they are used to rank people they get gamed, and you lose both the metric and the trust. Volunteering that shows maturity about metrics generally.
