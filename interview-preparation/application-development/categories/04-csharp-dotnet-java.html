Positioning, and the Java you already have

Many enterprises on this stack are Microsoft shops, so C# is often in play — but these job descriptions almost always say "or". Knowing how the two stacks map onto each other lets you answer confidently on either side.

PrimerThe two stacks are the same stack with different names

If you know Spring Boot conceptually, you know ASP.NET Core, and vice versa. They solve identical problems with near-identical architecture. Learning the mapping is a couple of hours and it lets you answer a C# question honestly without ever having shipped C#.

How to say this in the room

"My production language is Java — Spring Boot is the model I think in. I read C# comfortably and I've worked through the .NET equivalents, because the architecture maps almost one to one: DI container, middleware pipeline, EF Core instead of JPA. I'd expect to be productive in C# quickly, but I wouldn't claim to have shipped it."

That answer is honest, demonstrates the knowledge, and pre-empts the "so you don't know C#" objection by showing you already did the mapping. It is much stronger than either bluffing or saying "no".

The perennial follow-up: equals and hashCode. Override them together. Two objects that are equal must have the same hash code, or a HashMap lookup will fail to find an object you just put in. Also: a mutable field used in hashCode means mutating the object after insertion makes it unfindable — the object is in the map, in the wrong bucket.

Q2Java streams — and where they are the wrong tool▼
Map<Long, List<Asset>> bySite = assets.stream()
    .filter(Asset::isActive)
    .sorted(Comparator.comparing(Asset::getName))
    .collect(Collectors.groupingBy(Asset::getSiteId));

Optional<Asset> worst = assets.stream()
    .min(Comparator.comparingDouble(Asset::getScore));

double average = assets.stream()
    .mapToDouble(Asset::getScore)
    .average()
    .orElse(0.0);

Streams are lazy — nothing runs until a terminal operation (collect, forEach, reduce, count). Intermediate operations just build the pipeline.

The senior nuance: parallelStream() is not free concurrency. It uses the common ForkJoin pool, so one slow parallel stream can starve others, and it is a net loss for small collections or I/O-bound work. Use it only for large, CPU-bound, side-effect-free computation — and measure. Candidates who suggest parallelStream as a general performance fix reveal a lot.

Q3Checked vs unchecked exceptions, and how to design them▼

Checked (extends Exception) must be declared or caught — the compiler enforces it. Unchecked (extends RuntimeException) need not be.

Modern practice leans heavily toward unchecked for application code, because checked exceptions force every intermediate layer to declare things it cannot handle, and the result is usually a catch that wraps and rethrows or, worse, swallows.

The design answer: throw a domain exception (AssetNotFoundException), let it propagate, and map it to an HTTP status in one place — a @ControllerAdvice in Spring, exception middleware in ASP.NET Core. Business logic should not know what a 404 is.
C# has no checked exceptions at all — a reasonable thing to mention as a deliberate language design difference, since it shows you have compared the two rather than just used one.

Q4Spring Boot: how a request actually flows▼
@RestController
@RequestMapping("/v1/assets")
public class AssetController {

    private final AssetService service;                 // constructor injection

    public AssetController(AssetService service) {      // no @Autowired needed
        this.service = service;
    }

    @GetMapping("/{id}")
    public AssetDto get(@PathVariable Long id) {
        return service.findById(id)
                      .orElseThrow(() -> new AssetNotFoundException(id));
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public AssetDto create(@Valid @RequestBody CreateAssetRequest request) {
        return service.create(request);
    }
}

@RestControllerAdvice
public class ErrorHandler {
    @ExceptionHandler(AssetNotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public ProblemDetail handle(AssetNotFoundException ex) { ... }
}
AnnotationRole
@SpringBootApplicationConfig + component scan + auto-configuration on the main class
@RestControllerController whose returns are serialised to the body
@Service / @Repository / @ComponentRegisters a bean for injection
@ValidTriggers bean validation on the request body — a 400 with field errors
@TransactionalWraps the method in a database transaction
@ProfileBean active only in a named environment
Say "constructor injection, not field injection". Constructor injection makes dependencies explicit and required, keeps fields final, and lets you build the object in a test without a Spring context. @Autowired on a field is a legacy pattern and interviewers notice which one you reach for.

Q5What does Spring Boot's auto-configuration actually do?▼

Spring Boot inspects the classpath and configures sensible defaults conditionally: if it finds an H2 driver and no configured DataSource, it creates an in-memory one; if it finds Spring MVC, it configures an embedded Tomcat. Every auto-configuration is guarded by @ConditionalOnClass / @ConditionalOnMissingBean, so anything you define yourself wins.

That is the whole "convention over configuration" claim: a dependency on spring-boot-starter-web replaces several hundred lines of XML.

Mention Actuator — /actuator/health, /actuator/metrics, /actuator/info. These are exactly the liveness and readiness endpoints a container platform needs, which ties this answer straight back to cloud-native.

Q6JPA: entity states, lazy loading and the N+1 problem▼

An entity is transient (new, unknown to the persistence context), managed (attached — changes are flushed automatically at commit), detached (was managed, the context closed), or removed.

Lazy loading defers fetching an association until it is touched. Two failure modes, both extremely common interview material:

  • N+1 queries — loading 100 sites then touching site.getAssets() in a loop issues 101 queries. Fix with JOIN FETCH, an entity graph, or a batch size.
  • LazyInitializationException — serialising a detached entity outside the transaction. The real fix is to return a DTO shaped for the API rather than exposing entities directly, which also stops your database schema leaking into your public contract.
@Query("select s from Site s join fetch s.assets where s.region = :region")
List<Site> findByRegionWithAssets(@Param("region") String region);
Never return entities from controllers. It couples your API to your schema, triggers lazy loads during serialisation, and leaks fields you did not intend to publish. This is a strong opinion worth holding.

Q8An ASP.NET Core minimal API, end to end▼
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddDbContext<AppDb>(o =>
    o.UseSqlServer(builder.Configuration.GetConnectionString("Default")));
builder.Services.AddScoped<IAssetService, AssetService>();
builder.Services.AddHealthChecks();
builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();

var app = builder.Build();

app.UseExceptionHandler();          // order matters — this is a pipeline
app.UseAuthentication();
app.UseAuthorization();
app.MapHealthChecks("/health");

app.MapGet("/v1/assets/{id:int}", async (int id, IAssetService svc) =>
    await svc.FindAsync(id) is { } asset
        ? Results.Ok(asset)
        : Results.NotFound());

app.MapPost("/v1/assets", async (CreateAssetRequest req, IAssetService svc) =>
{
    var created = await svc.CreateAsync(req);
    return Results.Created($"/v1/assets/{created.Id}", created);
});

app.Run();
  • Middleware order is the behaviour. Authentication before authorisation; exception handling first so it wraps everything. A misordered pipeline is a classic bug and a classic question.
  • Service lifetimes: AddSingleton (one per application), AddScoped (one per request — correct for a DbContext), AddTransient (a new one each time).
  • Configuration layers in order: appsettings.json → appsettings.{Environment}.json → environment variables → Key Vault. Later sources override earlier ones, which is exactly the twelve-factor model.
The lifetime trap: injecting a scoped DbContext into a singleton. It is captured on the first request and reused forever — stale data, a leaked connection, and cross-request data exposure. ASP.NET Core will actually throw on this in development, which is worth knowing.

Q9Entity Framework Core: tracking, and the queries that surprise people▼
// read-only query — skip change tracking for a measurable speed-up
var assets = await db.Assets
    .AsNoTracking()
    .Include(a => a.Site)                 // eager load; avoids N+1
    .Where(a => a.SiteId == siteId && a.ConditionScore < 50)
    .OrderBy(a => a.Name)
    .Skip(offset).Take(limit)
    .Select(a => new AssetDto(a.Id, a.Name, a.ConditionScore))   // projection
    .ToListAsync();
  • Change tracking is how SaveChanges knows what to update. Turn it off with AsNoTracking() for reads — it is one of the cheapest wins available.
  • Include is EF's JOIN FETCH. Without it, lazy loading gives you N+1.
  • Projection with Select means the database only returns the columns you need.
  • Migrations — dotnet ef migrations add, applied in the pipeline, not by EnsureCreated at startup.
The client-evaluation trap: a Where containing something EF cannot translate to SQL. Older versions silently pulled the whole table into memory and filtered there; EF Core now throws instead. Either way, know that a LINQ query against IQueryable and one against IEnumerable are completely different things — the first becomes SQL, the second runs in your process.

Q10async/await in C#: what to know and what to avoid▼

await frees the thread while I/O is in flight, so a server handles far more concurrent requests with the same thread pool. Async in C# is about throughput, not about making one request faster.

Three things that get asked:
  • Never .Result or .Wait() on a task — it blocks a thread and, in some contexts, deadlocks. Async all the way up.
  • async void only for event handlers — exceptions from it cannot be caught and will crash the process. Use async Task.
  • Task.WhenAll for independent work, exactly like Promise.all and asyncio.gather. Awaiting in a loop is sequential.
Three languages, one idea. Promise.all / asyncio.gather / Task.WhenAll are the same tool. Saying that in an interview demonstrates that you understand the concept rather than one syntax, and it makes your multi-language claim credible.

Q11Garbage collection and memory — what a developer should know▼

Both runtimes use generational, tracing collectors: most objects die young, so the collector scans a small "young generation" frequently and the older ones rarely. You do not manage memory, but you can still leak it.

How a managed language still leaks
  • A static or singleton collection that only ever grows — a cache with no eviction.
  • Event handlers or listeners never unsubscribed, keeping the subscriber alive.
  • Unclosed resources — connections, streams, HTTP clients. Use try-with-resources / using.
  • A ThreadLocal not cleared on a pooled thread, so the value survives into the next request that reuses that thread.
Coming from test automation → that last one is a genuine automation gotcha; if you have used ThreadLocal<WebDriver> for parallel execution you have met exactly this class of bug. It is a good, specific story.
If asked how you'd diagnose one: watch memory over time under steady load — a sawtooth that never returns to baseline is a leak — then take a heap dump and compare two snapshots to find the type that keeps growing.

Q12Job descriptions say "Python, JavaScript, C# or Java" — how do you position that?▼

You do not need all four. You need one you are deep in, one you are fluent in, and the rest at reading literacy. Decide which is which before the interview and stay consistent across every round — a mismatch between the screening call and the technical round gets noticed.

A useful way to grade your own claim, because each level commits you to something:

ClaimWhat it commits you to
StrongestA live coding problem, questions on concurrency and memory, and an opinion on its ecosystem's frameworks.
FluentWriting idiomatic code unaided and explaining the runtime model.
LiterateReading it confidently and explaining how its stack maps onto one you do know. Say plainly that you have not shipped it in production.

The literate tier is the useful one, and it is worth stating explicitly rather than dodging: "I read C# comfortably and I understand the .NET model — DI container, middleware pipeline, EF Core. I haven't shipped production C#, but the mapping from Spring Boot is close enough that I'd be productive quickly." That is a bounded, checkable claim, and the mapping table at the top of this page is what makes it true rather than aspirational.

The failure mode is over-claiming. "I know all four" invites a whiteboard problem in the one you know least, and the recovery from that is very difficult. A confident, bounded claim plus a demonstrated ability to map concepts across languages reads as more senior, not less.
