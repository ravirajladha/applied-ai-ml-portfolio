SECTION 1

The language: JavaScript and TypeScript

You already write TypeScript daily. This section closes the gap between test TypeScript and application TypeScript — which is smaller than you think.

PrimerWhat changes when TypeScript stops being test code

Your Playwright work already gave you the hard parts: async/await, typed function signatures, module imports, npm, and the mental model of a single-threaded event loop. Four things are genuinely different on the application side.

1. You define the types instead of consuming them

In test code the types mostly come from Playwright. In application code you design the domain types — and the quality of those types is a large part of how maintainable the codebase is. Expect to be asked to model something, not just to use a model.

2. Runtime data does not obey your types

TypeScript types are erased at compile time. A response from an API is any in reality no matter what you annotate it as. Professional codebases therefore validate at the boundary — zod or similar — and trust types only inside. This is the single most important thing to say about TypeScript in an interview, because it shows you understand what the type system is and is not.

import { z } from "zod";

const AssetSchema = z.object({
  id: z.number(),
  name: z.string().min(1),
  conditionScore: z.number().min(0).max(100),
});
type Asset = z.infer<typeof AssetSchema>;      // the type is derived from the validator

const asset = AssetSchema.parse(await res.json());   // throws on a malformed response

3. There is rendering, and rendering has its own rules

A UI framework re-runs your code when data changes. Understanding when and why it re-renders is the front-end equivalent of understanding the request lifecycle.

4. CSS and accessibility are part of the job

The JD explicitly says "translating design wireframes and mockups into responsive, interactive web and mobile applications". Most backend-leaning candidates prepare nothing here and lose marks that were free. Section 3 of this page covers it.

Coming from test automation → you have an unusual advantage in front-end interviews: you know exactly which UI patterns are hard to test, which selectors are stable, and what an accessible DOM looks like — because you have written the locators. "I write components with stable roles and labels, partly because it's the accessible thing and partly because I've spent years fighting UIs that weren't" is a very strong sentence.
Q1The event loop: call stack, microtasks, macrotasks▼

JavaScript executes on one thread. The call stack runs synchronous code. When asynchronous work is started, the environment (browser or Node) handles it and puts the callback on a queue. When the stack empties, the event loop takes the next callback.

Microtasks (promise callbacks, queueMicrotask) drain completely before the next macrotask (setTimeout, I/O events).

console.log("1");
setTimeout(() => console.log("2"), 0);      // macrotask
Promise.resolve().then(() => console.log("3"));  // microtask
console.log("4");
// 1, 4, 3, 2

Why it matters practically: blocking the loop blocks everything. A synchronous one-second computation in a Node service freezes every concurrent request, not just one.

Q2Promises and async/await — including the parallelism trap▼
// sequential — 20 items × 200 ms = 4 seconds
for (const id of ids) {
  results.push(await fetchAsset(id));
}

// concurrent — about 200 ms
const results = await Promise.all(ids.map(fetchAsset));

// concurrent, tolerant of individual failures
const settled = await Promise.allSettled(ids.map(fetchAsset));
const ok = settled.filter(r => r.status === "fulfilled").map(r => r.value);
CombinatorBehaviour
Promise.allResolves when all resolve; rejects immediately if any rejects
Promise.allSettledAlways resolves, with a status per promise
Promise.raceSettles with the first to settle — used for timeouts
Promise.anyFirst to fulfil; ignores rejections until all fail
Two traps they will look for: an unhandled rejection because you forgot to await or catch (in Node this can terminate the process), and firing 10,000 concurrent requests with Promise.all and exhausting sockets or being rate-limited. For large sets, batch with a concurrency limit — mentioning that unprompted is a senior signal.

Q3The ES6+ features you are expected to use fluently▼
const { name, siteId: site = 0, ...rest } = asset;      // destructuring + rename + default + rest
const merged = { ...defaults, ...overrides };          // spread
const label = `Asset ${asset.name} (${asset.id})`;     // template literal

The classic question: ?? vs ||. || falls back on any falsy value, so 0 || 10 gives 10 — a real bug when 0 is a legitimate score. ?? falls back only on null or undefined, so 0 ?? 10 gives 0. Use ?? for defaults.
Arrow functions vs function: arrows do not have their own this — they inherit it from the enclosing scope. That is why they fixed the old const self = this pattern, and why an arrow is wrong as an object method that needs to reference the object.

Q4TypeScript: type vs interface, and when it matters▼
interface Asset {              // can be extended and re-opened (declaration merging)
  id: number;
  name: string;
}
interface TrackedAsset extends Asset { lastInspected: Date; }

type Status = "draft" | "active" | "retired";        // union — impossible with interface
type AssetWithStatus = Asset & { status: Status };   // intersection
type AssetKeys = keyof Asset;                        // "id" | "name"

Rule of thumb: interface for object shapes you may extend, type for everything else — unions, intersections, tuples, mapped and conditional types. In practice teams pick one for consistency; what matters in an interview is knowing that unions and mapped types are type-only.

Utility types worth naming: Partial<T>, Required<T>, Pick<T,K>, Omit<T,K>, Record<K,V>, Readonly<T>, ReturnType<F>. Omit and Partial come up constantly in real code — type AssetUpdate = Partial<Omit<Asset, "id">> is exactly the shape of a PATCH body.

Q5Discriminated unions and narrowing — the pattern that shows real TypeScript▼
type Result =
  | { kind: "ok"; data: Asset[] }
  | { kind: "error"; message: string; retryable: boolean };

function render(result: Result) {
  switch (result.kind) {
    case "ok":
      return list(result.data);        // TypeScript knows .data exists here
    case "error":
      return banner(result.message);   // and .message here, but not .data
  }
}

The literal kind field lets the compiler narrow the type inside each branch. This is how you model "one of several shapes" without optional fields everywhere, and it makes illegal states unrepresentable — you cannot accidentally read data from an error.

The advanced follow-on: add a default branch that assigns to never. If someone later adds a third variant, the code stops compiling until it is handled — exhaustiveness checking enforced by the type system.
default: {
  const _exhaustive: never = result;
  throw new Error(`unhandled: ${JSON.stringify(_exhaustive)}`);
}

Q6Generics, and why any is a smell▼
async function getJson<T>(url: string, schema: z.ZodType<T>): Promise<T> {
  const res = await fetch(url);
  if (!res.ok) throw new ApiError(res.status, url);
  return schema.parse(await res.json());
}

const assets = await getJson("/v1/assets", z.array(AssetSchema));  // typed as Asset[]

A generic preserves the relationship between input and output types instead of discarding it. Compare with returning any, which switches type checking off for everything downstream — the bug does not surface at the cast, it surfaces three files away.

If you need an escape hatch, use unknown, not any. unknown forces you to narrow before use; any silently disables checking. Also mention strict: true in tsconfig.json — particularly strictNullChecks, which is what makes TypeScript actually catch the null bugs it is famous for preventing.

One of the languages these roles list. Worth being able to describe a Node service even if Python or C# is your primary answer.

Q7What is Node.js, and what is it bad at?▼

A JavaScript runtime built on V8 with an event-driven, non-blocking I/O model. One thread runs your code; a thread pool underneath handles file system and some crypto work.

Good at: many concurrent I/O-bound connections — APIs, gateways, streaming, real-time with WebSockets. Bad at: CPU-bound work, which blocks the single loop and degrades every concurrent request. Push that to a worker thread, a separate service, or a different runtime.

Scaling: the cluster module or a process manager runs one Node process per core; in containers you simply run more replicas. Same conclusion as Python — horizontal, not threaded.

Q8An Express API with the things that are usually missing▼
import express from "express";
import helmet from "helmet";
import { z } from "zod";

const app = express();
app.use(helmet());                 // security headers
app.use(express.json({ limit: "1mb" }));
app.use(correlationId);            // custom middleware, sets req.correlationId

const CreateAsset = z.object({
  name: z.string().min(1).max(120),
  siteId: z.number().int().positive(),
});

app.post("/v1/assets", async (req, res, next) => {
  try {
    const body = CreateAsset.parse(req.body);          // 400 on bad input
    const created = await assetService.create(body);
    res.status(201).location(`/v1/assets/${created.id}`).json(created);
  } catch (err) {
    next(err);                                          // delegate to the error handler
  }
});

// error middleware must have four parameters — this is how Express identifies it
app.use((err, req, res, _next) => {
  const status = err instanceof z.ZodError ? 400 : err.status ?? 500;
  if (status >= 500) logger.error({ err, correlationId: req.correlationId });
  res.status(status).json({ title: err.name, status, traceId: req.correlationId });
});
The Express trap: an error thrown inside an async handler is not caught by Express 4 automatically — you must call next(err) or wrap the handler. Forgetting it produces a request that hangs until it times out, with nothing in the logs. Express 5 fixes this; knowing the difference is a good detail.
If asked about NestJS: it is an opinionated framework over Express with decorators, modules and dependency injection — structurally very close to Spring Boot or ASP.NET Core. Choose it for a larger team that benefits from imposed structure; plain Express for a small service.

SECTION 3

From wireframe to responsive UI

The JD line most candidates skip entirely. Preparing this is nearly free marks.

PrimerLayout, from zero

The box model

Every element is a box: content, padding, border, margin. By default width means the content only, so padding and border are added on top — which is why layouts overflow. Every modern codebase starts with *{box-sizing:border-box} so width includes padding and border. Knowing that one line and why it exists is a real front-end signal.

Flexbox — one dimension

For a row or a column: toolbars, card contents, form rows, anything that should sit in a line and wrap.

.toolbar {
  display: flex;
  gap: 12px;                    /* replaces margin hacks */
  align-items: center;          /* cross axis */
  justify-content: space-between; /* main axis */
  flex-wrap: wrap;              /* allow wrapping on narrow screens */
}
.toolbar .spacer { flex: 1; }   /* grow to fill remaining space */

Grid — two dimensions

For page layouts and card grids. The single most useful line in responsive CSS:

.cards {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(260px, 1fr));
  gap: 16px;
}

That produces as many columns as fit, each at least 260px, sharing space equally — a fully responsive card grid with no media queries at all. Being able to write it from memory is worth more than reciting the flexbox property list.

Mobile-first breakpoints

/* base styles = smallest screen */
.layout { display: grid; grid-template-columns: 1fr; }

@media (min-width: 768px)  { .layout { grid-template-columns: 220px 1fr; } }
@media (min-width: 1200px) { .layout { grid-template-columns: 260px 1fr 300px; } }

Write the small screen first and add complexity upward with min-width. The reverse — designing for desktop and stripping away — produces layouts that carry desktop weight onto phones, and it is what interviewers mean when they ask "mobile-first".

Design tokens

Put the design system's decisions in one place so the whole UI changes together, and so dark mode is a variable swap rather than a rewrite:

:root {
  --space-2: 8px;  --space-3: 12px;  --space-4: 16px;
  --color-ink: #161a22;  --color-accent: #4338ca;
  --radius: 12px;
}
.card { padding: var(--space-4); border-radius: var(--radius); }
Q9"Walk me through turning a Figma mockup into a working screen."▼

Give them a process. The process is the answer; the CSS is incidental.

  1. Inventory the components. Go through the mockup and mark what repeats — button, card, field, table row, empty state. Build those first as reusable components, then compose screens from them. Building screen-by-screen is how you end up with nine slightly different buttons.
  2. Extract the tokens. Spacing scale, type scale, colours, radii, breakpoints, into CSS variables or the theme file. Agree them with the designer once.
  3. Ask for the states the mockup does not show. Loading, empty, error, no permission, very long text, 500 rows, offline. Designers hand over the happy path; asking this question in the interview is itself the strong signal.
  4. Build mobile-first, semantic HTML first, then layout, then polish.
  5. Wire the data with explicit loading and error handling — no screen that shows nothing while it waits.
  6. Check accessibility as you go, not at the end.
  7. Review against the design at real breakpoints on a real device, and walk the designer through it before it reaches QA.
The collaboration point they are testing: a good developer pushes back on a design that is expensive for no user benefit, and offers the cheap alternative. "This layout needs a custom scroll behaviour that will break on mobile Safari — here's a version that gets 95% of it for a tenth of the effort" is what they want to hear.

Q10React fundamentals: components, props, state, keys▼
type Props = { siteId: number; onSelect: (a: Asset) => void };

export function AssetList({ siteId, onSelect }: Props) {
  const [assets, setAssets] = useState<Asset[]>([]);
  const [status, setStatus] = useState<"loading" | "ready" | "error">("loading");

  useEffect(() => {
    const controller = new AbortController();
    getJson(`/v1/assets?siteId=${siteId}`, z.array(AssetSchema), controller.signal)
      .then(data => { setAssets(data); setStatus("ready"); })
      .catch(err => { if (err.name !== "AbortError") setStatus("error"); });
    return () => controller.abort();      // cleanup — cancels if siteId changes or unmounts
  }, [siteId]);                            // dependency array: re-run when siteId changes

  if (status === "loading") return <Spinner />;
  if (status === "error")   return <ErrorBanner onRetry={...} />;
  if (!assets.length)       return <EmptyState />;

  return (
    <ul>
      {assets.map(a => (
        <li key={a.id}>                 {/* stable key, never the array index */}
          <button onClick={() => onSelect(a)}>{a.name}</button>
        </li>
      ))}
    </ul>
  );
}
  • Props come from the parent and are read-only. State is owned by the component and changing it triggers a re-render.
  • The dependency array controls when the effect re-runs. Omitting a dependency is the most common React bug — the effect closes over a stale value.
  • Cleanup (the returned function) cancels in-flight work. Without it you get "state update on an unmounted component" and race conditions where an old response overwrites a new one.
  • Keys must be stable and unique. Using the array index means React reuses the wrong DOM node when the list reorders — you see it as input values jumping between rows.
The four states rule. Notice the component handles loading, error, empty and data. Shipping only the data path is the most common front-end review comment there is — showing all four unprompted marks you out.

Q11Hooks: useState, useEffect, useMemo, useCallback — and when not to▼
HookPurpose
useStateLocal state that triggers re-render
useEffectSynchronise with something outside React: fetches, subscriptions, timers
useMemoCache an expensive computed value between renders
useCallbackKeep a function identity stable so a memoised child does not re-render
useRefA mutable value that does not trigger re-render; also DOM access
useContextRead shared state without threading props through every level

Rules of hooks: only at the top level of a component (never inside a condition or loop) and only from components or other hooks. React identifies hooks by call order, which is why the order must be identical on every render.

The senior answer on useMemo/useCallback: they are not free — they cost memory and comparison on every render. Reach for them when you have measured a problem, not by default. Candidates who wrap everything in useMemo are cargo-culting, and experienced interviewers probe for it.

Q12How do you manage state and server data in a React app?▼

Separate the two kinds — this distinction is the whole answer:

  • Server state — data that lives in your API. It is cached, can go stale, needs refetching, retries and loading states. Use a data-fetching library (TanStack Query, RTK Query) rather than hand-rolling useEffect + useState everywhere. It gives you caching, deduplication, background refresh and stale-while-revalidate for free.
  • Client state — UI state: which tab is open, form input, a modal. Keep it local with useState; lift it only as far as it needs to go; reach for Context or a small store (Zustand, Redux Toolkit) only when genuinely shared.
"Most 'we need Redux' problems are really 'we're storing server data in client state'. Once server data is handled by a query cache, the amount of global client state left is usually small enough not to need a store at all."

Q13Accessibility — what a developer is expected to do▼
  • Semantic HTML first. A <button> is focusable, keyboard-activatable and announced as a button. A <div onClick> is none of those and needs four attributes to catch up. The best ARIA is no ARIA.
  • Labels tied to inputs — <label for="x"> or wrapping. Placeholder text is not a label; it disappears when you type.
  • Keyboard operability. Everything reachable by Tab, in a sensible order, with a visible focus ring. Never outline: none without a replacement.
  • Colour contrast at least 4.5:1 for body text, and never colour as the only signal — pair it with an icon or text.
  • Images: meaningful alt, or alt="" for decorative ones.
  • Live regions so screen readers announce async changes like "3 results found" or a validation error.
Coming from test automation → you may have run axe or Lighthouse audits. Say so, and make the developer-side point: accessibility issues are cheapest to fix at the component level and most expensive as a retro-fit audit, so it belongs in the definition of done — which is also exactly why accessible markup gives you stable test selectors (getByRole) instead of brittle CSS ones.
Why it matters in public-sector work: infrastructure and environmental work is frequently public-sector, and public-sector procurement in most countries carries accessibility requirements (WCAG 2.1 AA). This is a compliance concern, not a nice-to-have — saying that shows commercial awareness.

Q14Front-end performance: what actually makes a page slow▼
CauseFix
Huge JavaScript bundleCode-split by route, lazy-load heavy components (maps, charts, editors), analyse the bundle and remove the accidental 300 KB date library
Unoptimised imagesModern formats, correct dimensions, loading="lazy", a CDN
Waterfall requestsParallelise; preload critical resources; avoid fetch-inside-fetch chains
Rendering thousands of rowsVirtualise the list, or paginate — the DOM is the bottleneck, not the data
Layout shiftReserve space for images and async content with explicit dimensions or skeletons
Blocking the main threadMove heavy computation to a Web Worker

Core Web Vitals are the metrics to name: LCP (largest contentful paint — how soon the main content appears), INP (interaction to next paint — responsiveness), and CLS (cumulative layout shift — does the page jump about).

Method over trivia: "I'd start from a Lighthouse run and a network waterfall on a throttled connection, because the bottleneck on a site engineer's phone on 4G is rarely the one you see on a desktop with fibre."

Q15Front-end security: XSS, tokens, and where to store them▼

XSS is attacker-controlled content executing as script in another user's browser. React escapes interpolated values by default, which handles most of it — the hole is dangerouslySetInnerHTML (the name is a warning) and any href built from user input, since javascript: URLs execute.

Defence in depth: a Content-Security-Policy header restricting where scripts may load from, and sanitising any HTML you genuinely must render.

Where to keep the access token
OptionRisk
localStorageReadable by any script on the page — one XSS and the token is gone. Convenient, commonly used, genuinely weaker.
In-memory onlySafe from persistent theft, lost on refresh — pair with a refresh flow.
httpOnly, Secure, SameSite cookieNot readable by JavaScript at all. Best option; requires CSRF protection in return.
"I'd default to an httpOnly SameSite cookie for the refresh token and keep the access token in memory. Putting a long-lived token in localStorage means any XSS anywhere on the site is a full account compromise."

The field-engineering answer. Field data capture — a surveyor recording asset condition on a bridge or a site with no signal — makes offline-first the deciding requirement, not the rendering technology. That means local storage of pending changes, a sync queue, conflict resolution when two people edited the same record, and GPS and camera access. Q17How do you test a front-end?▼
  • Unit — pure functions and hooks (Vitest/Jest).
  • Component — React Testing Library, querying by role and accessible name rather than CSS classes, so tests survive refactors and implicitly check accessibility.
  • Integration — a few screens with the network mocked at the HTTP layer (MSW), so you test the real fetch path rather than a stubbed module.
  • End-to-end — Playwright, for critical journeys only.
  • Visual regression — screenshot comparison for a design system, where a CSS change can silently break twenty screens.
Coming from test automation, this is strong ground. The principle "test what the user does, not how the component is built" is arguable from experience rather than from theory — and preferring getByRole over CSS selectors is the same locator-stability argument, applied one layer earlier.
