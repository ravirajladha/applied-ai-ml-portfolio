SECTION 1

The anatomy of a modern application

The vocabulary every other page assumes. If any of this is fuzzy, fixing it here saves you three times the effort later.

PrimerWhat an application actually is, from zero

Strip away the frameworks and a web application is four things talking to each other.

1. The client

A browser or a mobile app. It renders an interface and sends requests. Critically, you do not control it — the user can modify anything in it, replay requests, or send requests your interface never would. This is why validation on the client is a convenience and validation on the server is the actual rule. That one sentence answers a surprising number of interview questions.

2. The server (your application)

A long-running process listening on a port. It receives an HTTP request, decides what it means, does some work — usually reading or writing data — and returns a response. Everything called a "backend framework" (FastAPI, Express, Spring Boot, ASP.NET Core) is machinery for turning "a request arrived at POST /v1/assets" into "call this function".

3. The data store

The only part that remembers anything between requests. Your application process can be killed and restarted at any moment without losing data — because it holds none. That property is what makes horizontal scaling possible, and it is the whole idea behind statelessness.

4. Everything else

Caches, queues, file storage, third-party APIs, identity providers. Each is a network call that can be slow or fail, and each one you add makes the system more capable and less reliable. Good engineering is being deliberate about that trade.

The request lifecycle, end to end

Being able to narrate this is a genuine mid-level checkpoint. A user clicks "Save":

  1. DNS resolves api.example.com to an IP address.
  2. TCP connection opens; TLS handshake negotiates encryption and verifies the server's certificate. From here everything is encrypted in transit.
  3. The browser sends an HTTP request: a method, a path, headers (including Authorization and Content-Type) and a body.
  4. It arrives at a load balancer / reverse proxy, which picks one of several healthy instances of your application.
  5. Your framework's middleware pipeline runs: logging, authentication, CORS, rate limiting, request validation.
  6. Routing matches the path to a handler function. The JSON body is deserialised into an object and validated.
  7. The handler calls into your business logic, which calls a repository, which issues SQL over a pooled connection.
  8. The result is serialised back to JSON, a status code is chosen, response headers are set, and it travels back down the chain.
  9. Along the way the request emitted logs, metrics and a trace — otherwise you have no idea what happened when it goes wrong.

The test for whether your layering is real: could you add a second interface — a scheduled job, a message consumer, a CLI — that reuses the service layer without touching it? If not, your business logic is stuck inside your controllers.

The same application in four environments

One codebase, one build artefact, four sets of configuration: local (your machine), dev, test/UAT (where stakeholders sign off), production. The artefact must not be rebuilt between them — if you rebuild for production you are shipping something nobody tested. Configuration comes from environment variables, secrets from a vault.

Coming from test automation → you have lived on the consequences of every one of these ideas: environment drift, unvalidated input, flaky behaviour that was really a race condition, data that persisted between tests. You are not learning these concepts from scratch — you are learning to name them from the building side.
Q1What happens between clicking a button and seeing the data?▼

Narrate the nine steps above. Interviewers ask this because it reveals instantly how much of the stack you actually hold in your head — a candidate who jumps straight from "click" to "the API returns data" is telling you where their understanding stops.

Score the extra mark by mentioning something most people forget: the browser may send a CORS preflight OPTIONS request first; connections are pooled and reused, not opened per request; and the response may be served from a cache without ever reaching your server.

Q3Why is HTTP stateless, and how do you have a logged-in user then?▼

Each HTTP request is independent — the server remembers nothing about the last one. That is a feature: any instance can serve any request, so you can put ten instances behind a load balancer and kill any of them freely.

Identity is therefore carried on every request. Two approaches:

Server-side sessionToken (JWT)
HowCookie holds an opaque session ID; server looks up session stateSigned token holds the claims; server validates the signature
ScalingNeeds shared session store (Redis) or sticky sessionsNo lookup at all — validate offline with the issuer's public key
RevocationEasy — delete the sessionHard — a valid token works until it expires. Mitigate with short lifetimes plus refresh tokens
SuitsTraditional server-rendered web appsAPIs, SPAs, mobile, service-to-service
The follow-up they hope you cannot answer: "how do you log someone out immediately with JWTs?" You cannot, purely. You either keep a short-lived access token (5–15 minutes) with a revocable refresh token, or maintain a deny-list of revoked token IDs — which re-introduces the state you were avoiding. Saying "there's a real trade-off here" is the correct answer.

Q4What is CORS, and why does it keep breaking things?▼

Browsers enforce the same-origin policy: JavaScript on app.example.com cannot read a response from api.example.com unless that server explicitly allows it. CORS is the set of response headers by which the server grants permission — Access-Control-Allow-Origin and friends.

For anything beyond a simple GET, the browser first sends a preflight OPTIONS request asking whether the real request is allowed.

Two things to say that show you understand it properly: CORS is enforced by the browser, not the server — which is why the same call works fine from Postman or curl and fails in the app. And Access-Control-Allow-Origin: * is not a fix; it is disabling a protection, and it cannot be combined with credentialed requests anyway. List the actual origins.
Coming from test automation → you have almost certainly debugged "works in Postman, fails in the browser". Now you know the real reason, and it makes a good answer.

A runtime is what your code needs to exist while it runs: memory management and garbage collection, threading, the standard library, JIT compilation. It is why "install the JRE" or "install Python 3.12" is a deployment concern — and why containers, which bundle the runtime with the app, removed a whole class of problems.

Trap worth knowing: because TypeScript types vanish at runtime, a JSON response that does not match your interface will not throw — you get undefined three layers later. That is why you still validate incoming data at the boundary (zod, class-validator) even in a fully typed codebase.

Q6Process, thread, and asynchronous — what is the difference?▼
  • Process — an isolated program with its own memory. Crashing one does not touch another. Communication between them is expensive.
  • Thread — a unit of execution inside a process, sharing memory with its siblings. Cheap to create, but shared mutable memory is where race conditions live.
  • Asynchronous — a single thread that does not sit idle waiting for I/O. When a request goes out, the thread is released to do other work and resumes when the answer arrives.

The decision rule: I/O-bound work benefits from async (you are waiting on a network or disk, not computing). CPU-bound work needs real parallelism — more threads on a multi-core machine, or more processes.

Language specifics they may probe: Python's GIL means threads do not give you CPU parallelism — use asyncio for I/O, multiprocessing for CPU. Node.js is single-threaded with an event loop, so CPU-heavy work blocks everything and belongs in a worker thread or a separate service. Java and .NET have genuine multithreading plus async/await for I/O.

Q7Race conditions, deadlocks and idempotency in one answer▼

A race condition is when the outcome depends on the timing of concurrent operations. The classic: two requests read a stock count of 1, both decide it is available, both decrement, and you have sold the same item twice. Fixes: a database transaction with the right isolation level, optimistic concurrency (a version column, rejecting the second write with a 409), or pessimistic locking.

A deadlock is two operations each holding what the other needs. Prevention: always acquire locks in the same order, keep transactions short, and set lock timeouts.

Coming from test automation → "flaky test" and "race condition" are very often the same sentence. You have debugged more of these than most application developers. Say that: "a large share of the flakiness I've chased turned out to be genuine concurrency bugs in the application, not in the test."

Q8Coupling and cohesion — the two words that explain most design advice▼

Cohesion is how related the things inside one module are. Coupling is how much one module depends on the internals of another. You want high cohesion, low coupling, and essentially every design principle is a restatement of that.

Practical signs of high coupling: changing one class forces edits in five others; you cannot test a class without standing up half the system; a module reaches into another's data structures rather than calling its interface.

Say this and it will land: "the useful question isn't whether a design is elegant, it's what happens when the next requirement arrives. Good structure is the one where the likely change touches one place."

Q9SOLID, with the two that actually come up▼

All five are worth being able to state in one line each. The two that actually get probed:

Single responsibility

Often misread as "a class does one thing". It is really "a class has one reason to change" — one stakeholder or concern. An Invoice class that both calculates tax and renders a PDF has two: a tax law change and a design change both edit it.

Dependency inversion

High-level policy should not depend on low-level detail; both depend on an abstraction. Concretely: your service layer depends on an AssetRepository interface, not on "the SQL Server implementation". That is what lets you test the service without a database and swap the store later.

The mature caveat, and worth volunteering: applied dogmatically, SOLID produces an interface for every class and indirection nobody can follow. Add the abstraction when there is a second implementation or a real testing need — not pre-emptively. Interviewers hearing this recognise someone who has maintained code rather than only written it.
coreadvanced
Q10DRY, KISS, YAGNI — and when DRY is wrong▼

DRY — every piece of knowledge has one authoritative representation. KISS — prefer the simple solution. YAGNI — do not build for a requirement you have imagined.

The senior nuance: DRY is about duplicated knowledge, not duplicated text. Two functions that look identical today but change for different reasons should stay separate — merging them creates a coupling that hurts the first time the two reasons diverge. "A little duplication is far cheaper than the wrong abstraction" is a well-known line in the field and it is a genuinely good answer.

Q12How should an application handle errors?▼
  • Fail fast at the boundary. Validate input as it enters and reject it with a clear 400/422. Do not let bad data travel three layers in.
  • Distinguish expected from unexpected. "Asset not found" is a normal outcome and deserves a 404, not an exception logged at error level. Only genuinely unexpected failures should page someone.
  • Catch only what you can handle. A catch that logs and swallows is how bugs become invisible. If you cannot do anything useful, let it propagate to a global handler.
  • One global exception handler maps exceptions to status codes and to a consistent error body, so every endpoint fails the same shape.
  • Never leak internals. Return a correlation ID to the caller; put the stack trace in the logs. A stack trace in an HTTP response is a security finding.
{
  "type": "https://api.example.com/errors/validation",
  "title": "Validation failed",
  "status": 422,
  "detail": "condition_score must be between 0 and 100",
  "traceId": "0af7651916cd43dd8448eb211c80319c"
}

That shape is Problem Details, standardised in RFC 9457 (which obsoleted the older and more widely quoted RFC 7807). Naming it is a cheap, real credibility point — and knowing it was renumbered is a slightly better one.

Q13What makes a log line useful?▼

Structured, correlated, levelled, and free of secrets.

logger.info("asset.created", extra={
    "asset_id": asset.id,
    "site_id": asset.site_id,
    "user_id": current_user.id,
    "duration_ms": elapsed,
    "correlation_id": ctx.correlation_id,
})

Structured means fields, not an interpolated sentence — you can then query duration_ms > 1000 instead of grepping. The correlation ID is created at the edge and passed to every downstream call, so one identifier reconstructs the whole journey.

LevelMeans
ERRORSomething failed and a human needs to know
WARNRecovered, but suspicious — a retry succeeded, a fallback was used
INFOBusiness-meaningful events: created, approved, exported
DEBUGDeveloper detail, off in production
Never log passwords, tokens, full card numbers, or personal data you would not want in a support ticket. Logs get shipped to third-party tools and retained for months.

Q14Configuration and secrets — where do they live?▼

Configuration — anything that differs per environment (database host, feature flags, log level, external API URLs) comes from environment variables, so the same artefact runs everywhere. Secrets — connection strings, API keys, certificates — come from a vault (Azure Key Vault), never from the repository.

The best answer goes one step further: on Azure, use a managed identity so the application authenticates to the database or storage account as itself and there is no secret to store at all. You have removed the problem rather than protected it.

If a secret does get committed: rotating it is the fix, not deleting the commit. It is in the history, in every clone, and possibly already scraped. Interviewers ask this to see whether you understand that git history is permanent.

Q15Semantic versioning, and what counts as a breaking change▼

MAJOR.MINOR.PATCH — MAJOR for breaking changes, MINOR for backwards-compatible additions, PATCH for backwards-compatible fixes.

For an API, breaking means: removing or renaming a field, making an optional request field required, tightening validation, changing a type, changing the meaning of an existing value, or removing an enum member. Non-breaking means adding an optional request field or a new response field — provided your consumers ignore unknown fields, which is worth stating explicitly in the contract.

Also know lock files. package-lock.json, poetry.lock, packages.lock.json pin the exact resolved dependency tree so a build is reproducible. Committing them is what stops "it built yesterday" — a good short answer if asked about supply-chain or build reliability.

Q16Big-O, at the level a web developer is actually asked▼
ComplexityExample
O(1)Hash map lookup, array index
O(log n)Binary search, B-tree index lookup
O(n)Single pass over a list
O(n log n)Efficient sorting
O(n²)Nested loop over the same collection — the one to spot in a review

The practical version for application work: the nested loop that becomes a full table scan, and the loop that does I/O per iteration. The second is far more expensive in real systems — an O(n) loop making a network call per item is worse than an O(n²) in-memory computation for any realistic n.

The line to use: "in application code the algorithmic complexity is rarely the bottleneck — the number of round trips is. I look for I/O inside loops before I look at nested loops."

Q17Technical debt — what is it and when do you pay it down?▼

Technical debt is a design shortcut taken for speed that makes future change more expensive. The metaphor matters: like financial debt it is sometimes the correct decision, and it charges interest until repaid.

Deliberate and documented — "we hard-coded the tax rate to hit the deadline; ticket raised" — is legitimate engineering. Accidental and invisible is the dangerous kind.

How to pay it down without a doomed "refactoring sprint": fix it in the area you are already working in, budget a percentage of each sprint, and — most importantly — argue for it in terms of delivery, not aesthetics. "This module has caused four of our last six production issues" persuades a product owner; "the code is ugly" does not.

Q18What does "clean, maintainable code" mean concretely?▼

The JD uses this phrase, so have a concrete answer rather than adjectives.

  • Names that remove the need for a comment. daysUntilInspectionDue, not d.
  • Small functions at one level of abstraction. A function that mixes "calculate the score" with "open a database connection" is doing two jobs.
  • Comments explain why, never what. The code says what. A comment earns its place by recording the reason — the regulation, the bug, the constraint.
  • No surprises. A function called getUser should not also send an email.
  • Errors handled deliberately, not swallowed.
  • Tests that read as a specification of the behaviour.
  • Automated formatting and linting so the team never spends review time on style.
The framing that impresses: "code is read far more often than it is written, and most of it is read by someone debugging at speed. I optimise for that reader."

Q21Framework vs library, and web server vs application server▼

You call a library; a framework calls you. That inversion of control is the whole distinction — you write handlers and the framework decides when to invoke them.

Web server (nginx, IIS) terminates TLS, serves static files and reverse-proxies to your application. Application server / runtime host (Uvicorn for FastAPI, Node, Kestrel for ASP.NET Core, Tomcat for Java) executes your code. In production you usually have both, because the web server is much better at TLS, compression, static files and buffering slow clients than your application process is.

In a PaaS like Azure App Service or Container Apps, the platform provides the front end and you only ship the application — which is precisely the appeal.

Q23Horizontal vs vertical scaling, and what stops you scaling out▼

Vertical = a bigger machine. Simple, no code changes, but there is a ceiling and it is a single point of failure. Horizontal = more machines behind a load balancer. Effectively unbounded and more resilient, but your application has to tolerate it.

What breaks when you add a second instance — this is the real question:

  • In-memory session state (user gets logged out on every other request)
  • In-memory caches drifting out of sync
  • Files written to local disk that the next request cannot find
  • A scheduled job that now runs N times instead of once
  • An in-process lock or counter that is no longer global

Fixes: externalise state to Redis, blob storage or the database; use a distributed lock or a leader election for scheduled work.

The one nobody mentions: the database usually becomes the bottleneck long before the application layer does, and it is the hardest part to scale out. Read replicas, caching and connection pooling come before sharding.

Q24CAP theorem and eventual consistency, without the hand-waving▼

In a distributed system, when the network partitions you must choose between consistency (every read sees the latest write, or errors) and availability (every request gets an answer, possibly stale). Partition tolerance is not optional — networks do fail — so the real choice is CP or AP.

Eventual consistency means replicas converge given time without new writes. It is perfectly acceptable for a dashboard count or a search index, and unacceptable for an account balance or a permission check.

What makes this answer good rather than recited: tie it to a product decision. "For an asset-condition dashboard I'd happily accept a few seconds of staleness for availability. For whether a user can approve a document, I want strong consistency and I'll take the error." Interviewers are checking whether you can turn theory into a choice.
