SECTION 1

SQL and relational databases

You have written SQL for test data and verification. This section moves you from querying a schema to designing and tuning one.

PrimerDesigning a schema, and the three normal forms that matter

Keys

  • Primary key — uniquely identifies a row. Prefer a surrogate key (an auto-increment integer or a UUID) over a natural key, because natural keys turn out to change.
  • Foreign key — a reference to another table's primary key. It is a constraint the database enforces, so orphan rows become impossible rather than merely unlikely.
  • Unique constraint — business uniqueness, e.g. asset reference within a site.
  • Composite key — several columns together, common in join tables.

Normalisation, practically

FormRuleFixes
1NFNo repeating groups; one value per cellA tags column holding "a,b,c"
2NFNo partial dependency on part of a composite keySite name stored on every inspection row
3NFNo non-key column depending on another non-key columnStoring region next to site_id when region is a property of the site

The working rule: normalise until it hurts, denormalise until it works. Normalise the transactional model so there is one place to update a fact; denormalise deliberately for read performance, and know that you now own keeping the copies consistent.

A schema you could be asked to design

CREATE TABLE sites (
    id           BIGINT PRIMARY KEY,
    name         VARCHAR(200) NOT NULL,
    region       VARCHAR(80)  NOT NULL,
    created_at   TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE assets (
    id           BIGINT PRIMARY KEY,
    site_id      BIGINT       NOT NULL REFERENCES sites(id),
    reference    VARCHAR(60)  NOT NULL,
    asset_type   VARCHAR(40)  NOT NULL,
    installed_on DATE,
    CONSTRAINT uq_asset_ref UNIQUE (site_id, reference)   -- unique within a site
);

CREATE TABLE inspections (
    id               BIGINT PRIMARY KEY,
    asset_id         BIGINT      NOT NULL REFERENCES assets(id),
    inspected_at     TIMESTAMPTZ NOT NULL,
    inspector_id     BIGINT      NOT NULL REFERENCES users(id),
    condition_score  NUMERIC(5,2) CHECK (condition_score BETWEEN 0 AND 100)
);

CREATE INDEX ix_inspections_asset_time
    ON inspections (asset_id, inspected_at DESC);   -- serves "latest inspection per asset"

Points to make while writing it: constraints in the database rather than only in application code (there is always a second writer eventually); timestamps with time zone, always; NUMERIC not FLOAT for anything measured or monetary; and an index designed for the query you know you will run.

Coming from test automation → you have written verification queries against schemas designed by other people, which means you have seen bad ones: nullable everything, no foreign keys, statuses stored as free text. That is genuinely useful design experience — you know what the failure looks like from the outside.
Q1Joins, and the one that catches people▼
JoinReturns
INNEROnly rows matching on both sides
LEFTAll left rows; NULLs where the right has no match
RIGHTMirror of LEFT — rarely used; rewrite as LEFT for readability
FULL OUTEREverything from both, NULLs where unmatched
CROSSCartesian product. Almost always a mistake when it appears by accident
SELFA table joined to itself — hierarchies, comparing rows to other rows
The classic trap: putting a condition on the right table in the WHERE clause of a LEFT JOIN. It silently converts the join to an inner join, because the NULL rows fail the predicate. Put the condition in the ON clause when you want to keep unmatched rows.
-- WRONG: excludes assets that have no inspection at all
SELECT a.*, i.condition_score
FROM assets a
LEFT JOIN inspections i ON i.asset_id = a.id
WHERE i.inspected_at >= '2026-01-01';

-- RIGHT
SELECT a.*, i.condition_score
FROM assets a
LEFT JOIN inspections i
       ON i.asset_id = a.id
      AND i.inspected_at >= '2026-01-01';

Q2Write a query: latest inspection per asset (window functions)▼

"Latest row per group" is the single most commonly set SQL exercise. Know the window function version.

WITH ranked AS (
    SELECT i.*,
           ROW_NUMBER() OVER (PARTITION BY i.asset_id
                              ORDER BY i.inspected_at DESC) AS rn
    FROM inspections i
)
SELECT a.reference, a.asset_type, r.inspected_at, r.condition_score
FROM assets a
JOIN ranked r ON r.asset_id = a.id AND r.rn = 1
WHERE a.site_id = :site_id
ORDER BY r.condition_score ASC;
FunctionBehaviour on ties
ROW_NUMBER()1,2,3 — always distinct, arbitrary tie-break
RANK()1,1,3 — gaps after a tie
DENSE_RANK()1,1,2 — no gaps
LAG() / LEAD()Previous / next row's value — perfect for "change since last inspection"
Also know the aggregate rules: WHERE filters rows before grouping; HAVING filters groups after. And COUNT(*) counts rows while COUNT(col) skips NULLs — a difference that has produced a lot of wrong reports.

Q3Indexes: how to choose one, and how to kill one▼

An index is a sorted structure (B-tree) over one or more columns. Faster reads, slower writes, more storage.

Composite index column order — the left-most prefix rule

An index on (site_id, asset_type, installed_on) serves queries filtering on:

  • site_id ✓
  • site_id + asset_type ✓
  • site_id + asset_type + installed_on ✓
  • asset_type alone ✗ — cannot use the index

So order columns by: equality filters first, then range filters, then sort columns.

What makes an index unusable
QueryWhy it failsFix
WHERE YEAR(inspected_at) = 2026Function on the columnWHERE inspected_at >= '2026-01-01' AND inspected_at < '2027-01-01'
WHERE reference LIKE '%A12'Leading wildcardTrailing wildcard, or a full-text/trigram index
WHERE id = '123' on an integer columnImplicit conversionPass the right type — an ORM usually handles this, raw SQL may not
WHERE a = 1 OR b = 2Often cannot combine two indexes efficientlySometimes a UNION of two indexed queries is faster
The nuance that impresses: more indexes are not better. Each one is maintained on every insert, update and delete, and takes space and cache. An unused index is pure cost. Databases expose index usage statistics — dropping indexes nobody uses is real performance work and few candidates mention it.

Q4How do you read an execution plan?▼
EXPLAIN ANALYZE
SELECT ... ;          -- PostgreSQL: estimated AND actual rows and timing

Read it bottom-up, inner-out. What you are looking for:

SignMeaning
Seq Scan / Table Scan on a large tableNo usable index — usually the finding
Index Seek/ScanGood — an index is being used
Nested Loop with a big outer row countFine for small sets, disastrous for large — often means a missing index on the inner side
Hash Join / Merge JoinAppropriate for large joins
Estimated rows far from actualStale statistics — the optimiser is choosing badly because it has the wrong idea of the data
Sort or Spill to diskNot enough memory, or an index could have supplied the order
The answer that shows judgement: "A sequential scan is not automatically bad — on a small table it is faster than an index lookup. What I'm actually looking for is the operator where estimated and actual row counts diverge, because that is where the optimiser made a bad decision, and everything downstream of it inherits that."

Q5Transactions and isolation levels▼
LevelPreventsStill allows
Read uncommittedNothingDirty reads — reading data another transaction may roll back
Read committedDirty readsNon-repeatable reads, phantoms. The usual default.
Repeatable readNon-repeatable reads — the same row read twice gives the same valuePhantom rows appearing in a range
SerializableEverything — behaves as if transactions ran one at a timeNothing; costs concurrency and may cause serialisation failures you must retry

The three anomalies: dirty read (uncommitted data), non-repeatable read (a row changes between two reads in your transaction), phantom read (new rows appear in a range you already queried).

The practical follow-up: "how do you stop two users overwriting each other?" Do not reach for Serializable. Use optimistic concurrency: a version or rowversion column, included in the WHERE clause of the update. If zero rows are affected, someone else changed it — return 409 Conflict and let the user decide. It scales far better than locking and matches how users actually think about the problem.

Q6Deadlocks, long transactions and connection pools▼
  • Deadlock — two transactions each hold a lock the other needs. The database detects it and kills one with an error. Prevent by acquiring locks in a consistent order and keeping transactions short.
  • Long transactions are the underlying disease. A transaction that stays open while calling an external API holds locks and a connection for the whole round trip. Never do I/O inside a transaction.
  • Connection pool exhaustion presents as a mysterious application-wide hang: every request waits for a connection that a few slow queries are holding. The pool is small (tens, not thousands) by design, so one slow query pattern can stall everything.
A good, specific answer to "how would you diagnose it?" Look at the database's active sessions and wait statistics, find the blocking query, and check whether transactions are being held open across application calls. Then fix the transaction scope, not the pool size — increasing the pool usually just moves the queue.

Q7ORM or raw SQL?▼

Both, deliberately. The ORM handles the 90% that is straightforward CRUD — mapping, change tracking, migrations, parameterisation for free. Drop to SQL (or a view, or a stored procedure) for reporting queries, bulk operations and anything where you need to control the plan.

The ORM traps to name:

  • N+1 queries from lazy loading. The most common performance bug in ORM code.
  • Loading whole entities to read one column. Project into a DTO instead.
  • Bulk operations row by row. Deleting 100,000 rows one at a time through the ORM instead of one statement.
  • Not knowing what SQL is generated. Turn on query logging in development — it is the single fastest way to find the problem.
"An ORM is a productivity tool, not an abstraction that lets you avoid understanding the database. The teams I've seen get in trouble with one are the teams that never looked at the SQL it emitted."

Q8When would you use something other than a relational database?▼
StoreFits
RelationalStructured data with relationships and transactions. The default; the burden of proof is on the alternative.
Document (Cosmos, Mongo)Records with varying shape, read as whole aggregates by key, needing horizontal scale.
Key-value (Redis)Caching, sessions, rate-limit counters, distributed locks. Usually alongside, not instead.
Time-seriesSensor readings — huge append-only volumes, queried by time window, with downsampling and retention policies.
Search (Elasticsearch, Azure AI Search)Full-text relevance, faceting, fuzzy matching. A database LIKE is not search.
GraphRelationship traversal — dependency networks, "what else is affected if this fails".
Spatial (PostGIS)Geometry: "which assets are within 500 m of this flood boundary". Very relevant in infrastructure work.
Polyglot persistence is normal — a real system uses SQL for transactional data, Redis for caching, blob storage for documents and a search index for lookup. The skill is justifying each one, not picking a favourite.

SECTION 2

Data engineering workflows

A common preferred qualification, and half of "work with data engineers to operationalize analysis pipelines". You need the vocabulary and the shape, not a data engineer's depth.

PrimerWhat a data platform looks like

Application databases answer "what is true right now, for this record". Analytics needs "what happened across everything, over time". Those are different access patterns, so they get different systems — and understanding why is most of what an application developer needs to know.

OLTP (your application database)OLAP (the analytics platform)
AccessMany small reads and writes by keyFew huge scans and aggregations
ModelNormalisedDenormalised — star schema
StorageRow-orientedColumn-oriented — you read three columns of a billion rows, not whole rows
LatencyMillisecondsSeconds to minutes, and that is fine

The medallion (lakehouse) architecture

LayerContainsPurpose
BronzeRaw, exactly as ingested, append-only, with load metadataNever lose the source. You can always reprocess when requirements change — which they will.
SilverCleaned, typed, de-duplicated, conformed, joinedA trustworthy, queryable version of reality
GoldBusiness aggregates, star schemas, ML feature tablesServes dashboards, reports and models

Why bronze exists is the point worth making: transforming on ingest and discarding the raw data means a bug in the transformation is unrecoverable. Cheap storage removed the reason to throw anything away.

The Azure toolchain

ToolRole
Azure Data FactoryOrchestration and ingestion — connectors, schedules, dependencies, retries. The scheduler and mover.
DatabricksSpark for large-scale transformation and ML. Where the heavy compute happens.
Synapse Analytics / Microsoft FabricWarehousing and analytics, increasingly consolidated under Fabric.
ADLS Gen2The storage layer underneath all of it.
Power BIWhat the business actually looks at. Worth remembering — it is often the real requirement.
Q9ETL vs ELT — and why ELT won▼

ETL: extract, transform in a separate engine, load the result. Designed when storage and compute were expensive and you only kept what you needed.

ELT: extract, load raw, transform inside the warehouse or lakehouse.

ELT is now the default because cloud storage is cheap and warehouse compute is elastic. The real benefit is not performance — it is that you still have the raw data. When a definition changes or a bug is found, you reprocess. Under ETL, the untransformed data is gone.

Where ETL still wins: when the data cannot be landed raw for legal or privacy reasons — personal data that must be masked or tokenised before it is stored. That is a good caveat to offer, and it shows you think about governance.

Q10Batch or streaming?▼
BatchStreaming
ProcessesA bounded set on a scheduleUnbounded events as they arrive
LatencyMinutes to a daySeconds
ComplexityLow — rerun it if it failsHigh — windowing, late-arriving data, state, exactly-once concerns
CostLowerAlways-on compute
"I'd start by asking what decision the data supports and how quickly it has to be made. A lot of 'real-time' requirements turn out to mean 'not tomorrow morning', and a 15-minute micro-batch gives you that at a fraction of the complexity. Genuine streaming is worth it when something acts on the event automatically — a threshold alarm on a sensor, for instance."
The concepts to name if streaming comes up: event time vs processing time (a sensor's reading is timestamped when it was taken, not when it arrived), windowing (tumbling, sliding, session), and watermarks (how long you wait for late data before closing a window). Those three terms show you have looked past the marketing.

Q11Spark, enough to be useful▼

Spark distributes a computation over a cluster. Data is split into partitions; each executor processes partitions in parallel.

from pyspark.sql import functions as F

readings = spark.read.format("delta").load("/mnt/bronze/sensor_readings")

daily = (readings
    .filter(F.col("recorded_at") >= F.lit("2026-01-01"))
    .withColumn("day", F.to_date("recorded_at"))
    .groupBy("site_id", "day")
    .agg(F.avg("value").alias("avg_value"),
         F.max("value").alias("max_value"),
         F.count("*").alias("reading_count")))

daily.write.format("delta").mode("overwrite").save("/mnt/silver/daily_readings")
  • Transformations are lazy (filter, groupBy); nothing runs until an action (write, count, collect). Spark optimises the whole plan before executing it.
  • Shuffles are the cost. A groupBy or wide join moves data across the network between executors. Minimising shuffles is most of Spark tuning.
  • Data skew — one key with vastly more rows than others makes one task run for hours while the cluster idles. The commonest real Spark problem.
  • Never collect() a large DataFrame — it pulls everything into the driver's memory and kills it.
Honest positioning: "I understand the model — partitions, lazy evaluation, the cost of shuffles — and I've written PySpark, but I haven't tuned a large production cluster. Where I'd add value is on the engineering side: making pipelines idempotent, testable and observable, which is often where notebook-grown pipelines are weakest." That is exactly the gap these roles describe, and it is an honest one to claim.

Q12File formats: why Parquet and Delta rather than CSV▼
FormatProperties
CSVHuman-readable, universal, and bad: no types, no schema, no compression, must be read entirely.
JSONFlexible and self-describing, but verbose and slow to scan at volume.
ParquetColumnar, compressed, typed, with per-column statistics. Reading three columns of a hundred skips the rest entirely. The analytics standard.
AvroRow-oriented, strong schema evolution. Good for streaming and message payloads.
Delta LakeParquet plus a transaction log: ACID on a data lake, schema enforcement, time travel, upserts (MERGE). The default on Databricks.
What Delta actually solves: on plain Parquet, a job that fails halfway leaves partial files that readers will happily pick up. The transaction log makes writes atomic, so readers only ever see complete versions — and "time travel" lets you query the table as it was before a bad load. Being able to say why Delta exists, not just that it does, is the differentiator.

Q13What makes a data pipeline production-grade?▼

This is where an application developer adds the most value to a data team, so it is the answer to invest in.

  • Idempotent. Re-running the same day's load produces the same result rather than doubling it. Use overwrite-by-partition or MERGE, never blind append.
  • Backfillable. Parameterised by date so you can reprocess history when a bug is found — because one will be.
  • Incremental with a watermark, so it does not reprocess everything nightly and grow linearly in cost.
  • Schema-aware. A silently added upstream column should be handled deliberately, not break the job at 3am — or worse, be dropped without anyone noticing.
  • Validated. Row counts within expected bounds, nulls in required fields, ranges, referential checks. Fail loudly rather than publishing wrong numbers.
  • Observable. Runtime, rows in and out, and alerting on failure and on suspicious success — a job that finishes in 3 seconds instead of 20 minutes processed nothing.
  • Versioned and reviewed. Pipeline code in Git, deployed by CI/CD, not edited in a notebook in production.
  • Tested. Transformation logic unit-tested on small fixtures.
This is the entry point into data work for an application developer. Notebook-grown pipelines are typically strong on analysis and weak on exactly these engineering properties. "The gap I'd expect to help close is turning analysis code into pipelines that are idempotent, tested, version-controlled and alerting" is a precise, credible offer, and it is close to a direct quote of how these roles describe the work.

Q14Star schema and slowly changing dimensions▼

A star schema has a central fact table (the measurements — one row per inspection, with numeric values and foreign keys) surrounded by dimension tables (the descriptive context — asset, site, date, inspector). Denormalised on purpose, because analytical queries filter and group by dimensions and sum facts.

Slowly changing dimensions handle attributes that change over time:

TypeBehaviour
Type 1Overwrite. History lost. Fine for a corrected typo.
Type 2Add a new row with validity dates and a current flag. Preserves history — the most commonly asked.
Type 3Keep a "previous value" column. Only one step of history.
Why Type 2 matters, concretely: if a site is reassigned to a different region in 2026, a report on 2024 inspections should still show the 2024 region. Overwriting the dimension silently rewrites history — and if that report went to a regulator, that is a serious problem, not an inconvenience.

Q15Data quality, lineage and governance▼

Quality dimensions: completeness (are values missing), accuracy (do they match reality), consistency (do systems agree), timeliness (is it current enough), uniqueness (no duplicates), validity (conforms to rules).

Lineage is knowing where a number came from — which source, through which transformations. The moment a stakeholder challenges a figure in a report, lineage is the only thing that resolves it. Azure Purview / Microsoft Fabric provide this centrally.

Governance: who may see what, retention periods, personal data handling, and audit. For public-sector infrastructure work, the retention and audit requirements are contractual.

The practice to name: data quality checks as a gate in the pipeline, not a report someone reads afterwards. If the row count drops 40% overnight, stop and alert rather than publishing — because a dashboard that is quietly wrong is worse than one that is visibly broken. That is exactly the same argument as a failing build stopping a deployment, which is a nice bridge from your background.

Q16Geospatial and time-series data▼

Worth ten minutes of preparation because almost no other candidate will raise it, and it is the domain the whole company works in.

Geospatial
  • Data types: point (an asset), linestring (a road, a pipeline), polygon (a site boundary, a flood zone).
  • Coordinate reference systems matter: WGS84 (lat/long, EPSG:4326) for global positioning, a projected local CRS for accurate distance and area. Mixing them silently gives wrong answers — this is the classic geospatial bug.
  • Queries are spatial predicates: within, intersects, distance, buffer. They need a spatial index (R-tree / GiST) or they are full scans.
  • Tools: PostGIS on PostgreSQL, spatial types in Azure SQL, GeoJSON on the wire, map tiles for rendering, and formats like Shapefile and GeoPackage from survey teams.
Time-series
  • Append-heavy, queried by time window, and it grows without limit — so retention and downsampling are design requirements, not afterthoughts. Keep raw for 90 days, hourly aggregates for 2 years, daily forever.
  • Partition by time so old partitions can be dropped cheaply and queries prune.
  • Gaps and irregular intervals are normal — sensors fail, batteries die. Interpolation and gap detection are part of the pipeline, and "no data" must be distinguishable from "zero".
"The thing I find interesting about this domain is that the data has physical constraints software people aren't used to — a coordinate system you can get subtly wrong, and an asset whose record has to outlive several generations of the system that holds it."
