# Edge AI Foundations (M1, S1-S2): coverage spec

**Ladder:** Machine Learning on the Edge (AIMLCZG535) › Module 1 Foundations of Edge AI (Sessions 1-2)   ·   **Prerequisites:** ml-what, ops-serving (for general serving patterns)
**Why it matters for AI/ML:** Module 1 answers the first architectural question of every edge project: where must inference run, and why? It builds the vocabulary (embedded systems, IoT, sensors, AI/ML, embedded ML, TinyML, DSP), defines Edge AI, justifies it with BLERP, contrasts cloud, fog and edge AI, places them on the cloud-to-device continuum, names the four key characteristics (latency, bandwidth, privacy, power) and the sensing → inference → actuation architecture. The mid-sem papers test it with latency-budget arithmetic (position error = speed × latency), the five-stage Edge AI pipeline and its preprocessing failure mode, and the "five-question deployment decision framework" (BLERP applied letter by letter, forcing or not) on an Indian fleet scenario with a vendor "upload every N hours" proposal.

## Must-know facts
- Edge AI = running ML inference on (or very near) the device that produces the data, instead of sending raw data to a remote cloud. The slides: Edge AI = edge devices + AI. It ranges from simple conditional logic (a threshold) to compressed deep networks in kilobytes.
- Building blocks: an embedded system is a computer that does one dedicated job inside a device, with limited memory, compute and power; IoT = physical things with sensors, software and connectivity that collect and exchange data (first IoT device: the 1982 CMU Coke machine); a sensor converts a physical property into a signal; edge computing processes and stores data at the periphery of the network.
- AI (slides): "knowing the right thing to do at the right time"; ML is one way to build it. Collect → train → infer → generalize. Parameters change in training and are fixed in inference; training needs far more compute.
- Concept hierarchy: AI ⊃ ML ⊃ embedded ML ⊃ TinyML, with DSP paired throughout. Embedded ML is usually inference only; TinyML runs on MCUs, DSPs and small FPGAs with kilobytes of RAM/ROM. DSP and the model must be co-designed.
- Use ML only when the rules are not fixed (bearing faults vary by machine); a fixed table (marks → grade points) needs no model. Not every application needs an LLM or even deep learning.
- Edge sensor data is "high volume, low information density" (about 2% of traffic footage matters): process on the device and transmit only what matters.
- BLERP (Jeff Bier, Edge AI and Vision Alliance; T1 Ch 1): Bandwidth, Latency, Economics, Reliability, Privacy. It is a filter, not a score: one or two strong letters can justify the edge; apply it per task, not per device. Slide examples: vibration sensors (B), Mars rovers (L), camera traps (E), safety-critical factory monitoring (R), home security camera (P).
- The papers' "five-question deployment decision framework" = BLERP applied letter by letter: for each letter say forcing or not, the constraint, and the architectural implication. Connectivity is the R question; data volume and the ₹ bill are B and E. Power/battery life has no letter: raise it under E (maintenance cost) or R (unattended operation).
- One forcing letter is enough to require on-device inference; the cloud can still be used for non-critical work (training, dashboards).
- Cloud-only limitations: round-trip latency, dependence on connectivity, bandwidth and data-transfer cost, privacy exposure of raw data, and radio energy.
- Physics sets a floor: light in fibre covers about 200 km per ms. Server speed only shrinks compute time, not network time.
- Position error = speed × latency. 3 mm/s × 35 ms = 0.105 mm; 20 m/s × 100 ms = 2 m. If the budget is smaller than the cloud round-trip (10 ms vs 80 ms), inference must run on the device.
- Cloud AI: virtually unlimited compute, best for big models, training and global aggregation, highest latency and bandwidth cost. Edge AI: on the sensor-bearing device, no network hop, works offline, strong privacy, tight resources. Fog AI (Cisco 2012, OpenFog Consortium): fog nodes (routers, set-top boxes, switches, IoT gateways) between device and cloud; an extension of the cloud for a geographic area, not standalone.
- Cloudlet (CMU 2009, "data centre in a box", Wi-Fi, single hop, low context awareness) vs fog (single or multi-hop, Bluetooth/Wi-Fi/mobile, mid) vs MEC (ETSI 2014, renamed Multi-access Edge Computing 2016; server in the base station, mobile network, single hop, high).
- The three edges (Edge AI Foundation): heavy (on-site servers), smart (vacuum, AI camera, robot-arm controller, drone), embedded (vibration sensor, motion sensor, smart label).
- The continuum: End devices ⇄ Edge ⇄ Fog ⇄ Cloud; data flows up, updated models flow down; the cloud will not be replaced. Zhou et al. (2019), as on the slide, list six levels: cloud intelligence, cloud-edge co-inference, edge-cloud split inference, edge inference, edge on-device, fully on-device intelligence. Training in the cloud and inferring on the device is still Edge AI.
- Hybrid intelligence: edge reacts (immediate decisions, filtering, events), fog coordinates (multiple devices, short-term buffering, consolidation), cloud learns (training, cross-site analytics, long-term storage, global knowledge).
- Four key characteristics: bandwidth (cellular links are often the scarcest resource at remote sites), latency (time from event to response; for remote assets the alternative may be periodic human inspection), privacy (keeping raw data local reduces exposure, it does not guarantee privacy), power efficiency (radio transmission is the most energy-hungry task; efficient edge AI can make a device run for years).
- Seven differences from server-side AI: training on the edge is rare; focus on sensor streams; models must be small; feedback loops are limited; compute is heterogeneous; "good enough" is the goal (except safety-critical systems); tools are still evolving. Edge AI is a subset of AI.
- Responsible Edge AI: privacy (on-device stores still need protection), security (physically reachable devices: firmware signing, secure boot), sustainability (manufacturing billions of devices and e-waste: not automatically green).
- Four market domains: keeping track of objects; understanding and controlling systems; understanding people and living things; transforming signals. Products: Izoelektro RAM-1 (forest-fire risk on power lines, ~20-year battery), SlateSafety BioTrac (first responders), OpenCollar Edge (elephants, ~5-year battery); Edge AI for good: Smart Parks, RAM-1, oral cancer screening (screening, not diagnosis), coffee-leaf disease ID.
- Architecture: sensing → inference → actuation; only the sensor, the inference task and the action change between products. Actuation can be a message (send selected images).
- The five-stage pipeline the papers ask for: data acquisition (sensing) → preprocessing → inference → post-processing / decision → action. It refines the three-stage architecture; do not confuse it with the five-stage development lifecycle (develop & train → optimize & deploy → run inference → monitor & diagnose → iterate).
- Preprocessing mismatch is the stage most likely to degrade accuracy from laptop to device. z = (x − μ) / σ with the TRAINING μ and σ.
- Model-update workflow: devices collect operational data → samples to cloud storage → cloud retrains and validates → deployment service distributes → devices install and activate. Two-stage build: development (design, collect, train, save weights and base model) off-device; deployment on the device.
- Daily data volume = rate (Hz) × bytes per sample × 86,400 s; the papers use decimal MB (10^6 B).

## Common traps (each one must have at least one question)
- "Buy a faster cloud server" to meet a 10 ms budget -> the round-trip is network and propagation time.
- Treating the cloud round-trip as the only latency -> sensor, preprocessing and actuation also consume the budget.
- Forgetting units in position error (mm/s × ms) -> 3 mm/s × 35 ms is 0.105 mm, not 105 mm.
- Fog = cloud, or fog as a standalone replacement -> fog is a local extension of the cloud.
- Edge AI means training on the device, or "trained in the cloud, so not Edge AI" -> Edge AI is defined by where inference runs.
- Blaming the model file when a deployed model outputs random classes -> check preprocessing first.
- Answering the five pipeline stages with the five lifecycle stages -> the pipeline runs the model, the lifecycle builds it.
- A cheap daily upload cost means the cloud plan is viable -> Latency, Reliability and Privacy can still force the edge.
- Treating BLERP as a points total, or applying it per device -> one forcing letter is enough, and each task gets its own verdict.
- Calling Latency forcing when the deadline is minutes and the round-trip is milliseconds -> say "not forcing" and name the letter that is (usually R or P).
- Putting power/battery under the P of BLERP -> P is Privacy; battery life belongs under E or R.
- Picking the most accurate model that does not fit -> filter on RAM and latency first ("good enough"), except in safety-critical systems.
- "On-device means fully private" -> privacy is relocated: theft, remote access and firmware remain.
- "Edge AI is automatically green" -> manufacturing and e-waste count.
- Event-only reporting -> silence cannot be told apart from a dead device; add a heartbeat.
- Retraining only on uploaded alerts -> the set is biased; sample normal data too.
- "Hybrid" read as "everything twice" -> each tier does the work it is best at.
- MB vs MiB confusion in cost calculations -> state the convention (the papers use 10^6 bytes).

## Interview angle
1. **"When would you run a model on-device instead of on a server?"** Use BLERP per task: data too big to ship (B), millisecond deadlines (L), per-request costs at scale (E), must work offline (R), sensitive data (P). One strong letter is enough; training and analytics usually stay in the cloud, so most systems are hybrid: edge reacts, fog coordinates, cloud learns.
2. **"Your budget is 10 ms and the cloud round-trip is 80 ms. Options?"** Inference must move on-device or to a co-located edge node; a faster server does not help because the gap is network time.
3. **"A model works on the laptop but gives random output on the MCU. Where do you look?"** Preprocessing: normalisation constants, sample rate, window length and input layout must match training. Add a golden-input test.
4. **"Explain fog computing to a web developer."** Like a regional CDN or a BFF layer: a local tier that aggregates and pre-processes many devices before anything goes to the origin; it extends the cloud, it does not replace it.
5. **"Is 95% accuracy good enough for your edge model?"** Use-case based: yes if it fits the device and meets latency for a non-critical task; no for safety-critical systems, where the hardware must give way.
