# Privacy & Ethics in NLP (S8): coverage spec

**Ladder:** NLP Applications (AIMLCZG519) › Session 8 Privacy and Ethics in NLP   ·   **Prerequisites:** ml-metrics (confusion matrix, TPR/FPR), nlpa-overview (NLP pipeline), nlpa-qa-conv (chatbots)
**Why it matters for AI/ML:** Every NLP application ingests emails, chats, resumes or medical notes. Session 8 walks the whole lifecycle (data collection, annotation, training, evaluation, deployment, monitoring) and asks what can go wrong at each stage: missing consent, PII in corpora, biased labels, bias amplification, memorisation, hallucination, black-box decisions, no output filters, no audit trail. The end-sem papers turn this into numbers: demographic parity difference, disparate impact with the four-fifths rule, equal opportunity and equalized odds from per-group confusion counts, counterfactual name-swap tests, and regex PII masking with its false positives.

## Must-know facts
- NLP systems ingest highly personal text (emails, chats, medical records); models can memorise and leak PII; biased data gives discriminatory outputs at scale. Regulations: GDPR (EU), DPDP (India), CCPA (USA), EU AI Act. GDPR fines go up to EUR 20M or 4% of global annual turnover, whichever is higher.
- The ethical risk lifecycle: Data Collection (PII, consent, representativeness) -> Annotation (label bias, sensitive categories) -> Model Training (bias amplification, leakage) -> Evaluation (fairness, explainability, robustness) -> Deployment (monitoring, abuse, governance). Bad data -> biased labels -> biased model -> unfair decisions -> harm. Governance spans the entire lifecycle.
- Data issues: scraping without consent, no opt-out, unclear retention, no purpose limitation; underrepresented groups, historical bias, annotator label bias, geographic/language imbalance; names, emails, IDs in training data, memorisation of rare examples, inference attacks on embeddings, no provenance tracking.
- Model issues: demographic parity violations (identical text scored differently by inferred gender/race/religion), lack of explainability (GDPR Art. 22 automated decisions), training-data memorisation and extraction, calibration and hallucination; models amplify patterns in data.
- Fairness metrics: Demographic parity = equal positive (selection) rates; Equal opportunity = equal TPR; Equalized odds = equal TPR and FPR; Counterfactual = prediction unchanged if group changes; Individual fairness = similar people treated similarly.
- Exam formulas: SR = (TP + FP) / N; DPD = |SR(A) - SR(B)|; DI = SR(lower) / SR(higher), adverse impact if DI < 0.80 (four-fifths rule); TPR = TP / (TP + FN); FPR = FP / (FP + TN); EOD = |TPR(A) - TPR(B)|; counterfactual difference = |P(A) - P(B)| against a threshold (0.05 in the lab).
- Equal accuracy across groups does not mean fairness: a model that reproduces biased labels perfectly has accuracy 1.0 and DPD 1.0.
- Deployment issues: no output filtering, no monitoring (drift, fairness dashboards, anomaly alerts), audit-trail gaps, access-control failures, adversarial attacks, vendor lock-in.
- Deployment risk stack: Application (UX, misuse, prompt injection), Model (hallucination, drift, explainability), Data (privacy, retention, stale knowledge), Infrastructure (latency, scaling, logging, security). Controls: access control, safety filters, red-team testing, continuous monitoring.
- Logging: safe to log outputs, timestamp, model version, error types; avoid raw inputs with PII, full conversations unless anonymised, sensitive identifiers. Log for debugging, minimise personal data.
- Accountability: primarily the deploying organisation; shared with developers (design, safeguards), the company (deployment, monitoring) and regulators (compliance).
- Explainable/smaller models for high-stakes domains (healthcare, finance, legal); large black-box models acceptable for low-risk uses. The trade-off depends on risk level.
- Tools: Presidio, spaCy + custom NER, Google DLP (PII); DP-SGD (training with privacy guarantees); AIF360, Fairlearn, What-If Tool, Aequitas (fairness); SHAP, LIME, Captum, BertViz (explainability); Garak, Guardrails AI, NeMo Guardrails / LangKit, Rebuff (safety, red-teaming).
- Production setup: Data pipeline (PII scrubbing, consent validation, lineage) -> Training (fairness constraints, bias audit, DP-SGD, model cards) -> Evaluation (demographic parity, calibration, SHAP/LIME, red-team, robustness) -> Deployment (guardrails, rate limiting and auth, audit logging, rollback) -> Monitoring (drift, fairness dashboards, incident response, GDPR deletion pipeline).
- Differential privacy (Laplace mechanism): add Laplace noise with scale b = sensitivity / epsilon; smaller epsilon = more noise = more privacy; epsilons add up across queries (sequential composition).
- k-anonymity: every combination of quasi-identifiers is shared by at least k records; removing names alone does not anonymise.
- Model cards (Mitchell et al. 2019) document a model's intended use, evaluation across groups and limitations; datasheets for datasets (Gebru et al. 2021) document a dataset's motivation, composition, collection and consent.

## Common traps (each one must have at least one question)
- "Both groups have the same accuracy, so the model is fair" -> accuracy hides who gets the errors; check SR, TPR, FPR per group.
- DI computed as higher / lower -> it is lower / higher, compared with 0.80.
- Equal opportunity confused with equalized odds -> EO needs equal TPR only; equalized odds needs TPR and FPR.
- "Drop the gender column and the model is fair" -> proxies (names, colleges, hobbies) carry the signal.
- "Removing names anonymises the data" -> quasi-identifiers (pincode, age, job) re-identify people.
- Pseudonymised data treated as anonymous -> a reversible mapping still makes it personal data under GDPR.
- Over-broad regex (any 4 digits = card) -> years, amounts and phone pieces get masked; order of substitutions matters.
- "Public data needs no consent" -> scraping still needs a legal basis and purpose limitation (Clearview).
- "Larger epsilon is more private" -> smaller epsilon means more noise and more privacy.
- "Bias is only in the data, the model is neutral" -> models amplify skews beyond the training rates.
- "Log every full conversation for debugging" -> log outputs, versions, error types; anonymise or skip raw PII.
- "The user (or the developer alone) is accountable" -> the deploying organisation leads, responsibility is shared.
- "A model card is a marketing page" -> it must state intended use, per-group evaluation and limitations.
- "Ethics is a training-time fix" -> the course stresses every lifecycle stage, including post-deployment audits.
- Ambiguity vs bias in translation -> a gender-neutral source pronoun forces a choice; defaulting by occupation is the bias.

## Interview angle
1. **"Your resume screener has 70% accuracy for both groups. Ship it?"** Not yet: compute selection rates and TPR/FPR per group. Equal accuracy can hide a 0.80 vs 0.50 TPR gap and a DI below 0.80. Fix data, mask proxies, re-audit, add human review.
2. **"How do you keep PII out of a support-chat model?"** Scrub before training (regex + NER, Presidio), minimise and pseudonymise, DP-SGD if feasible, output PII filter, don't log raw inputs, red-team for extraction.
3. **"What does epsilon mean in differential privacy?"** The privacy loss bound; Laplace noise scale is sensitivity / epsilon, so smaller epsilon adds more noise; repeated queries spend budget.
4. **"Who is accountable when a health chatbot gives harmful advice?"** The deploying organisation first; developers for safeguards; the company for monitoring; regulators for enforcement. Design human escalation and audit logs so it can be traced.
5. **"Black-box LLM or a smaller interpretable model?"** Depends on risk: interpretable for healthcare, finance, legal decisions (GDPR Art. 22 explanations); the large model is fine for low-stakes support chat.
