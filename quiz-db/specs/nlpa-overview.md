## Must-know facts
- Core tasks (tokenization, POS tagging, NER, parsing, coreference resolution) are building blocks; applications (MT, IR, summarisation, dialogue systems/agents, sentiment/market analysis) are end-to-end products built from them.
- Course applications: spell and grammar checking, QA and conversational AI, knowledge-graph applications including RAG variants, MT, IE, sentiment and opinion mining, plus privacy & ethics and scalable & efficient NLP. All discussed with hybrid approaches (statistical, GenAI, agentic).
- Difficulty (course slide): easy = spam detection, language detection, intelligent document processing; moderate = sentiment analysis, speech recognition, question answering; hard = summarisation, machine translation, open conversation. Spam detection with Naive Bayes reaches near-perfect accuracy at minimal cost.
- Assistant ladder: notification -> FAQ -> contextual (needs memory and tools) -> personalised -> autonomous organisation of assistants. Notification and FAQ can be rule-based or statistical; contextual and above need GenAI/agentic designs.
- Ambiguity: lexical (bank, aid vs aide), syntactic/attachment ("I saw the man with the telescope"), semantic/word sense ("he wrote the last sentence two years later"), pragmatic/referential (pronouns, intent). Also multilinguality, low-resource languages, code-mixing, domain diversity.
- NLTK is a Python teaching/research toolkit with many corpora (needs nltk.download for punkt_tab, averaged_perceptron_tagger_eng, vader_lexicon); spaCy (Cython) is an industrial pipeline loaded as a model (spacy.load('en_core_web_sm')) that runs tokenizer -> tagger -> parser -> NER in one call; Hugging Face transformers gives pretrained models via pipeline(task).
- spaCy entity labels in the notebook: PERSON, ORG, GPE (countries/cities/states). Penn POS tags: NN, NNP, VB, VBZ, JJ, DT, IN.
- VADER is a rule-based sentiment lexicon for social media; it returns neg, neu, pos and compound (-1 to +1); capitals and '!!!' boost intensity.
- Porter stemming chops suffixes by rule (studies -> studi, was -> wa, university/universe -> univers); lemmatization returns dictionary forms (studies -> study, was -> be with a verb POS).
- Course checklist: if the task and labels are well defined, use a conventional NLP approach (rules or statistics); use an LLM only when the problem justifies its cost; always keep human control and a fallback.
- Evaluation per application: MT = BLEU/chrF (overlap), COMET (learned), human review; spell/grammar = precision, recall, F0.5 (precision-weighted), ERRANT per error type, M2 scorer; IE = strict span+type F1, exact vs partial match; sentiment = macro F1, per-class recall, confusion matrix.

## Common traps (each one must have at least one question)
- "Use an LLM agent for everything" -> spam, notifications and FAQs are solved cheaply by classic methods; the course starts cheap and escalates.
- Splitting sentences on every '.' -> breaks at "Dr." and "U.S."; use a trained sentence splitter.
- `str.split()` as a tokenizer -> punctuation stays glued to words ("language.").
- Stemmer output treated as real words -> "studi", "wa" are not words; use a lemmatizer when output is shown to users.
- Lemmatizing "was" without a POS -> WordNet treats it as a plural noun and returns "wa"; pass pos="v" to get "be".
- Lowercasing + stopword removal before NER or monitoring -> "US" becomes "us" and is deleted (negations like "not" are also on stock lists).
- Lowercasing before NER -> loses the capitalisation cue for proper nouns.
- Thinking spaCy downloads nothing -> its models are separate packages; NLTK needs resource downloads too.
- High BLEU = good translation -> "15 days" vs "30 days" has high overlap but a critical error.
- Weighted F1 or accuracy on imbalanced data -> hides a class with zero recall; report macro F1.
- One string = one meaning -> attachment and word-sense ambiguity give several valid parses.

## Interview angle
1. **"A bank wants a support bot. Where do you start?"** FAQ/intent tier for the repetitive 50-60%, NER for amounts/dates/accounts, context management for multi-turn, Hindi support, and a human handoff with full chat history; escalate to RAG or agents only for the long tail.
2. **"NLTK or spaCy for production?"** spaCy: one fast Cython pipeline, trained models, consistent Doc objects. NLTK: teaching, corpora, many algorithms and some Indian-language resources. Either way pin models and versions.
3. **"Why is NLP hard?"** Ambiguity at every level (lexical, syntactic, semantic, pragmatic), thousands of languages and dialects, code-mixing and domain shift; errors in early stages propagate.
4. **"Rules vs ML vs LLM?"** Rules: transparent, no data, rigid. Statistical/ML: learn from labelled data, cheap at inference. Neural/LLM: context and generation, but cost, latency, hallucination. Production systems are hybrids.
5. **"Which metric?"** Match the metric to the risk: precision-weighted F0.5 for correction, strict span F1 for IE, macro F1 for imbalanced sentiment, BLEU/chrF plus COMET plus human review for MT.
