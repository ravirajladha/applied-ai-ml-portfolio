## Must-know facts
- Dockerfile = blueprint (instructions); image = read-only template built from it (`docker build`); container = a running process of an image (`docker run`). One image can start many containers.
- `docker push` uploads an image to a registry (Docker Hub, ECR, GHCR); `docker pull` downloads it. Docker's purpose: reproduce the same environment in development, staging and production.
- Docker architecture: the client (CLI) sends commands to the Docker daemon (dockerd), which builds images, runs containers and talks to registries.
- Containers share the host kernel; VMs each run a guest OS on a hypervisor. An image built for linux/amd64 does not run natively on arm64.
- Each Dockerfile instruction that changes the filesystem adds a layer; after a change, that layer and every later layer rebuild, earlier ones come from cache.
- Kubernetes features on the slide: high availability (no downtime), scalability (high performance), disaster recovery (backup and restore).
- Control plane: API server (the front door; every component talks through it), etcd (key-value store of cluster state), scheduler (assigns pods to nodes), controller manager (runs controllers such as the ReplicaSet and Deployment controllers). Nodes: kubelet (keeps the node's containers running), kube-proxy (Service networking), container runtime.
- A pod is the smallest deployable unit: one or more containers sharing network and storage. Layers of abstraction: Deployment -> ReplicaSet -> Pod -> container.
- A Service gives a set of pods (chosen by label selector) a stable IP and DNS name.
- Deployment YAML: apiVersion: apps/v1, kind: Deployment, metadata (name, labels), spec (replicas, selector.matchLabels, template with labels and containers). Status is added by Kubernetes; controllers drive actual state to the desired state (self-healing).
- Minikube: a single-node Kubernetes cluster on a laptop, run in a container or VM; `minikube dashboard` opens the web UI showing Deployments, Pods, ReplicaSets and Services.
- Basic: all at once, not outage-proof. Ramped (rolling): replace instances in batches; Kubernetes' default; needs old and new versions to coexist. Blue/green: two identical environments, switch all traffic, instant rollback, double cost. Canary: release to a small subset of users, then roll out fully.
- RollingUpdate defaults: maxSurge 25% (rounded up) and maxUnavailable 25% (rounded down).

## Common traps (each one must have at least one question)
- Image and container confused -> the image is the template, the container the running instance.
- `docker run` thought to rebuild the image -> it starts a container from an existing image.
- "Docker runs on any hardware" -> containers still need a compatible kernel and CPU architecture.
- Putting the app and its MySQL in one container (as the slide example suggests) -> one main process per container; run the DB as its own container or managed service.
- Editing an early Dockerfile line thought to rebuild only that line -> every later layer rebuilds too.
- The scheduler thought to start containers -> it only picks a node; the kubelet starts them.
- etcd thought to run the workloads -> it only stores cluster state.
- Running bare pods in production -> nothing recreates them; use a Deployment.
- Deployment selector that does not match the template labels -> the API server rejects it. The slide's Deployment YAML also omits `selector`, which apps/v1 requires.
- Writing `status` in the YAML -> Kubernetes owns it.
- Rolling update with maxUnavailable 0 and maxSurge 0 -> invalid; nothing can move.
- Rolling update assumed to avoid compatibility issues -> old and new versions serve at the same time.
- Blue/green colours taken from the slide -> the slide calls blue "staging" and green "production"; most sources call blue the current live version and green the new one. The idea is two identical environments and an instant switch.
- Canary percentage assumed exact with plain replica counts -> the share follows the replica ratio.
- Baking .env or API keys into the RAG image -> secrets leak to anyone who can pull it.

## Interview angle
1. **"What happens when you run kubectl apply -f deployment.yaml?"** kubectl sends it to the API server, which validates it and stores it in etcd; the Deployment controller creates a ReplicaSet, the ReplicaSet controller creates pods, the scheduler assigns each to a node, and that node's kubelet asks the runtime to pull the image and start the containers.
2. **"Pod vs Deployment vs Service?"** A pod runs containers; a Deployment keeps N pods of a template running and rolls out new versions through ReplicaSets; a Service gives those pods one stable address.
3. **"Rolling vs blue/green vs canary?"** Rolling: cheap and default, but mixed versions and slow verification. Blue/green: instant switch and rollback, double the environment cost. Canary: real-user validation on a small share, needs metrics and traffic control.
4. **"Why did my rolling update stall?"** New pods fail readiness, and maxUnavailable stops more old pods being removed; check events, the readiness probe and the image.
5. **"How would you containerise a RAG app?"** Retriever, generator and a FastAPI wrapper in one image with pinned requirements; keys from environment/secrets, the vector index and model weights mounted or fetched, not baked in; run it as a Deployment behind a Service.
